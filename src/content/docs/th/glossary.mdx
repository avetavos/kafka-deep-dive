ศัพท์ของ Kafka ครอบคลุมหลายชั้นพร้อมกัน: ชั้น storage (log, segment, index, offset) ที่ทุกชั้นอื่นวางอยู่บนมัน, ชั้น coordination (KRaft, controller quorum, `__cluster_metadata`) ที่มาแทน ZooKeeper ตั้งแต่ Kafka 4.0, topic/partition/replication (leader, follower, ISR, high watermark) ที่ทำให้ log ทนทานและขยายได้, producer กับ consumer (acks, idempotence, transaction, consumer group, rebalancing) ที่อ่าน/เขียนมัน และชั้น processing/integration (share group, Kafka Streams, Connect, Schema Registry) ที่สร้างอยู่บนทุกอย่างข้างต้น เวลาอ่านบทเรียนแล้วเจอคำที่ไม่คุ้น หรือไม่แน่ใจว่ายังใช้ได้อยู่กับ Kafka 4.3.1 ไหม ให้กลับมาดูที่นี่ — ทุกคำนิยามด้านล่างมาจากบทเรียนที่พิสูจน์กับ broker จริงหรือ client จริง ไม่ใช่จากความจำ

## A

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| acks | ค่าที่ producer ตั้งว่าต้องมี replica กี่ตัวยืนยันการเขียนก่อนถือว่าสำเร็จ: `acks=0` (ไม่รอเลย ได้ response ว่างกลับมาไม่มี offset — พิสูจน์แล้วว่าให้การยืนยันการส่งเป็นศูนย์ไม่ว่าผลจะเป็นอย่างไร), `acks=1` (leader ตัวเดียว) หรือ `acks=all`/`acks=-1` (ทุก in-sync replica ซึ่งเป็นค่า default จริงของ KafkaJS) | [Acks and Durability](/kafka/th/producers/acks-and-durability/) |
| ACL (Access Control List) | กฎที่ผูก principal, operation (Read/Write/...) และ resource (topic, group, ...) เข้าด้วยกัน ACL จะไม่ทำอะไรเลยจนกว่าจะตั้งค่า authorizer — `kafka-acls.sh --list` บน broker ที่ไม่มี authorizer จะโยน `SecurityDisabledException` จริง; พอเปิดแล้ว principal ที่ไม่มีสิทธิ์จะได้ `TopicAuthorizationException` จริงตอน produce/consume | [Security and Production](/kafka/th/operations-and-production/security-and-production/) |
| acknowledgement mode (ACCEPT / RELEASE / REJECT) | วิธีที่ share-group consumer จัดการ record ที่ตัวเองรับมา: `ACCEPT` (ค่า default) คือทำเสร็จแล้ว ไม่ถูกส่งซ้ำอีก; `RELEASE` ("ทำไม่เสร็จ ขอคืน") จะเพิ่ม delivery count ทุกครั้งที่ release จนกว่าจะถึง `group.share.delivery.count.limit` (default 5); `REJECT` คือทำเครื่องหมายว่าเสียถาวร ถูกอ่านครั้งเดียวแล้วไม่ถูกส่งซ้ำอีกเลย | [Choosing a Processing Layer](/kafka/th/streams-connect-schema/choosing-a-processing-layer/) |
| apache/kafka vs apache/kafka-native | Apache มี image broker สองแบบ: `apache/kafka` (JVM มี CLI tool `bin/*.sh` ครบทุกตัว) กับ `apache/kafka-native` (คอมไพล์ด้วย GraalVM เร็วกว่าประมาณ 7 เท่าจนถึง log "Kafka Server started" จากการวัดจริงบน Mac เครื่องหนึ่ง แต่ `/opt/kafka/` มีแค่ไฟล์ binary ที่คอมไพล์แล้ว — ไม่มี `kafka-topics.sh` ไม่มี CLI เลย) | [Running Kafka Locally](/kafka/th/operations-and-production/running-kafka-locally/) |
| at-least-once | record ทุกตัวถูกส่งอย่างน้อยหนึ่งครั้ง ไม่มีวันหาย ทำได้โดย commit offset ของ consumer *หลัง* ประมวลผลเสร็จ — พิสูจน์ด้วยการ kill จริงกลางช่อง: record ถูก apply สองครั้งหลัง crash ระหว่างการเขียนจริงกับการ commit | [Delivery Semantics](/kafka/th/consumers/delivery-semantics/) |
| at-most-once | record ทุกตัวถูกส่งศูนย์หรือหนึ่งครั้ง ไม่มีวันซ้ำ ทำได้โดย commit offset *ก่อน* ประมวลผล — พิสูจน์ด้วยการ kill จริง: รอดมา 3 จาก 4 record อีก 1 ตัวหายถาวรเพราะ offset ขยับผ่านมันไปแล้ว | [Delivery Semantics](/kafka/th/consumers/delivery-semantics/) |
| authorizer (StandardAuthorizer) | component ของ broker ที่บังคับใช้ ACL จริง ๆ Kafka มาโดยไม่ตั้งอะไรไว้เป็น default `authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer` คือ authorizer แบบ KRaft-native ตัวจริง (`AclAuthorizer` ยุค ZooKeeper หายไปแล้ว) — `super.users` คือรายชื่อ principal ที่ข้ามการเช็ก ACL ทุกอัน | [Security and Production](/kafka/th/operations-and-production/security-and-production/) |
| auto.create.topics.enable | ค่า default ของ broker คือ `true`: การ produce/consume ไปยัง topic ที่ยังไม่มีจะแข่งกับการสร้างจริง (`UNKNOWN_TOPIC_OR_PARTITION` ชั่วคราว แล้วสำเร็จ) ถ้าตั้งเป็น `false` (เป็น static config ต้อง restart) error เดิมจะเกิดซ้ำตลอดไปโดย topic ไม่ถูกสร้างขึ้นจริง | [Brokers, Topics & Partitions](/kafka/th/foundations/brokers-topics-partitions/) |
| auto.offset.reset / share.auto.offset.reset | ตำแหน่งที่ client เริ่มอ่านเมื่อไม่มี committed position `subscribe({ fromBeginning })` ของ KafkaJS เลือกได้ระหว่าง `earliest` (`true`) หรือ `latest` (`false`, ค่า default) ส่วนของ share group คือ `share.auto.offset.reset` (default `latest`) ซึ่งเป็น *broker config ระดับ group* ตั้งด้วย `kafka-configs.sh --entity-type groups` — ส่ง property `auto.offset.reset` ของ client ปกติให้ share consumer จะได้ `ConfigException` จริง | [Offsets & Commits](/kafka/th/consumers/offsets-and-commits/) |
| Avro / Protobuf / JSON Schema | สามรูปแบบ serialization ที่ Schema Registry จัดการทั่วไป: Avro (binary กะทัดรัด เป็นตัวเลือกที่ใช้บ่อยที่สุด), Protobuf (schema language ของ Google, เครื่องมือข้ามภาษาแข็งแรง) และ JSON Schema (อ่านง่ายด้วยตาคน) ที่ไม่ใช่: รูปแบบดิบไม่ประกาศ type อย่าง CSV | [Schema Registry](/kafka/th/streams-connect-schema/schema-registry/) |

## B

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| batch.num.messages | ตัวจำกัดขนาด batch เฉพาะของ `librdkafka` วัดเป็นจำนวน record แทนที่จะเป็น byte เปิดให้ใช้ผ่าน native surface ของ `@confluentinc/kafka-javascript` — ไม่มีชื่อเทียบเท่าใน KafkaJS หรือ Java client ตัวเปล่า | [Batching and Compression](/kafka/th/producers/batching-and-compression/) |
| bootstrap server | ที่อยู่ broker ตัวแรกที่ client เชื่อมต่อ (`--bootstrap-server` หรือ `brokers: [...]` ใน client config) จากนั้น client จะค้นพบคลัสเตอร์ทั้งหมดและว่า broker ไหนเป็น leader ของแต่ละ partition Kafka สมัยใหม่ไม่มี `--zookeeper` เทียบเท่าอีกแล้ว — เครื่องมือที่ยังรับ flag นั้นได้คือของก่อนยุค KRaft | [Brokers, Topics & Partitions](/kafka/th/foundations/brokers-topics-partitions/) |
| broker | Kafka server process หนึ่งตัว หลาย broker รวมกันเป็นคลัสเตอร์ แต่ละ broker เก็บข้อมูลบางส่วนและให้บริการอ่าน/เขียนสำหรับ partition ที่ตัวเองเป็น leader | [What Is Kafka](/kafka/th/foundations/what-is-kafka/) |
| buffer.memory | ขนาด buffer สำหรับส่งข้อมูลฝั่ง producer ของ Java client เมื่อเต็ม `send()` จะ block (สูงสุด `max.block.ms`) เป็น back-pressure KafkaJS ไม่มีการตั้งค่าเทียบเท่า — มันไม่ buffer record ล่วงหน้าก่อน `send()` แบบที่ Java client ทำ | [Batching and Compression](/kafka/th/producers/batching-and-compression/) |

## C

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| changelog topic | topic ของ Kafka ที่หนุนหลัง state store ของ Kafka Streams: ทุกการอัปเดต state store จะถูกเขียนลงไปด้วย ดังนั้น instance ที่ crash แล้ว restart ที่อื่นจะสร้าง state store ใน RocksDB ของตัวเองขึ้นใหม่ได้ด้วยการ replay changelog | [Kafka Streams](/kafka/th/streams-connect-schema/kafka-streams/) |
| cleanup.policy | ค่าระดับ topic ที่เลือก lifecycle ของ topic: `delete` (default — ลบ segment ตามอายุ/ขนาด), `compact` (เก็บแค่ค่าล่าสุดต่อ key) หรือ `compact,delete` (ทั้งคู่ — มีเพดานอายุแข็งบน snapshot ที่สร้างใหม่ได้ตาม key) | [Retention & Compaction](/kafka/th/topics-and-partitions/retention-and-compaction/) |
| `__cluster_metadata` | topic ภายในที่ KRaft จัดการ (partition 0) ซึ่ง *คือ* metadata log ของคลัสเตอร์เลย — การสร้าง topic, การเลือก leader, การเปลี่ยน ISR ทุกอย่างคือ event ที่ถูก append เข้าไปและ replicate ข้าม controller quorum `kafka-dump-log.sh --cluster-metadata-decoder` อ่านมันได้ตรง ๆ เห็น record ชนิดจริงอย่าง `TOPIC_RECORD`, `PARTITION_RECORD`, `FEATURE_LEVEL_RECORD` และ `REGISTER_BROKER_RECORD` | [KRaft & the Cluster](/kafka/th/foundations/kraft-and-the-cluster/) |
| cluster.id | ตัวตนของคลัสเตอร์ ถูกเขียนลง `meta.properties` ของทุก broker ตอน format ยืนยันบน image ของคอร์สนี้เอง: container `apache/kafka` ใหม่ที่ไม่ได้ตั้ง env `CLUSTER_ID` จะได้ค่า default ที่ฝังไว้ *ค่าเดียวกัน* ทุกครั้ง — `kafka-storage.sh random-uuid` รันสองครั้งได้ค่าต่างกันจริง พิสูจน์ว่า default ของ container (ไม่ใช่ตัวเครื่องมือ) ต่างหากที่ตายตัว | [Running Kafka Locally](/kafka/th/operations-and-production/running-kafka-locally/) |
| co-partitioning | การให้ topic สองตัวมีจำนวน partition และ partitioner เหมือนกัน เพื่อให้ key ที่ใช้ร่วมกัน (เช่น `orderId`) ตกที่หมายเลข partition เดียวกันในทั้งสอง topic เสมอ — เงื่อนไขที่ Kafka Streams ต้องการสำหรับ join แบบอิง key เพื่อเห็นทั้งสองฝั่งของ join ในเครื่องเดียวกัน ไม่ต้อง shuffle ข้าม partition | [Keys & Partitioning](/kafka/th/topics-and-partitions/keys-and-partitioning/) |
| combined controller / isolated controller | node แบบ **combined** รัน `process.roles=broker,controller` (ทำทั้งสองหน้าที่ในโปรเซสเดียว — รูปแบบที่ทุกการพิสูจน์ในโมดูล foundations ของคอร์สนี้ใช้) ส่วน controller แบบ **isolated** รัน `process.roles=controller` อย่างเดียว แลกโปรเซสที่ต้องรันเพิ่มกับการแยก blast-radius ไม่ให้ load ของ client แย่ง CPU/disk I/O ของ controller quorum | [KRaft & the Cluster](/kafka/th/foundations/kraft-and-the-cluster/) |
| commit (offset commit) | บันทึกของ consumer ว่า "ทุกอย่างก่อน offset นี้เสร็จแล้ว" Kafka เก็บมันเป็น record จริงที่ decode ได้ใน `__consumer_offsets` การ commit offset ของ record *ตัวเอง* แทนที่จะเป็น `offset + 1` คือบั๊กที่พิสูจน์แล้วว่าเกิดซ้ำได้จริง: record ล่าสุดที่ประมวลผลไปจะถูกส่งซ้ำตอน restart | [Offsets & Commits](/kafka/th/consumers/offsets-and-commits/) |
| compaction | กระบวนการของ cleaner thread ที่เก็บเฉพาะ record ล่าสุดต่อ key บน topic แบบ `compact` แล้วเก็บกวาดค่าเก่า ๆ ทิ้ง พิสูจน์ข้าม segment ด้วย `kafka-dump-log.sh` ก่อน/หลังจริง: ค่าที่ถูกแทนที่จะถูกเก็บกวาดก็ต่อเมื่อ cleaner รันจริง (คุมด้วย `min.cleanable.dirty.ratio` default `0.5`) และ segment ที่ **active** จะไม่ถูก compact เลยไม่ว่าค่าของ key ในนั้นจะเก่าแค่ไหน | [Retention & Compaction](/kafka/th/topics-and-partitions/retention-and-compaction/) |
| compatibility mode (BACKWARD / FORWARD / FULL) | กฎที่ Schema Registry บังคับใช้ก่อนรับ schema version ใหม่ของ subject: `BACKWARD` (default — schema ใหม่อ่านข้อมูลเก่าได้ อัปเกรด consumer ก่อน), `FORWARD` (schema เก่าอ่านข้อมูลใหม่ได้ อัปเกรด producer ก่อน) หรือ `FULL` (สองทางพร้อมกัน) การลงทะเบียนที่ผิดกฎถูกปฏิเสธทันที | [Schema Registry](/kafka/th/streams-connect-schema/schema-registry/) |
| `@confluentinc/kafka-javascript` | Node.js client ของ Confluent ที่ยัง maintain อยู่ สร้างบน `librdkafka` มีสอง surface จาก package เดียว: promise API แบบเข้ากันได้กับ KafkaJS (`.KafkaJS.Kafka`) และ native `librdkafka` callback API (`Producer`/`KafkaConsumer`) ที่ใช้ config key ดิบของ `librdkafka` รองรับ KIP-848 (`group.protocol=consumer`) มาตั้งแต่ `librdkafka` 2.12.0 (ต.ค. 2025) | [The Producer API](/kafka/th/producers/producer-api/) |
| compression.type | codec ที่ใช้บีบอัด batch ก่อนส่ง: `lz4`, `zstd`, `snappy`, `gzip` หรือ `none` (default) KafkaJS มีให้ **แค่** `gzip` แบบ native (ตรวจจาก source แล้ว) — `Snappy`/`LZ4`/`ZSTD` จะโยน `KafkaJSNotImplemented` เว้นแต่จะติดตั้งและลงทะเบียน codec package แยกต่างหาก วัดจริงบน JSON แบบสมจริง: `gzip` บีบ batch 500 record จาก 108,177 เหลือ 4,741 byte (22.8 เท่า); บน random byte ที่บีบไม่ได้ `lz4` กลับ **ช้ากว่า** ไม่บีบเลยประมาณ 4% | [Batching and Compression](/kafka/th/producers/batching-and-compression/) |
| config source (DEFAULT_CONFIG / STATIC_BROKER_CONFIG / DYNAMIC_BROKER_CONFIG / DYNAMIC_TOPIC_CONFIG) | tag ที่มาของ config จริงที่ `kafka-configs.sh --describe --all` พิมพ์ใน `synonyms={...}` พิสูจน์ด้วย chain สามชั้นจริง: `DYNAMIC_TOPIC_CONFIG` ของ topic เองชนะ `DYNAMIC_BROKER_CONFIG` ของ broker ซึ่งชนะ `DEFAULT_CONFIG` ที่ติดมากับตัวเครื่อง ค่าที่เป็น `DEFAULT_CONFIG` ไม่ได้แปลว่าจะ `--alter` แบบ dynamic ได้ — `auto.create.topics.enable` และ `log.dirs` ทั้งคู่ปฏิเสธ `--alter` ด้วย `InvalidRequestException: Cannot update these configs dynamically` จริง | [Brokers, Topics & Partitions](/kafka/th/foundations/brokers-topics-partitions/) |
| connector (source / sink) | หน่วยของ Kafka Connect ที่ใช้ config อย่างเดียว ใช้ซ้ำได้: connector แบบ **source** ดึงจากระบบภายนอก (ฐานข้อมูล, ไฟล์) เข้า Kafka; connector แบบ **sink** ส่งจาก Kafka ไปยังระบบภายนอก (search index, warehouse) deploy ไปยัง distributed Connect cluster ผ่าน REST API (`POST /connectors`) | [Kafka Connect](/kafka/th/streams-connect-schema/kafka-connect/) |
| `__consumer_offsets` | topic ภายในแบบ compacted ที่เก็บ offset ที่ commit ไว้ทุกอัน keyed ด้วย `(group, topic, partition)` อ่านตรง ๆ ได้ด้วย `kafka-console-consumer.sh --formatter org.apache.kafka.tools.consumer.OffsetsMessageFormatter` — ค่าที่ decode แล้วมี `offset`, `leaderEpoch` และ `commitTimestamp` | [Offsets & Commits](/kafka/th/consumers/offsets-and-commits/) |
| consumer | client ที่อ่าน record จาก topic หนึ่งตัวหรือมากกว่า ในฐานะ consumer group โดยติดตามตำแหน่งของตัวเอง (offset) ต่อ partition | [What Is Kafka](/kafka/th/foundations/what-is-kafka/) |
| consumer group | กลุ่ม consumer ที่ใช้ `groupId` ร่วมกัน Kafka มอบแต่ละ partition ให้สมาชิกกลุ่มเพียงคนเดียวในเวลาหนึ่ง ๆ ดังนั้นจำนวน partition คือเพดานของ parallelism — consumer ตัวที่ 7 บน topic ที่มี 6 partition จะว่างสนิท กลุ่มต่างกันเป็นอิสระต่อกัน แต่ละกลุ่มติดตาม offset ของตัวเองตลอดทั้ง stream | [Consumer Groups & Rebalancing](/kafka/th/consumers/consumer-groups-and-rebalancing/) |
| controller | broker ที่ทำหน้าที่เป็นส่วนหนึ่งของ KRaft metadata quorum คอย replicate metadata log ของคลัสเตอร์ ตัวหนึ่งจะถูกเลือกเป็น leader (active controller) นับตั้งแต่ Kafka 4.0 เอา ZooKeeper ออก quorum นี้เอง — ไม่ใช่ระบบภายนอก — คือที่ที่รูปทรงของคลัสเตอร์อาศัยอยู่ | [KRaft & the Cluster](/kafka/th/foundations/kraft-and-the-cluster/) |

| converter | component ของ Kafka Connect ที่แปลระหว่าง record format ภายในของ Connect กับ byte บน topic — `AvroConverter` serialize ด้วย schema id ของ Schema Registry; `JsonConverter` เขียนเป็น JSON ธรรมดา นี่คือจุดที่ Schema Registry เสียบเข้ากับ pipeline ของ Connect | [Kafka Connect](/kafka/th/streams-connect-schema/kafka-connect/) |

## D

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| dead-letter topic (DLQ) | topic ที่ record มีพิษถูก produce แยกไว้ก่อนที่ offset ของมันจะถูก commit ผ่านไป พิสูจน์ว่าลำดับมีผลจริงด้วยการ kill จริง: commit ก่อนแล้วค่อย produce ไป DLQ ทำให้ record หายถาวรถ้า crash ในช่องว่างนั้น (หาไม่เจอที่ไหนเลย); produce ไป DLQ ก่อนแล้วรอ ack ก่อน commit เสี่ยงแค่ DLQ entry ซ้ำที่ไม่เป็นอันตรายในจุด crash เดียวกัน | [Error Handling & Retries](/kafka/th/delivery-and-transactions/error-handling-retries/) |

| delivery.timeout.ms | เส้นตาย wall-clock เดี่ยวของ Java/`librdkafka` client (default `120000`) ครอบคลุมวงจรการส่งทั้งหมด — batching, network และทุก retry — ตั้งแต่ `send()` จนถึงได้รับการยืนยัน KafkaJS ไม่มีเส้นตายเดี่ยวเทียบเท่า มันจำกัด retry ด้วยจำนวนครั้งและ backoff แทน (`retries`, `initialRetryTime`, `maxRetryTime`) ซึ่งได้แค่ประมาณงบเวลารวมเท่านั้น | [Batching and Compression](/kafka/th/producers/batching-and-compression/) |
| distributed mode (Connect) | worker หลายตัวของ Connect ประสานงานกันเหมือน consumer group โดยเก็บ config ของ connector และ offset ไว้ใน topic ของ Kafka — worker ตายไปงานของมัน (task) จะ rebalance ไปยังตัวที่รอดอยู่ นี่คือโหมด production จริง บริหารผ่าน REST API; โหมด **standalone** คือ worker เดียว config ไฟล์ local เหมาะกับ demo ครั้งเดียว | [Kafka Connect](/kafka/th/streams-connect-schema/kafka-connect/) |

## E

| Term | ความหมาย | บทเรียน |
|------|---------|--------|
| eachBatch | handler ของ KafkaJS ที่รับ batch ทั้งก้อนในครั้งเดียว **และ** ฟังก์ชัน `heartbeat` ที่ต้องเรียกเองสำหรับงานที่ช้าจริง ๆ — พิสูจน์สด ๆ: งาน `eachBatch` 8 วินาที (นานกว่า `sessionTimeout` 6 วินาที) ไม่ทำให้เกิด rejoin เลยเมื่อมีการเรียก `heartbeat()` เองกลางทาง | [The Consumer API](/kafka/th/consumers/consumer-api/) |
| eachMessage | handler การอ่านที่ง่ายที่สุดของ KafkaJS ทีละ record heartbeat ถูกส่งแบบ synchronous ทันทีหลัง `eachMessage` return ในรอบ loop เดียวกัน — ไม่ใช่ timer แยก — ดังนั้น handler ที่ block นานเกิน `sessionTimeout` จะทำให้ heartbeat ของตัวเองอดตายและเกิด rebalance จริง (`The coordinator is not aware of this member, re-joining the group`) | [The Consumer API](/kafka/th/consumers/consumer-api/) |

| exactly-once (EOS) | record ทุกตัวมีผลต่อผลลัพธ์แค่ครั้งเดียว — ไม่หาย ไม่ซ้ำ — ทำได้ใน consume-transform-produce loop โดยเอา input offset ของ consumer ใส่ *ใน* transaction ของ producer ผ่าน `sendOffsets` พิสูจน์ end-to-end ด้วย `SIGKILL` กลาง transaction จริง (2 จาก 5 sends buffer ไว้ ยังไม่ commit เลย): การ restart fence transaction ที่ค้างอยู่แล้วประมวลผล batch ใหม่ทั้งก้อน จบที่ output record 5 ตัวไม่ซ้ำกันสำหรับ input 5 ตัว | [Exactly-Once Processing](/kafka/th/delivery-and-transactions/exactly-once-processing/) |
| exactly_once_v2 | ค่า `processing.guarantee` ของ Kafka Streams ที่ห่อวงจร read-process-write แต่ละรอบ — รวมถึง changelog ของ state store และ consumer offset — ไว้ใน Kafka transaction เดียว เพื่อไม่ให้ retry apply การอัปเดตซ้ำสอง | [Kafka Streams](/kafka/th/streams-connect-schema/kafka-streams/) |

| ZooKeeper (removed) | ระบบ coordination ภายนอกที่ Kafka เคยพึ่งพาก่อนมี KRaft เก็บ metadata ของคลัสเตอร์ไว้ใน ensemble แยกต่างหากที่ต้อง deploy, รักษาความปลอดภัยและปรับแต่งเอง **ถูกเอาออกทั้งหมดตั้งแต่ Kafka 4.0** — ไม่ใช่แค่ deprecated แต่หายไปเลย: ไม่มี ZooKeeper process ให้ start และ `--zookeeper` ไม่ใช่ flag ที่เครื่องมือบน broker Kafka 4.3.1 ของคอร์สนี้รับด้วยซ้ำ | [KRaft & the Cluster](/kafka/th/foundations/kraft-and-the-cluster/) |
