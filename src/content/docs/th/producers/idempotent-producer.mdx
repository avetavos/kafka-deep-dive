## ไอเดียในหนึ่งประโยค

**Idempotent producer** ติด tag ให้ทุก record ด้วย producer id, epoch และ sequence number ต่อ partition เพื่อให้ broker **ทิ้ง duplicate** ที่เกิดจาก retry ได้ — ให้การส่งแบบ exactly-once **ต่อ partition**

## ปัญหา duplicate ที่ retry สร้างขึ้น

ถ้าไม่มี idempotence การ retry อาจสร้าง record ซ้ำเงียบ ๆ producer ส่ง record broker เขียนสำเร็จ แต่ acknowledge หายระหว่างทางกลับ producer timeout แล้ว retry และ broker ก็เขียน **record เดิมเป็นครั้งที่สอง** ตอนนี้เรามีสองสำเนา แถมแยกไม่ออกด้วย (บทก่อนหน้าพิสูจน์เรื่องนี้ไปแล้วจริง ๆ — duplicate ห้าชุดจริงจาก `send()` ครั้งเดียว ด้วย `idempotent: false`)

idempotence แก้เรื่องนี้: broker assign **producer id (PID)** และ **epoch** ให้แต่ละ producer และ producer ก็ stamp ทุก record ด้วย **sequence number ที่เพิ่มขึ้นเรื่อย ๆ** ต่อ partition เมื่อ record มาถึง broker เช็ค sequence number: ถ้าเคยเห็นเลขนี้สำหรับ PID และ partition นั้นแล้ว จะ **acknowledge แต่ไม่เขียน** record ซ้ำอีก

<Callout title="เป็น default แต่เฉพาะใน Java client">
`enable.idempotence=true` เป็น **default ใน Java client** (ตั้งแต่ Kafka 3.0) **KafkaJS ตั้ง default ตรงข้ามกัน — `idempotent: false`** — คุณจึงต้อง opt in เอง อย่าสมมติว่า producer ของ KafkaJS เป็น idempotent ถ้าคุณไม่ได้ตั้งเอง
</Callout>

```properties
# The Java client: idempotence is on by default; shown explicitly here
enable.idempotence=true
# acks=all is required and applied automatically once idempotence is on
acks=all
# retries must be > 0 (defaults high) so the producer actually retries
retries=2147483647
# ordering is preserved only if in-flight requests per connection stays <= 5
max.in.flight.requests.per.connection=5
```

**KafkaJS** ต้อง opt in เองที่ producer:

```typescript
const producer = kafka.producer({ idempotent: true })
```

## producer id, epoch และ sequence number ตัวจริง บนดิสก์

นี่ไม่ใช่แค่แนวคิดนามธรรม — เป็นข้อมูลจริงใน header ของ record batch บนดิสก์ ส่ง 3 record ด้วย idempotent producer ของ KafkaJS แล้วอ่าน segment file ตรง ๆ ด้วย `kafka-dump-log.sh --print-data-log`:

```typescript
// src/idempotent-producer/send-three.ts
// @run
import { Kafka } from 'kafkajs';

const brokers = [process.env.KAFKA_BROKERS ?? 'localhost:9092'];
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}orders-idem-demo`;

const kafka = new Kafka({ clientId: 'idem-demo', brokers });

async function main() {
  const admin = kafka.admin();
  await admin.connect();
  await admin.createTopics({ topics: [{ topic, numPartitions: 1, replicationFactor: 1 }] });
  await admin.disconnect();

  const producer = kafka.producer({ idempotent: true });
  await producer.connect();
  for (let i = 0; i < 3; i++) {
    const [meta] = await producer.send({
      topic,
      messages: [{ key: `order-${i}`, value: `payload-${i}` }],
    });
    console.log(`sent order-${i} -> offset ${meta.baseOffset}`);
  }
  await producer.disconnect();
  process.exit(0);
}

main();
```

ผลลัพธ์จริง ตัดให้สั้นลง — `baseSequence`/`lastSequence` หนึ่งค่าต่อ record ทุกอันใช้ `producerId` เดียวกัน:

```text
baseOffset: 0 ... producerId: 0 producerEpoch: 0 baseSequence: 0 lastSequence: 0
| offset: 0 sequence: 0 key: order-0 payload: payload-0
baseOffset: 1 ... producerId: 0 producerEpoch: 0 baseSequence: 1 lastSequence: 1
| offset: 1 sequence: 1 key: order-1 payload: payload-1
baseOffset: 2 ... producerId: 0 producerEpoch: 0 baseSequence: 2 lastSequence: 2
| offset: 2 sequence: 2 key: order-2 payload: payload-2
```

ทุก record จาก producer session นี้แปะ `producerId: 0` (PID ที่ Kafka assign ให้ connection นี้ตอน `InitProducerId` รัน) และ `producerEpoch: 0` เหมือนกัน; `sequence` เพิ่มขึ้นทีละหนึ่งพอดีต่อ record ต่อ partition นี่คือกลไกตัวจริงที่การพิสูจน์ duplicate-จาก-retry ในบทก่อนอาศัยอยู่: เมื่อความพยายามที่ถูก retry มาถึงพร้อม `sequence` ที่ broker เคยบันทึกไว้แล้วสำหรับ `(producerId, partition)` นั้น มันจะถูกทิ้งแทนที่จะถูก append

## `enable.idempotence` ต้องการอะไรจริง ๆ — ยืนยันกับ official config reference

อ้างจาก `kafka.apache.org/43/configuration/producer-configs/` ตรง ๆ เรื่อง `enable.idempotence`:

> "enabling idempotence requires `max.in.flight.requests.per.connection` to be less than or equal to 5 (with message ordering preserved for any allowable value), `retries` to be greater than 0, and `acks` must be 'all'."

และเรื่อง `max.in.flight.requests.per.connection`:

> "if this configuration is set to be greater than 1 and `enable.idempotence` is set to false, there is a risk of message reordering after a failed send due to retries" — และ idempotence ต้องการค่านี้ **ไม่เกิน 5** "since brokers retain a maximum of 5 batches per producer"

นั่นคือ **เพดานที่ 5** ไม่ใช่ข้อกำหนดว่าต้องเป็น 1 เป๊ะ ๆ — Java client (และ cache sequence number ของ broker เอง) ยอมให้มี batch in-flight ได้ถึงห้าตัวต่อ connection โดยยังรับประกัน ordering ได้ เพราะ broker เก็บประวัติมากพอที่จะตรวจจับ batch ที่มาผิดลำดับหรือซ้ำภายในหน้าต่างนั้น

<Callout title="คำแก้ไขที่ยืนยันจาก source ของ KafkaJS เอง: เพดานนี้ไม่ได้ถูกบังคับฝั่ง client">
คงง่ายที่จะสมมติว่า KafkaJS บังคับเพดาน 5-batch แบบเดียวกัน (หรือถึงขั้นบีบ `maxInFlightRequests` ให้เหลือ `1`) ทันทีที่คุณส่ง `idempotent: true` แต่ไม่ใช่เลย อ่านตรงจาก source ของ `kafkajs@2.2.4` (`node_modules/kafkajs/src/producer/index.js`): สิ่งเดียวที่ `idempotent: true` เปลี่ยนคือ default ของ retry (`retries: Number.MAX_SAFE_INTEGER`) กับการตรวจว่า retry ไม่ถูกปิด — ไม่มี code path ไหนอ่านหรือบีบ `maxInFlightRequests` ตาม `idempotent` เลย `maxInFlightRequests` ยังคงเป็น option `Kafka.producer({ maxInFlightRequests })` ของ connection pool ที่แยกจากกันจากบทก่อนหน้า default เป็น `null` (ไม่จำกัด) ถ้าอยากได้ margin ความปลอดภัยแบบเดียวกับที่ default ของ Java client ให้ **คุณต้องตั้ง `maxInFlightRequests: 5` เอง** — KafkaJS จะไม่ทำให้คุณ และจะไม่ห้ามคุณตั้งสูงกว่านั้นด้วย
</Callout>

```typescript
// idempotent: true does NOT imply or clamp maxInFlightRequests in KafkaJS —
// verified from source. Set the connection-pool cap yourself if you want it.
const producer = kafka.producer({ idempotent: true })
const kafka2 = new Kafka({ clientId: 'orders-app', brokers: ['localhost:9092'] });
const producerWithCap = kafka2.producer({ idempotent: true, maxInFlightRequests: 5 })
```

## idempotence ต้องการอะไร และรับประกันอะไร

idempotence ไม่ได้ยืนได้ด้วยตัวเอง แต่ต้องการ config เฉพาะเพื่อให้การรับประกันเป็นจริง:

- **`acks=all`** — record ต้องถูกยืนยันโดยทุก in-sync replica
- **`retries > 0`** — retry คือต้นเหตุของ duplicate ตั้งแต่แรก ถ้าไม่มี retry ก็ไม่มีอะไรให้ dedupe
- **`max.in.flight.requests.per.connection <= 5`** — ยอมให้มี batch in-flight ได้ถึงห้าตัว **โดยยังรักษา ordering** ไว้ เพราะ broker ติดตาม sequence number และปฏิเสธอะไรที่มาผิดลำดับ

ใน Java client ทั้งสามข้อนี้ถูก **บังคับเป็น config constraint จริง** (ตั้งค่าขัดกับ idempotence จะ throw `ConfigException` ตอนสร้าง producer) ใน **KafkaJS** มีแค่ `acks` กับ `retries` เท่านั้นที่ client บังคับจริงตอน `idempotent: true` — `maxInFlightRequests` ปล่อยให้เป็นหน้าที่คุณทั้งหมด ตามคำแก้ไขด้านบน

เมื่อเงื่อนไขเหล่านี้เป็นจริง เราจะได้ **exactly-once delivery ต่อ partition ตอน retry**: ไม่ว่า record จะถูก retry กี่ครั้ง ก็ถูกเขียนลง log **ครั้งเดียว** ตัว **epoch** คือสิ่งที่ทำให้ปลอดภัยข้ามการ restart ของ producer และ network partition — epoch ใหม่กว่าจะ **fence** producer instance เก่าที่อาจเป็น zombie ทำให้ write ค้างเก่าถูกปฏิเสธ

## idempotence ไม่ใช่ transactions

จุดนี้คนสับสนบ่อย idempotence รับประกันว่า record ถูกเขียน **ครั้งเดียวต่อ partition** แม้มี retry — แต่ทำได้ **แค่นั้น** — **ไม่ได้** ทำให้การ write หลาย record หลาย partition เป็น atomic และ **ไม่ได้** ผูก write ของ producer เข้ากับการ commit offset ของ consumer

การรับประกันที่แข็งกว่านั้น — การ write แบบ atomic ข้าม partition และ exactly-once processing จริง ๆ — คือสิ่งที่ **transactions** ให้ ซึ่งสร้าง **ทับบน** idempotent producer อีกที โมดูล Delivery Semantics และ Transactions จะครอบคลุม `transactionalId`, `producer.transaction()` และ `txn.commit()` ตอนนี้จำเส้นแบ่งไว้: idempotence กำจัด duplicate จาก retry ส่วน transactions เพิ่ม atomicity

<Callout title="สรุปหนึ่งบรรทัด">
idempotent producer stamp record ด้วย **producer id**, **epoch** และ **sequence number** (พิสูจน์แล้วด้านบน ตรงบนดิสก์จริง) เพื่อให้ broker ทิ้ง **duplicate** จาก retry ให้ผล **exactly-once ต่อ partition** Java client ต้องการ **`acks=all`**, **`retries > 0`** และ **`max.in.flight.requests.per.connection <= 5`** — และบังคับทั้งสามข้อจริง **KafkaJS บังคับแค่สองข้อแรกเท่านั้น** เพดาน in-flight เป็นหน้าที่คุณต้องตั้งเอง เป็น **default ใน Java client** แต่ใน **KafkaJS คุณต้อง opt in เอง** ด้วย `idempotent: true` — และ **ไม่ใช่** สิ่งเดียวกับ **transactions** เต็มรูปแบบ
</Callout>

## Mental Model

idempotence ย้ายการตรวจจับ duplicate จาก "record นี้หน้าตาเหมือนอันเดิมไหม?" (การเทียบเนื้อหา ซึ่งเปราะและแพง) ไปเป็น "ฉัน apply พิกัด `(producerId, partition, sequence)` นี้ไปแล้วหรือยัง?" (การเทียบเลขจำนวนเต็มที่ broker ทำได้ในเวลาคงที่ ติดตามต่อ partition จำกัดแค่ batch ล่าสุดไม่กี่ตัว) โดยพื้นฐานแล้วมันคือ **ระบบพิกัด** ไม่ใช่ตัวกรองเนื้อหา — record สองอันที่ `key`/`value` เหมือนกันทุก byte แต่ sequence number ต่างกัน คือ record คนละอันสำหรับ broker และการ retry จริงของความพยายามเดิมก็ถูกจำได้จากพิกัดที่ตรงกับอันที่เคยเห็นเท่านั้น ไม่เคยเทียบ payload เลย

## Trade-offs

- **`idempotent: true`, `maxInFlightRequests` default (`null`, ไม่จำกัด)** — ตรงกับพฤติกรรม default จริงของ KafkaJS ที่ยืนยันแล้ว สะดวก แต่สละ margin ความปลอดภัยเรื่อง ordering/duplicate-detection ที่ Java client จะบังคับให้เงียบ ๆ
- **`idempotent: true, maxInFlightRequests: 5`** — ตรงกับเพดานจริงของ Java client เป๊ะ ทำให้ sequence cache 5-batch ของ broker ยัง track batch ที่ in-flight ได้ครบ เป็นตัวเลือกที่ปลอดภัย เจตนาชัด สำหรับอะไรก็ตามที่ durability สำคัญ
- **`idempotent: true, maxInFlightRequests: 1`** — serialize request ต่อ connection เข้มงวดที่สุด mental model ง่ายที่สุดและไม่มีความเสี่ยงเกินหน้าต่าง tracking ของ broker เลย แลกกับต้นทุนด้าน throughput จริง (ไม่มี pipelining)
- **`idempotent: false`** (default ของ KafkaJS) — ไม่มีกลไก PID/epoch/sequence เลย ถูกที่สุด แต่ทุก retry คือ duplicate เงียบ ๆ ที่อาจเกิดขึ้นได้ (พิสูจน์แล้วในบทก่อน)

## ความเข้าใจผิดที่พบบ่อย

- **"`idempotent: true` ใน KafkaJS บีบหรือตรวจสอบ `maxInFlightRequests` อัตโนมัติเหมือน Java client"** ไม่ — พิสูจน์จาก source แล้ว: KafkaJS ไม่มีการบีบหรือตรวจสอบแบบนั้นเลย คุณต้องตั้งเพดานเอง
- **"idempotent producer ต้องการ `max.in.flight.requests.per.connection` เป็น 1 เป๊ะ ๆ"** ไม่ — ยืนยันกับ official config reference แล้ว: ข้อกำหนดจริงคือ **`<= 5`** เพราะ broker เก็บได้สูงสุด 5 batch ต่อ producer สำหรับ track sequence `1` คือค่าปลอดภัยที่เข้มงวดที่สุด ไม่ใช่ค่าปลอดภัยค่าเดียว
- **"idempotence กับ transactions คือ feature เดียวกัน แค่ชื่อต่างกัน"** ไม่ — idempotence รับประกันแค่ว่า record ลงครั้งเดียวต่อ partition ตอน retry ไม่มีแนวคิดเรื่อง write แบบ atomic ข้าม partition หรือ consumer offset เลย นั่นคือสิ่งที่ transactions เพิ่มเข้ามาทับ
- **"producer id ใน dump-log output เป็น UUID สุ่ม ๆ"** ไม่ — มันคือเลขจำนวนเต็มเล็ก ๆ ที่ถูก assign เรียงลำดับ (`producerId: 0`, `1`, `9`, ... ในการรันของคอร์สนี้เอง) ที่แจกโดย handler `InitProducerId` ของ broker ต่อ producer session หนึ่งครั้ง คู่กับ `epoch` ที่เพิ่มขึ้นทุกครั้งที่ producer restart เพื่อ fence instance เก่าที่ค้างอยู่
