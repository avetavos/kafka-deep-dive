## แนวคิดในหนึ่งประโยค

**Kafka Streams** คือ Java library — ไม่ใช่คลัสเตอร์แยก — ที่ฝังเข้าไปในแอปของคุณเองเพื่อแปลง, รวม, และ join topic ของ Kafka ในฐานะ stream ต่อเนื่อง โดยมี state และ exactly-once guarantee ให้จัดการเอง

## KStream, KTable และ duality

Kafka Streams ให้มุมมองของ topic สองแบบ:

- **`KStream`** — ลำดับ **event** ที่ไม่มีขอบเขตและเป็นอิสระต่อกัน ทุก record คือข้อเท็จจริงใหม่ ("user คลิก") ไม่มีอะไรถูกเขียนทับ
- **`KTable`** — **changelog** ที่ตีความเป็นค่าล่าสุด **ต่อ key** แต่ละ record อัปเดตแถวของ key นั้น เหมือน `UPSERT` เข้าตาราง

นี่คือ **stream-table duality**: ตารางคือ snapshot ที่ได้จากการ replay stream ของการอัปเดต และ stream คือลำดับของการเปลี่ยนแปลงที่ได้จากการดูตาราง topic เดียวกันอ่านได้สองแบบขึ้นอยู่กับสิ่งที่ต้องการ — feed ของ event ที่วิ่งอยู่ หรือ state ปัจจุบันต่อ key

## Stateless vs stateful operations

Operation แบ่งเป็นสองตระกูล:

- **Stateless** — แต่ละ record จัดการตัวเอง: `map`, `filter`, `flatMap`, `branch` ไม่ต้องจำ record ก่อนหน้า
- **Stateful** — ผลลัพธ์ขึ้นกับ record ที่เห็นมาก่อนหน้า: `aggregate`, `count`, `reduce`, `join`, และ **windowing** (จัดกลุ่ม record เป็นช่วงเวลา) ต้องมีที่เก็บผลลัพธ์ที่กำลังสะสม

"ที่เก็บ" นั้นคือ **state store** — key-value store ในเครื่อง (RocksDB เป็นค่าเริ่มต้น) ที่อยู่ใน instance ของแอปตัวเอง เพื่อรอดจากการ crash ทุก state store ถูก back ด้วย **changelog topic** ใน Kafka: ทุกการอัปเดตถูกเขียนไปที่ changelog ด้วย ดังนั้นถ้า instance รีสตาร์ทที่อื่น Streams จะสร้าง store ขึ้นใหม่โดย replay changelog นั้น state ในเครื่องจึงคงทนโดยไม่ต้องจัดการฐานข้อมูลเอง

## Topology นับคำ พิสูจน์ด้วยการรัน `TopologyTestDriver` จริง

นี่คือตัวอย่างคลาสสิก — นับว่าแต่ละคำปรากฏกี่ครั้งใน input topic นี่ไม่ใช่สมมติฐาน: compile ด้วย `javac` ธรรมดาและ **รัน** ด้วย `java` กับ `kafka-streams-4.3.1.jar` / `kafka-streams-test-utils-4.3.1.jar` จริง (บวก `rocksdbjni`, `jackson-databind` และเพื่อน ๆ) ที่ดึงมาจาก Maven Central โดยตรงด้วย URL — ไม่มี gradle ไม่มี maven ตามข้อจำกัด toolchain ของคอร์สนี้

```java
// src/main/java/streams/WordCountTopologyTest.java
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.StreamsConfig;
import org.apache.kafka.streams.TestInputTopic;
import org.apache.kafka.streams.TestOutputTopic;
import org.apache.kafka.streams.Topology;
import org.apache.kafka.streams.TopologyTestDriver;
import org.apache.kafka.streams.kstream.KStream;
import org.apache.kafka.streams.kstream.KTable;
import org.apache.kafka.streams.test.TestRecord;

import java.util.Arrays;
import java.util.List;
import java.util.Properties;

public class WordCountTopologyTest {
    public static void main(String[] args) {
        StreamsBuilder builder = new StreamsBuilder();

        // Read the input topic as a stream of (key, line) events
        KStream<String, String> lines = builder.stream("text-input");

        KTable<String, Long> counts = lines
            .flatMapValues(line -> Arrays.asList(line.toLowerCase().split("\\W+"))) // split into words
            .groupBy((key, word) -> word)     // re-key by the word itself
            .count();                         // stateful: running total per word -> a KTable

        counts.toStream().to("word-counts");  // write the changelog of counts out

        Topology topology = builder.build();
        System.out.println(topology.describe());

        Properties props = new Properties();
        props.put(StreamsConfig.APPLICATION_ID_CONFIG, "wordcount-test");
        props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "dummy:9092");
        props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);
        props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);

        // TopologyTestDriver: an in-memory harness -- no broker needed to unit-test a topology
        try (TopologyTestDriver driver = new TopologyTestDriver(topology, props)) {
            TestInputTopic<String, String> input = driver.createInputTopic(
                "text-input", Serdes.String().serializer(), Serdes.String().serializer());
            TestOutputTopic<String, Long> output = driver.createOutputTopic(
                "word-counts", Serdes.String().deserializer(), Serdes.Long().deserializer());

            input.pipeInput(null, "the quick brown fox");
            input.pipeInput(null, "the lazy fox sleeps");

            List<TestRecord<String, Long>> results = output.readRecordsToList();
            for (TestRecord<String, Long> r : results) {
                System.out.println("word-counts: " + r.key() + " = " + r.value());
            }
            System.out.println("TOTAL RECORDS: " + results.size());
        }
    }
}
```

Output จริง (ตัดให้สั้น) จาก `javac -cp <jars> WordCountTopologyTest.java && java -cp <jars>:. WordCountTopologyTest` บน Mac เครื่องนี้:

สิ่งจริงสองอย่างที่พิสูจน์ได้: (1) `count()` compile ออกมาเป็น **สอง sub-topology** เชื่อมกันด้วย **repartition topic** ภายใน (`...-repartition`) — `groupBy` เปลี่ยน key ใหม่เป็นคำ ซึ่งไม่รับประกันว่าจะตกอยู่ partition เดียวกับ input Streams จึงแทรกขั้น repartition ให้อัตโนมัติ; (2) `the` และ `fox` ปล่อยออกมา **สองครั้ง** (ครั้งละหนึ่งครั้งต่อบรรทัด input ที่อัปเดต count ของมัน) เพราะ changelog ของ `KTable` ปล่อยทุก **การอัปเดต** ไม่ใช่แค่ยอดรวมสุดท้าย — 8 record output จาก 2 บรรทัด input ไม่ใช่ "ยอดสุดท้าย" 6 คำที่ไม่ซ้ำกัน ตรงกับ stream-table duality ในหัวข้อก่อนหน้าแบบจับต้องได้

<Callout title="TopologyTestDriver ต้องการ default serde ไม่งั้น throw ทันที">
ความพยายามครั้งแรกในการรันนี้ โดยไม่ตั้ง `DEFAULT_KEY_SERDE_CLASS_CONFIG`/`DEFAULT_VALUE_SERDE_CLASS_CONFIG` ล้มเหลวทันทีด้วย `org.apache.kafka.common.config.ConfigException: Please specify a key serde or set one through StreamsConfig#DEFAULT_KEY_SERDE_CLASS_CONFIG` จริง — state store ภายในของ `count()` ต้องการ serde และไม่ได้ถูก infer อัตโนมัติแค่จาก `Serdes.String()` ที่ส่งให้ `createInputTopic` การตั้ง `DEFAULT_KEY_SERDE_CLASS_CONFIG`/`DEFAULT_VALUE_SERDE_CLASS_CONFIG` ทั้งคู่ใน `props` แก้ปัญหาได้
</Callout>

## KIP-1071: `group.protocol=streams` ใหม่ — GA พร้อม feature set ที่จำกัด ยืนยันแล้ว

```java
// Turn on end-to-end exactly-once for the whole topology
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, "exactly_once_v2");

// The new broker-side rebalance protocol for Streams groups (KIP-1071)
props.put(StreamsConfig.GROUP_PROTOCOL_CONFIG, "streams");
```

ยืนยันสดจาก broker นี้: `kafka-configs.sh --entity-type brokers --entity-default --describe --all` แสดง `group.coordinator.rebalance.protocols = [classic, consumer, share, streams]` — `streams` เป็น rebalance protocol จริงที่เปิดใช้งานบน `apache/kafka:4.3.1` ตรงกับ `kafka-features.sh describe` ที่แสดง `Feature: streams.version  FinalizedVersionLevel: 1`

<Callout title="'limited feature set' หมายถึงอะไรจริง ๆ — คำยกมาตรง ๆ">
[ประกาศ release ของ Kafka 4.2.0](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/) ระบุตรง ๆ ว่า: **"Kafka Streams brings the server-side rebalance protocol to GA with a limited feature set."** [KIP-1071](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1071:+Streams+Rebalance+Protocol) และเนื้อหาติดตามผลขอบเขต GA ระบุข้อจำกัดชัดเจน: โปรโตคอลมาพร้อม **sticky assignment เท่านั้น** — ยังไม่มี warm-up task และ rack-aware placement; **ไม่มี static membership**; **ไม่มีการเปลี่ยน topology แบบ on-the-fly** ขณะ group กำลังรันอยู่; และการย้าย group ระหว่างโปรโตคอล classic กับ streams เป็นแบบ **offline เท่านั้น** — ทุก instance ต้องหยุดและ group ต้องว่างก่อนจะรีสตาร์ทด้วยโปรโตคอลใหม่ การตั้ง `group.protocol=streams` ใน production วันนี้หมายถึงการยอมรับข้อจำกัดเหล่านั้น ไม่ใช่ "GA" แบบไม่มีเงื่อนไขที่คำนี้มักสื่อถึง
</Callout>

## Co-partitioning: สิ่งที่เอกสารสัญญา กับสิ่งที่การรันจริงหนึ่งครั้งแสดงให้เห็น

**Stream-stream join** (`KStream.join(...)`) ต้องการให้ input topic ทั้งสองเป็น **co-partitioned** — จำนวน partition เท่ากัน, partitioning strategy เดียวกัน — เพื่อให้ partition ที่ *N* ของ topic ซ้ายต้อง join กับ partition ที่ *N* ของ topic ขวาเท่านั้น [Kafka Streams DSL developer guide](https://kafka.apache.org/43/streams/developer-guide/dsl-api/) ระบุชัดเจน: *"The input topics of the join (left side and right side) must have the same number of partitions... During the partition assignment step, i.e. at runtime, Kafka Streams verifies whether the number of partitions for both sides of a join are the same. If they are not, a `TopologyBuilderException` (runtime exception) is being thrown."* class exception ใน jar 4.3.1 ปัจจุบันคือ `org.apache.kafka.streams.errors.TopologyException` ไม่ใช่ชื่อเก่า `TopologyBuilderException` ที่เอกสารยังใช้อยู่ — ยืนยันจากการ decompile `CopartitionedTopicsEnforcer.class` จาก `kafka-streams-4.3.1.jar` จริง ซึ่งมี format string ตรงตัว `"%sTopics not co-partitioned: [%s]"` ที่ throw เป็น `TopologyException`

<Callout title="ผลลัพธ์แบบตรงไปตรงมา: ไม่ throw ในการรันจริงที่ทำซ้ำได้หนึ่งครั้งบน 4.3.1">
สร้าง topic จริงสองตัวบน broker จริง — `left-stream` (3 partitions) และ `right-stream` (5 partitions) — และ join ด้วย `KStream.join(...)` จริง (แบบ windowed, `StreamJoined.with(...)`) ในแอป `KafkaStreams` จริง (ไม่ใช่ `TopologyTestDriver`) ที่ชี้ไปยัง broker นั้น แอป reach `RUNNING` โดย **ไม่มี exception เลย** log บรรทัด partition-assignment จริงคือ: `Adding newly assigned partitions: [left-stream-0, left-stream-1, left-stream-2, right-stream-0, right-stream-1, right-stream-2, right-stream-3, right-stream-4]` กระจายใน 5 task (`0_0`…`0_4`) — หมายความว่า task `0_3` และ `0_4` ได้รับแค่ partition ของ `right-stream` โดย **ไม่มี partition คู่จาก `left-stream` เลย** ช่องโหว่ความถูกต้องแบบเงียบ (record บน partition เหล่านั้น join กับอะไรไม่ได้เลย) ไม่ใช่ error แบบ fail-fast ที่เอกสารบอกไว้ คอร์สนี้อธิบายไม่ได้ว่า *ทำไม* การบังคับใน `CopartitionedTopicsEnforcer.enforce()` ไม่ทำงานในกรณีนี้ — bytecode แสดงว่า check นี้มีอยู่จริงและควรรันระหว่างการตั้งค่า `RepartitionTopics` — จึงควรมองนี่เป็นความขัดแย้งจริงที่ทำซ้ำได้ระหว่างพฤติกรรมที่เอกสารระบุกับการรันที่สังเกตได้จริง ไม่ใช่การรับประกันไปทางใดทางหนึ่ง **ข้อสรุปเชิงปฏิบัติ: ตรวจจำนวน partition เองก่อน join (`kafka-topics.sh --describe`) — อย่าพึ่งพาว่า Kafka Streams จะ fail fast ให้เสมอ**
</Callout>

## Exactly-once และ streams protocol

Stream processing ที่อ่าน, อัปเดต state, และเขียน มีโอกาส *ผิดพลาด* ได้ง่ายเมื่อเกิดความล้มเหลว — อาจนับซ้ำได้ Kafka Streams ทำให้เรื่องนี้เป็นแค่ config บรรทัดเดียว เมื่อตั้ง `processing.guarantee` เป็น `exactly_once_v2` Streams จะห่อทุกรอบ read-process-write (รวมถึง changelog ของ state store และ offset ของ consumer) ไว้ใน transaction เดียวของ Kafka ดังนั้นการ retry จะไม่มีทางอัปเดตซ้ำสองครั้ง — กลไก transaction เดียวกันกับที่พิสูจน์แบบ end-to-end ใน [Exactly-Once Processing](/kafka/th/delivery-and-transactions/exactly-once-processing/) เพียงแต่ขับเคลื่อนโดย library Streams แทนการเรียก `txn.sendOffsets()` เอง

## คำตอบของ JS ecosystem: ไม่มีตัวที่ maintain อยู่

Kafka Streams เป็น library เฉพาะ JVM โดยการออกแบบ (state store, การ replicate changelog, และ rebalance protocol ล้วน implement อยู่ใน Java client) npm package ที่ชื่อ `kafka-streams` ตรงตัว — การเขียน KStream/KTable ใหม่ใน JS — มีอยู่จริงแต่ถูกทิ้งร้างไปแล้วโดยพฤตินัย: `npm view kafka-streams time.modified` รายงาน **`2022-06-19`** ซึ่งเก่ากว่าสี่ปีก่อนบทนี้จะถูกเขียน โดยไม่มี flag `deprecated` แต่ก็ไม่มีความเคลื่อนไหวเช่นกัน ไม่มี Node.js เทียบเท่า Kafka Streams ที่ maintain อยู่จริง ตัวเลือกจากโค้ด Node.js คือ plain consumer (ค่าเริ่มต้นของคอร์สนี้), เรียกไปยังเซอร์วิส Streams บน JVM, หรือใช้เครื่องมือของบทถัดไป Kafka Connect เมื่องานเป็นการย้ายข้อมูลแทนการแปลง

<Callout title="สรุปในบรรทัดเดียว">
**Kafka Streams** เป็น **Java library แบบ embedded**: `KStream` คือ feed ของ event, `KTable` คือค่าล่าสุดต่อ key, และ stream-table duality เชื่อมทั้งสอง — พิสูจน์แล้วด้านบนด้วยการรัน `TopologyTestDriver` จริงที่ `count()` ปล่อย 8 record การอัปเดตจาก 2 บรรทัด input ผ่าน repartition topic ที่แทรกอัตโนมัติ `group.protocol=streams` (KIP-1071) มีจริงและเปิดใช้งานใน 4.3.1 แต่ GA **พร้อมข้อจำกัดที่ระบุชัด** (sticky assignment เท่านั้น, ไม่มี warm-up, ไม่มี static membership, ย้ายโปรโตคอลแบบ offline เท่านั้น) Co-partitioning เป็นข้อกำหนดจริงตามเอกสาร — แต่พิสูจน์แล้วด้านบนว่าการรันจริงบน 4.3.1 ที่มี partition ไม่ตรงกันไม่ fail fast ดังนั้นควรตรวจจำนวน partition เอง `processing.guarantee=exactly_once_v2` ทำให้ read-process-write ปลอดภัย ไม่มี JS เทียบเท่าที่ maintain อยู่ (`kafka-streams` บน npm: publish ล่าสุด 2022)
</Callout>

คำอ้างเรื่องความปลอดภัยในคอมเมนต์ -- "Kafka Streams will refuse to start ... and throw immediately if they don't match" -- คือสมมติฐานเดียวกับที่บทนี้พิสูจน์แล้วว่าไม่น่าเชื่อถือ [DSL developer guide](https://kafka.apache.org/43/streams/developer-guide/dsl-api/) อธิบายพฤติกรรม fail-fast นั้นจริง แต่การรันจริงบน `apache/kafka:4.3.1` ที่ join สอง topic ที่ partition ไม่ตรงกันจริง (3 กับ 5) reach `RUNNING` โดย **ไม่มี exception** และ assign task แบบเงียบ ๆ ที่ไม่มีทางเห็นทั้งสองฝั่งของ join เลย การพึ่งพา framework ให้จับกรณีนี้ไม่ได้รับการพิสูจน์ว่าปลอดภัยบนเวอร์ชันนี้ ทางแก้ไม่ใช่การเปลี่ยนโค้ด join เอง -- แต่เป็นการแก้ **กระบวนการ**: ตรวจว่า `left-orders` กับ `right-payments` มีจำนวน partition เท่ากันด้วย `kafka-topics.sh --describe` (หรือตรวจด้วย admin client ใน CI) *ก่อน* deploy เพราะการ์ดที่ runtime ที่คอมเมนต์นี้สมมติไว้พึ่งไม่ได้

</SpotTheBug>

## Mental Model

คุณค่าทั้งหมดของ Kafka Streams คือการเปลี่ยนปัญหา distributed systems ที่ยากสามข้อ -- state ในเครื่องที่รอดจาก crash, read-process-write แบบ exactly-once, และการ rebalance instance ของ worker -- ให้กลายเป็นแค่การเรียก library แทนที่จะต้องเขียนโค้ดเอง ทุกการพิสูจน์ในบทนี้แสดงจุดที่ abstraction นี้แข็งแรง (การรัน `TopologyTestDriver` จริงที่ให้ผลตรงกับที่ stream-table duality ทำนายไว้เป๊ะ, `exactly_once_v2` transaction guarantee จริงที่ใช้ร่วมกับโมดูล delivery-and-transactions) และจุดที่มันใหม่กว่าและแคบกว่าที่เห็น (ข้อจำกัดที่ระบุชัดของ KIP-1071 และ safety net ของ co-partitioning ที่ไม่ทำงานในการรันจริงที่ทำซ้ำได้หนึ่งครั้ง) ถือว่า "Kafka Streams จัดการให้" เป็นจริงสำหรับ state และ exactly-once และ verify-เอง สำหรับอะไรก็ตามที่ release notes ระบุว่าเป็น GA "พร้อม feature set ที่จำกัด"

## Trade-offs

- **TopologyTestDriver** -- พิสูจน์แล้วด้านบนว่าเป็นวิธี unit-test output ของ topology ได้แม่นยำโดยไม่ต้องมี broker แลกกับการไม่ทดสอบ partition assignment จริงหรือการบังคับ co-partitioning (ช่องว่างนั้นคือสิ่งที่หัวข้อ co-partitioning ด้านบนเจอพอดีเมื่อทดสอบกับ broker จริงแทน)
- **`group.protocol=streams` (KIP-1071)** -- task assignment แบบรวมศูนย์ฝั่ง broker และ observability ที่ดีขึ้น แลกกับข้อจำกัดที่ระบุชัดของ 4.2 (ไม่มี warm-up task, ไม่มี rack-aware placement, ไม่มี static membership, ย้ายโปรโตคอลแบบ offline เท่านั้น)
- **`exactly_once_v2`** -- guarantee จริงที่ใช้งานได้ (กลไกเดียวกับ [Exactly-Once Processing](/kafka/th/delivery-and-transactions/exactly-once-processing/)) แลกกับ overhead ของ transaction coordinator ทุก commit interval
- **Kafka Streams vs Kafka Connect vs plain consumer** -- Streams เหมาะกับ logic แบบ transform/join/aggregate จริงที่มี state ใช้ Connect (บทถัดไป) เมื่องานเป็นการย้ายข้อมูลล้วน ๆ และใช้ plain consumer เมื่อต้องการภาษาอื่นหรือควบคุมเองเต็มที่

## ความเข้าใจผิดที่พบบ่อย

- **"`count()` บน KTable ปล่อย record เดียวต่อ key พร้อมยอดรวมสุดท้าย"** พิสูจน์แล้วว่าผิดด้านบน: การรันจริงปล่อย 8 record จาก 2 บรรทัด input เพราะ changelog ของ KTable ปล่อยทุกการอัปเดตระหว่างทาง ไม่ใช่แค่ตัวสุดท้าย — consumer ของ `word-counts` เห็นประวัติการอัปเดตทั้งหมด ไม่ใช่ snapshot
- **"Kafka Streams throw ทันทีเสมอถ้าสอง topic ที่ join กันมี partition ไม่เท่ากัน"** พิสูจน์แล้วว่าผิดด้านบน (SpotTheBug) ด้วยการรันจริงที่ทำซ้ำได้บน 4.3.1 ที่ reach `RUNNING` ทั้งที่ partition ไม่ตรงกันและไม่มี exception — พฤติกรรม fail-fast ตามเอกสารไม่ทำงานในการรันนี้
- **"`group.protocol=streams` เป็น GA เต็มรูปแบบไม่มีเงื่อนไข เพราะ release notes บอกว่า GA"** คำพูดของ release announcement เองคือ "GA with a limited feature set" -- sticky assignment เท่านั้น, ไม่มี warm-up/rack-aware/static-membership, ย้ายโปรโตคอลแบบ offline เท่านั้น ยืนยันผ่าน KIP-1071 wiki
- **"มี Node.js Kafka Streams ที่ maintain อยู่จริง"** npm package `kafka-streams` มีอยู่จริงแต่ publish ล่าสุดคือปี 2022 -- ถูกทิ้งร้างไปแล้วโดยพฤตินัย ยืนยันผ่าน `npm view`
