## แนวคิดในหนึ่งประโยค

**Schema Registry** คือสัญญาที่มีเวอร์ชันและใช้ร่วมกันสำหรับรูปร่างของ record — producer register schema แล้วทุก record จะพก **schema id** เล็ก ๆ แทนที่จะพก definition เต็ม ๆ และ consumer ดึง schema นั้นด้วย id เพื่อให้ทั้งสองฝั่งเข้าใจตรงกันเสมอว่าจะอ่าน byte เหล่านั้นอย่างไร

<Callout title="ผลิตภัณฑ์ของ Confluent รันแยกต่างหาก — วิธีที่บทนี้พิสูจน์">
Schema Registry ไม่ได้เป็นส่วนหนึ่งของ `apache/kafka` — ไม่มี `kafka-schema-registry.sh` ใน image ของ broker ที่คอร์สนี้ใช้ปกติ ทุกคำกล่าวด้านล่างพิสูจน์จริงกับ container `confluentinc/cp-schema-registry` จริงที่รันขึ้นมาเฉพาะสำหรับบทนี้ ต่อกับ broker จริง แล้วปิดลง — ไม่ได้จำลอง ไม่ได้แค่ยกคำพูดมา
</Callout>

## ทำไมต้องมี schema เลย?

Kafka เองไม่สนใจว่าข้างในของ record คืออะไร — สำหรับ broker ค่าคือ byte เฉย ๆ ความเป็นอิสระนั้นกลายเป็นปัญหาทันทีที่มีทีมที่สอง consume topic ของคุณ ถ้า producer เปลี่ยนชื่อ field หรือเปลี่ยน type consumer ทุกตัวจะพังแบบเงียบ ๆ ใน production **schema** เปลี่ยนสมมติฐานที่ไม่ชัดเจนให้เป็นสัญญาที่ชัดเจน

Schema Registry เก็บ schema เหล่านั้นแยกไว้ กำกับด้วย **subject** รองรับสามรูปแบบ serialization ที่ใช้บ่อย:

- **Avro** — binary กระชับ กฎ schema evolution ครบครัน เป็นตัวเลือกที่ใช้บ่อยที่สุด และเป็นสิ่งที่การพิสูจน์ทุกอันด้านล่างใช้
- **Protobuf** — schema language ของ Google เครื่องมือข้ามภาษาที่ดี
- **JSON Schema** — มนุษย์อ่านง่าย มีประโยชน์เมื่อใช้ JSON อยู่แล้ว

```json
// An Avro schema, registered live below as the subject "orders-value"
{
  "type": "record",
  "name": "Order",
  "namespace": "com.shop.orders",
  "fields": [
    { "name": "orderId", "type": "string" },
    { "name": "amount",  "type": "double" },
    { "name": "currency", "type": "string", "default": "USD" } // default => safe to add
  ]
}
```

การ register จริง รันกับ `cp-schema-registry` ที่มีชีวิตอยู่จริง:

```text
$ curl -s -X POST http://localhost:8081/subjects/orders-value/versions \
    -H "Content-Type: application/vnd.schemaregistry.v1+json" \
    -d '{"schema": "{\"type\":\"record\",\"name\":\"Order\", ... }"}'

{"id":1,"version":1,"guid":"0a0e8319-f24e-d105-654b-020124b17692","schemaType":"AVRO","schema":"..."}
```

## Record พก id ไม่ได้พก schema

การส่ง schema เต็ม ๆ ไปกับทุก record จะสิ้นเปลือง bandwidth แทนที่จะทำแบบนั้น serializer register schema ครั้งเดียว ได้ **schema id** เป็นจำนวนเต็มกลับมา (`1` ด้านบน) แล้วเติม header เล็ก ๆ หน้าค่าของแต่ละ record: **magic byte** หนึ่งตัว (เป็น `0` เสมอ), แล้ว **schema id 4 byte** (big-endian), แล้วตามด้วย payload ที่ encode แบบ Avro consumer อ่าน id, ดึง schema ที่ตรงจาก registry (และ cache ไว้), แล้ว deserialize

พิสูจน์ด้วย hex dump จริง — encode record ด้วย `@kafkajs/confluent-schema-registry` แล้ว decode byte เดียวกันตรงตัวที่ผ่าน broker จริง:

```text
// Real run: encode a payload, dump the wire bytes, produce to a real topic, consume it back
registered/looked-up schema id: 1
encoded length: 22
hex dump: 0000000001086f2d34320000000000e0584006544842
magic byte: 0 (must be 0)
schema id (4 bytes, big-endian) from wire: 1 == registered id? true
decoded: Order { orderId: 'o-42', amount: 99.5, currency: 'THB' }
raw bytes on the topic, hex: 0000000001086f2d34320000000000e0584006544842
decoded from real topic read: Order { orderId: 'o-42', amount: 99.5, currency: 'THB' }
```

อ่าน hex ทีละ byte: `00` (magic byte, 0), `00000001` (schema id `1`, 4 byte big-endian), แล้ว `086f2d3432...` (ค่าที่ encode แบบ Avro ของ `orderId`/`amount`/`currency`) byte ที่อ่านกลับมาจาก topic จริงหลังการ produce/consume จริง **ตรงกันเป๊ะ** กับที่ encode ไป — นี่คือ wire format จริง ไม่ใช่คำอธิบายของมัน

## Compatibility mode: วิวัฒน์อย่างปลอดภัย พิสูจน์ด้วย 409 จริง

schema ไม่เคยถูกแช่แข็ง — field ถูกเพิ่มและลบไปตามธุรกิจที่เปลี่ยนแปลง compatibility mode คือกฎที่ registry บังคับใช้ *ก่อน* จะยอมรับเวอร์ชันใหม่ เพื่อไม่ให้การเปลี่ยนแปลงทำลาย reader หรือ writer ที่คุณสนใจได้เลย:

- **BACKWARD** (ค่าเริ่มต้นของ registry เอง ยืนยันสด: `GET /config` → `{"compatibilityLevel":"BACKWARD"}`) — schema ใหม่อ่านข้อมูลที่เขียนด้วย schema **เก่า** ได้ อัปเกรด **consumer ก่อน** การลบ field หรือเพิ่ม field *ที่มี* default ปลอดภัย
- **FORWARD** — schema เก่าอ่านข้อมูลที่เขียนด้วย schema **ใหม่** ได้ อัปเกรด **producer ก่อน**
- **FULL** — ทั้งสองทางเป็นจริงพร้อมกัน: ใหม่อ่านเก่า *และ* เก่าอ่านใหม่
- แต่ละแบบยังมีรูปแบบ **`_TRANSITIVE`** (`BACKWARD_TRANSITIVE` ฯลฯ) ที่ตรวจ compatibility กับ **ทุก** เวอร์ชันก่อนหน้า ไม่ใช่แค่เวอร์ชันล่าสุด

**พิสูจน์: การลบ field ได้รับการยอมรับภายใต้ BACKWARD** การ register เวอร์ชันที่สองของ `orders-value` โดยลบ `orderId` ออก (ไม่มี default) สำเร็จด้วย `200` จริง:

```text
$ curl -s -w "\nHTTP_STATUS:%{http_code}\n" -X POST http://localhost:8081/subjects/orders-value/versions \
    -d '{"schema": "{...fields without orderId...}"}'
{"id":2,"version":2,...}
HTTP_STATUS:200
```

นี่ถูกต้อง ไม่ใช่บั๊ก: BACKWARD ต้องการเพียงให้ schema *ใหม่* อ่านข้อมูล *เก่า* ได้ — reader ที่ไม่มองหา `orderId` อีกแล้วก็ไม่มีปัญหาในการอ่าน record ที่บังเอิญมี field นั้นอยู่

**พิสูจน์: การเพิ่ม field โดยไม่มี default ถูก reject — body ของ HTTP 409 จริง** การ register เวอร์ชันที่สามที่เพิ่ม `shippingAddress` (ไม่มี default) *และ* เพิ่ม `orderId` กลับมา (ไม่มี default) กับ subject เดิม:

```text
$ curl -s -w "\nHTTP_STATUS:%{http_code}\n" -X POST http://localhost:8081/subjects/orders-value/versions \
    -d '{"schema": "{...orderId, amount, currency, shippingAddress (no defaults)...}"}'

{"error_code":40901,"message":"Schema being registered is incompatible with an earlier schema for subject \"orders-value\", details: [{errorType:'READER_FIELD_MISSING_DEFAULT_VALUE', description:'The field 'orderId' at path '/fields/0' in the new schema has no default value and is missing in the old schema', additionalInfo:'orderId'}, {errorType:'READER_FIELD_MISSING_DEFAULT_VALUE', description:'The field 'shippingAddress' at path '/fields/3' in the new schema has no default value and is missing in the old schema', additionalInfo:'shippingAddress'}, {oldSchemaVersion: 2}, {oldSchema: '{...}'}, {validateFields: 'false', compatibility: 'BACKWARD'}]"}
HTTP_STATUS:409
```

error ระบุเหตุผลชัดเจนว่า *ทำไม*: `READER_FIELD_MISSING_DEFAULT_VALUE` สำหรับ field ที่มีปัญหา **ทั้งสอง** ตัว — schema reader ที่ compatible แบบ BACKWARD ต้องอ่าน record เก่าได้ และ record เก่าไม่มีทั้ง `orderId` (ถูกลบใน v2) และ `shippingAddress` (ใหม่ในความพยายามนี้) ให้ default ตกลงมาใช้เลย registry reject การ register **ก่อน** ที่จะมี byte เดียวถูก produce เลยด้วยซ้ำ — การเปลี่ยนแปลงที่ไม่ compatible ล้มเหลวเร็วตอน deploy แทนที่จะไปพังตอนตีสามใน production

<Callout title="ตรวจ compatibility แบบสด โดยไม่ต้อง register อะไร">
`POST /compatibility/subjects/<subject>/versions/latest` รัน check เดียวกับที่การ register จริงจะทำ โดยไม่สร้างเวอร์ชันใหม่ — พิสูจน์สดว่าการเพิ่ม field *ที่มี* default คืนค่า `{"is_compatible":true}` พร้อม `200` จริง คุ้มค่าที่จะต่อเข้ากับ CI ก่อน deploy ไม่ใช่พึ่งพาแค่การเรียก register เพื่อ reject schema ที่ผิดเท่านั้น
</Callout>

## Subject naming strategy

**subject** ที่ schema ถูก register ไว้ไม่จำเป็นต้องเป็น `<topic>-value` เสมอไป — [เอกสารของ serializer ของ Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/serdes-develop/index.html) กำหนดสามกลยุทธ์:

- **`TopicNameStrategy`** (ค่าเริ่มต้นของทุก client) — derive subject จากชื่อ topic: `<topic>-value` / `<topic>-key` หนึ่ง schema ต่อหนึ่ง topic นี่คือสิ่งที่การพิสูจน์ทุกอันด้านบนใช้ (`orders-value`)
- **`RecordNameStrategy`** — derive subject จาก **ชื่อแบบ fully-qualified ของ record** (namespace + name ของ Avro) ไม่ขึ้นกับ topic ทำให้ผสม record หลายชนิดบน topic เดียวได้ แต่ละอันมีประวัติ schema ของตัวเอง
- **`TopicRecordNameStrategy`** — รวมทั้งสอง: `<topic>-<ชื่อ record แบบ fully-qualified>` จัดกลุ่ม event ที่เกี่ยวข้องกันแต่รูปร่างต่างกันไว้ใน topic เดียวโดยยังจำกัด compatibility ต่อ topic

เลือก `RecordNameStrategy`/`TopicRecordNameStrategy` อย่างตั้งใจเมื่อมี event หลายชนิดใช้ topic เดียวกัน ไม่งั้นค่าเริ่มต้น `TopicNameStrategy` (หนึ่ง schema หนึ่ง topic พิสูจน์ตลอดบทนี้) คือ mental model ที่ง่ายที่สุด

## การผสาน KafkaJS: `@kafkajs/confluent-schema-registry` — ตรวจสอบว่า maintain อยู่ไหม

`npm view @kafkajs/confluent-schema-registry` ถูกตรวจสอบตรง ๆ สำหรับบทนี้: เวอร์ชันล่าสุดที่ publish คือ **`4.1.0`** publish วันที่ **2026-05-29** — เก่าไม่กี่เดือนตอนที่เขียนบทนี้ ไม่ได้ถูกทิ้งร้าง ทั้งที่ KafkaJS core เองไม่ maintain มาตั้งแต่ 2023-02-27 (มี maintainer คนละกลุ่มที่ดูแล package นี้ไว้) การพิสูจน์ encode/decode/produce/consume เต็มรูปแบบด้านบนรันกับเวอร์ชันที่ pin ไว้ตรงนี้เป๊ะ

```text
// Fragment -- depends on @kafkajs/confluent-schema-registry against a real registry;
// not collected/run by this course's harness (no schema registry on the shared broker).
// This is the real script that produced the hex dump above, run from this Mac.
import { SchemaRegistry, SchemaType } from '@kafkajs/confluent-schema-registry';
import { Kafka } from 'kafkajs';

const registry = new SchemaRegistry({ host: 'http://localhost:8081' });
const { id } = await registry.register({ type: SchemaType.AVRO, schema: JSON.stringify(orderSchema) });

const encoded = await registry.encode(id, { orderId: 'o-42', amount: 99.5, currency: 'THB' });
// encoded.toString('hex') === '0000000001086f2d34320000000000e0584006544842' (proven above)

const kafka = new Kafka({ clientId: 'sr-probe', brokers: ['localhost:9092'] });
const producer = kafka.producer();
await producer.connect();
await producer.send({ topic: 'orders', messages: [{ key: 'o-42', value: encoded }] }); // real bytes, real broker

const decoded = await registry.decode(encoded); // { orderId: 'o-42', amount: 99.5, currency: 'THB' }
```

### serdes ของ confluent client เอง

`@confluentinc/schemaregistry` (เวอร์ชัน `1.10.1` ตรวจผ่าน `npm view` — เป็นส่วนหนึ่งของ repo `confluentinc/confluent-kafka-javascript` เดียวกับ `@confluentinc/kafka-javascript`) เป็น package จริงแยกต่างหากที่มี serializer class ของตัวเอง: `AvroSerializer`/`AvroDeserializer` (ยืนยันเป็น export จริงในไฟล์ `.d.ts` ที่มากับมัน) บวก Protobuf และ JSON Schema เทียบเท่า มันคือคำตอบของ ecosystem confluent/librdkafka สำหรับปัญหาเดียวกันที่ `@kafkajs/confluent-schema-registry` แก้ให้ KafkaJS — เลือกตัวที่ตรงกับ client (`kafkajs` vs `@confluentinc/kafka-javascript`) ที่โค้ดของคุณใช้อยู่แล้ว ตามแนวทางการเลือก client ที่พูดถึงตลอดทั้งคอร์สนี้

<Callout title="สรุปในบรรทัดเดียว">
Schema Registry คือ **สัญญา** ระหว่างทีม: schema ถูกเก็บ **มีเวอร์ชัน** ตาม subject แต่ละ record พกแค่ **schema id** เล็ก ๆ (พิสูจน์แล้วด้านบนด้วย hex dump จริง: magic byte `00` + id 4 byte + payload) และ **compatibility mode** (BACKWARD พิสูจน์สดว่ายอมรับการลบ field และ reject การเพิ่ม field ที่ไม่มี default ด้วย HTTP 409 จริง) ให้ schema วิวัฒน์ได้โดยไม่ทำลาย producer หรือ consumer subject naming strategy (`TopicNameStrategy` ค่าเริ่มต้น, `RecordNameStrategy`, `TopicRecordNameStrategy`) ควบคุมว่ากี่ schema ใช้ topic เดียวกันได้ `@kafkajs/confluent-schema-registry` (publish ล่าสุด 2026-05-29) และ `@confluentinc/schemaregistry` ทั้งคู่เป็นตัวเลือกจริงและใช้งานได้ปัจจุบัน ขึ้นอยู่กับว่าใช้ Kafka client ตัวไหน
</Callout>

## Mental Model

ทุกอย่างในบทนี้คือแนวคิดเดียวที่ใช้สองครั้ง: **schema id คือ pointer ไม่ใช่สำเนา** และ **compatibility mode คือประตูกั้น ไม่ใช่คำแนะนำ** การพิสูจน์ wire-format ด้านบนแสดง pointer นั้นตรงตัวทีละ byte; การพิสูจน์ 409 แสดงประตูที่ปฏิเสธการละเมิดที่เจาะจงจริงด้วยเหตุผลที่เครื่องอ่านได้ (`READER_FIELD_MISSING_DEFAULT_VALUE`) แทนข้อความ "incompatible" ที่คลุมเครือ การคิดเรื่อง schema evolution ให้ถูกต้องคือการถามคำถามเดียวทุกครั้ง: *reader ที่ใช้ schema ใหม่จะเข้าใจ record ที่เขียนด้วย schema เก่าได้ไหม* (หรือย้อนกลับ สำหรับ FORWARD)? ทุกสิ่งที่ BACKWARD ยอมรับหรือปฏิเสธด้านบนตอบคำถามนี้อย่างตรงไปตรงมา

## Trade-offs

- **BACKWARD (ค่าเริ่มต้น)** -- พิสูจน์แล้วด้านบนว่ายอมรับการลบที่ปลอดภัยและการเพิ่มที่มี default ในขณะที่ reject การเพิ่มแบบไม่มี default ใน SpotTheBug ต้นทุนคือ producer ต้องอัปเกรด *หลัง* consumer ซึ่งตรงข้ามกับ FORWARD
- **`RecordNameStrategy`/`TopicRecordNameStrategy`** -- ให้ event หลายรูปร่างใช้ topic เดียวกันได้ แลกกับการ mapping จาก topic ไปยัง schema ที่ไม่ชัดเจนเท่าค่าเริ่มต้น
- **`@kafkajs/confluent-schema-registry` vs `@confluentinc/schemaregistry`** -- package ของ KafkaJS เล็กและง่ายกว่า (พิสูจน์แล้วด้านบนด้วยการรัน encode/decode/produce/consume สั้น ๆ) แต่วางอยู่บน core client ที่ไม่ maintain; package ของ confluent พัฒนาอยู่จริงแต่ผูกกับรูปแบบ client confluent/librdkafka
- **การเรียกเช็ค compatibility เท่านั้น (`POST /compatibility/...`)** -- จับ schema ที่ไม่ดีได้ใน CI ก่อนที่จะถูก register จริง แลกกับการเป็นการเรียกแยกที่ pipeline ต้องจำให้เรียก

## ความเข้าใจผิดที่พบบ่อย

- **"การเพิ่ม field ปลอดภัยเสมอภายใต้ BACKWARD compatibility"** พิสูจน์แล้วว่าผิดด้านบน (SpotTheBug + 409 จริง): การเพิ่ม field **ที่มี default** เท่านั้นที่ปลอดภัย; การเพิ่มแบบไม่มี default ล้มเหลวเพราะ record เก่าไม่มีอะไรให้ใส่แทน
- **"การลบ field อันตรายเสมอ"** พิสูจน์แล้วว่าผิดด้านบน: การลบ field สำเร็จด้วย `200` จริงภายใต้ BACKWARD -- schema ใหม่ (ที่เล็กลง) แค่ไม่ขอ field นั้นแล้ว จึงยังอ่าน record เก่าได้สบาย
- **"KafkaJS ไม่ maintain แล้ว แปลว่าการผสาน Schema Registry ของมันก็ไม่ maintain ด้วย"** พิสูจน์แล้วว่าผิดผ่าน `npm view`: `@kafkajs/confluent-schema-registry` publish `4.1.0` วันที่ 2026-05-29 หลัง release ล่าสุดของ KafkaJS core ไปนาน
- **"subject เป็น `<topic>-value` เสมอ"** จริงแค่ภายใต้ `TopicNameStrategy` ค่าเริ่มต้น -- `RecordNameStrategy` และ `TopicRecordNameStrategy` (strategy จริงที่มีเอกสารรองรับ) derive มันต่างกันเมื่อ event หลายชนิดใช้ topic เดียวกัน
