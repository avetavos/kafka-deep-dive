## แนวคิดในหนึ่งประโยค

**Kafka Connect** คือ framework สำเร็จรูปสำหรับย้ายข้อมูล **เข้าและออก** Kafka ด้วย configuration แทนโค้ด — ชี้ **source connector** ไปที่ฐานข้อมูลหรือไฟล์เพื่อดึงข้อมูลเข้า หรือ **sink connector** ไปที่ search index หรือ warehouse เพื่อส่งข้อมูลออก แล้ว Connect จัดการ scaling, offset, และการรีสตาร์ทให้เอง

## Source และ sink connector

งาน "Kafka" ส่วนใหญ่ไม่ใช่ business logic เลย — มันคือท่อประปา: อ่านแถวจาก Postgres เข้า topic หรือเขียน topic ออกไป Elasticsearch การเขียนท่อประปานี้เองหมายถึงต้องแก้ปัญหา offset tracking, retry, และ parallelism ใหม่ทุกครั้ง Connect ห่อสิ่งนี้เป็น **connector** ที่ใช้ซ้ำได้:

- **Source connector** — ระบบภายนอก → Kafka (ฐานข้อมูล, ไฟล์, change-data-capture stream)
- **Sink connector** — Kafka → ระบบภายนอก (ฐานข้อมูล, search index, data warehouse, object storage)

เพราะ connector คือแค่ config เท่านั้น มีอยู่แล้วเป็นร้อย ๆ ตัว แทบไม่ต้องเขียนเอง แค่ config เท่านั้น

```json
// A JDBC source connector: poll a Postgres table into a topic
{
  "name": "orders-source",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
    "connection.url": "jdbc:postgresql://db:5432/shop",
    "table.whitelist": "orders",          // which table to pull
    "mode": "incrementing",               // track new rows by a column
    "incrementing.column.name": "id",
    "topic.prefix": "pg-",                // -> topic "pg-orders"
    "tasks.max": "3"                       // up to 3 parallel tasks
  }
}
```

## Worker, task, และ converter

มีสามส่วนหลักที่ทำงาน:

- **Worker** — process JVM ที่รัน connector worker หนึ่งตัวหรือมากกว่าประกอบเป็น Connect cluster
- **Task** — หน่วยของ parallelism connector แบ่งงานออกเป็น task สูงสุด `tasks.max` ตัว ที่ worker กระจายไปทั่วคลัสเตอร์ (เช่น หนึ่ง task ต่อตาราง หรือต่อช่วง partition)
- **Converter** — แปลระหว่างรูปแบบ record ภายในของ Connect กับ byte บน topic ตรงนี้คือจุดที่ Schema Registry เข้ามาเชื่อมต่อ: `AvroConverter` serialize ด้วย schema id, `JsonConverter` เขียนเป็น JSON ล้วน

## โหมด Standalone: `ClassNotFoundException` จริงที่พิสูจน์ได้ — และวิธีแก้

image `apache/kafka:4.3.1` มากับ `connect-standalone.sh` และใน `/opt/kafka/libs/` มี `connect-file-4.3.1.jar` จริง jar นั้น *อยู่จริง* ไม่ได้แปลว่า FileStream connector *ใช้ได้เลย* ทันที — Connect ค้นหา connector ผ่าน **plugin isolation path** (`plugin.path`) เท่านั้น ซึ่ง `connect-standalone.properties` ค่าเริ่มต้นมากับค่า **ว่างเปล่า** พิสูจน์จริงตรง ๆ:

```bash
# scripts/kafka-connect/connect-standalone-demo.sh
/opt/kafka/bin/kafka-topics.sh --bootstrap-server $BOOTSTRAP --create --topic scs-connect-test --partitions 1 --replication-factor 1 2>&1 | tail -1 || true
printf 'hello line 1\nhello line 2\n' > /tmp/scs-test.txt
cat > /tmp/scs-standalone-empty.properties <<EOF
bootstrap.servers=$BOOTSTRAP
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable=true
value.converter.schemas.enable=true
offset.storage.file.filename=/tmp/scs-connect.offsets
offset.flush.interval.ms=5000
EOF
cat > /tmp/scs-file-source.properties <<EOF
name=scs-local-file-source
connector.class=FileStreamSource
tasks.max=1
file=/tmp/scs-test.txt
topic=scs-connect-test
EOF
echo "== attempt 1: no plugin.path set (default classpath scan) =="
timeout 8 /opt/kafka/bin/connect-standalone.sh /tmp/scs-standalone-empty.properties /tmp/scs-file-source.properties 2>&1 | grep -E "ERROR|Failed to find any class" | head -3
echo "== fix: mount the FileStream connector jar via plugin.path =="
mkdir -p /tmp/scs-plugins/connect-file
cp /opt/kafka/libs/connect-file-4.3.1.jar /tmp/scs-plugins/connect-file/
cat > /tmp/scs-standalone-plugin.properties <<EOF
bootstrap.servers=$BOOTSTRAP
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable=false
value.converter.schemas.enable=false
offset.storage.file.filename=/tmp/scs-connect2.offsets
offset.flush.interval.ms=5000
plugin.path=/tmp/scs-plugins
EOF
timeout 8 /opt/kafka/bin/connect-standalone.sh /tmp/scs-standalone-plugin.properties /tmp/scs-file-source.properties 2>&1 | grep -E "Finished creating connector" || true
echo "== real records that landed on the topic =="
timeout 6 /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server $BOOTSTRAP --topic scs-connect-test --from-beginning 2>&1 | grep -v "^\[" || true
```

ด้วย `plugin.path` ว่างเปล่า classpath scan ของ Connect เจอแค่สาม connector ที่ฝังอยู่ใน `connect-mirror-*.jar` ของ image เอง (connector ของ MirrorMaker เอง) — `connect-file-4.3.1.jar` ที่อยู่ใน `/opt/kafka/libs/` ไม่เคยถูกสแกนเป็น plugin source เลย การชี้ `plugin.path` ไปที่ directory ที่ mount (ในที่นี้คือ copy) jar เดียวกันเข้าไปในโฟลเดอร์บนสุดของตัวเองแก้ปัญหาได้ทันที: `Finished creating connector` และสองบรรทัดจริงจาก `/tmp/scs-test.txt` ก็เข้า topic

## โหมด Distributed: `connect-distributed.sh` + session REST API จริง

โหมด **Distributed** รัน worker หนึ่งตัวหรือมากกว่าที่ประสานงานกันเหมือน consumer group โดยเก็บ connector config, offset, และ status **ใน topic ของ Kafka เอง** แทนไฟล์ในเครื่อง — นี่คือสิ่งที่ production รัน จัดการทั้งหมดผ่าน HTTP:

```bash
# scripts/kafka-connect/connect-distributed-demo.sh
printf 'hello line 1\nhello line 2\n' > /tmp/scs-test.txt
mkdir -p /tmp/scs-plugins/connect-file
cp /opt/kafka/libs/connect-file-4.3.1.jar /tmp/scs-plugins/connect-file/
cat > /tmp/scs-distributed.properties <<EOF
bootstrap.servers=$BOOTSTRAP
group.id=scs-connect-cluster
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable=false
value.converter.schemas.enable=false
offset.storage.topic=scs-connect-offsets
offset.storage.replication.factor=1
config.storage.topic=scs-connect-configs
config.storage.replication.factor=1
status.storage.topic=scs-connect-status
status.storage.replication.factor=1
offset.flush.interval.ms=5000
plugin.path=/tmp/scs-plugins
EOF
/opt/kafka/bin/connect-distributed.sh /tmp/scs-distributed.properties > /tmp/scs-distributed.log 2>&1 &
CONNECT_PID=$!
for i in $(seq 1 25); do wget -qO- http://localhost:8083/ >/dev/null 2>&1 && break; sleep 1; done

echo "== GET /connector-plugins =="
wget -qO- http://localhost:8083/connector-plugins

echo
echo "== POST a source connector with an InsertField\$Value SMT =="
cat > /tmp/scs-smt-source.json <<'JSON'
{
  "name": "scs-orders-file-source",
  "config": {
    "connector.class": "org.apache.kafka.connect.file.FileStreamSourceConnector",
    "tasks.max": "1",
    "file": "/tmp/scs-test.txt",
    "topic": "scs-connect-smt-demo",
    "transforms": "insertOrigin",
    "transforms.insertOrigin.type": "org.apache.kafka.connect.transforms.InsertField$Value",
    "transforms.insertOrigin.static.field": "source_system",
    "transforms.insertOrigin.static.value": "file-connector-demo"
  }
}
JSON
wget -qO- --header="Content-Type: application/json" --post-file=/tmp/scs-smt-source.json http://localhost:8083/connectors
echo
sleep 4
echo "== GET status (SMT vs a schemaless String value) =="
wget -qO- http://localhost:8083/connectors/scs-orders-file-source/status

echo
echo "== DLQ: sink connector with errors.tolerance=all reading a topic with one bad record =="
/opt/kafka/bin/kafka-topics.sh --bootstrap-server $BOOTSTRAP --create --topic scs-dlq-source --partitions 1 --replication-factor 1 2>&1 | tail -1 || true
printf '{"orderId":"o-1","amount":10.5}\nthis-is-not-valid-json\n{"orderId":"o-2","amount":22.0}\n' | /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server $BOOTSTRAP --topic scs-dlq-source
cat > /tmp/scs-dlq-sink.json <<'JSON'
{
  "name": "scs-dlq-demo-sink",
  "config": {
    "connector.class": "org.apache.kafka.connect.file.FileStreamSinkConnector",
    "tasks.max": "1",
    "topics": "scs-dlq-source",
    "file": "/tmp/scs-dlq-output.txt",
    "key.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter",
    "key.converter.schemas.enable": "false",
    "value.converter.schemas.enable": "false",
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "scs-dlq-demo-dlq",
    "errors.deadletterqueue.topic.replication.factor": "1",
    "errors.log.enable": "true"
  }
}
JSON
wget -qO- --header="Content-Type: application/json" --post-file=/tmp/scs-dlq-sink.json http://localhost:8083/connectors
echo
sleep 5
echo "== good records that reached the sink file =="
cat /tmp/scs-dlq-output.txt
echo "== the bad record, in the DLQ topic =="
timeout 6 /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server $BOOTSTRAP --topic scs-dlq-demo-dlq --from-beginning 2>&1 | grep -v "^\[" || true

kill $CONNECT_PID 2>/dev/null || true
wait $CONNECT_PID 2>/dev/null || true
```

สามสิ่งจริงที่พิสูจน์ได้ใน session เดียว: (1) หลัง mount plugin path แล้ว `connector-plugins` แสดง `FileStreamSinkConnector`/`FileStreamSourceConnector` ควบคู่กับ connector ในตัว Mirror — REST API คือแหล่งความจริงว่า worker รันอะไรได้จริง; (2) `tasks.max`, SMT, และ connector config ทั้งหมด deploy ได้ด้วย `POST /connectors` ธรรมดา; (3) `GET /connectors/<name>/status` แยก **connector state** (`RUNNING`) จาก **task state** (`FAILED` ในที่นี้) — connector อาจสมบูรณ์ดีในขณะที่ task ทุกตัวตายได้

## `tasks.max` และความล้มเหลวของ SMT จริงที่ควรอ่านให้ละเอียด

`tasks.max` จำกัด parallelism ที่ connector แบ่งได้ — JDBC source ที่มี `tasks.max: 3` และ 3 ตาราง ได้หนึ่ง task ต่อตาราง; FileStream source โดยธรรมชาติมี task เดียว (ไฟล์เดียว ตัวอ่านเดียว)

**Single Message Transform (SMT)** รันแบบ inline บนแต่ละ record ไม่ต้องมีงานแยก — `transforms=insertOrigin` บวก `transforms.insertOrigin.type=...InsertField$Value` ข้างบนเพิ่ม field คงที่ให้ทุก record พิสูจน์แล้วด้านบน: มัน **ล้มเหลว** ด้วย error จริงที่เจาะจง — `DataException: Only Struct objects supported for [field insertion], found: java.lang.String` `FileStreamSourceConnector` ปล่อยค่าที่มี **schema แบบ `STRING` แนบมาด้วย** ไม่ใช่ค่าแบบ schemaless และไม่ใช่ `Struct` — และ code path ของ `InsertField` ที่รับรู้ schema (`applyWithSchema`) ต้องการ `Struct` เสมอโดยไม่มีเงื่อนไข ไม่ว่า type จริงของ schema จะเป็นอะไร นี่คือสิ่งที่มีประโยชน์จริงที่ควรรู้ก่อนใช้ `InsertField`/`ReplaceField`: มันทำงานกับ **record ที่มีโครงสร้าง (Struct-schema)** — โดยทั่วไปมาจาก JDBC source, Debezium, หรือ topic ที่แปลงด้วย Avro/JSON-Schema — ไม่ใช่กับ source แบบ plain-string อย่าง `FileStreamSourceConnector` ไม่ว่า `key.converter.schemas.enable`/`value.converter.schemas.enable` จะตั้งเป็นอย่างไร (สิ่งเหล่านั้นมีผลกับ wire format ที่เขียนลง Kafka ไม่ใช่ `SourceRecord.valueSchema()` ภายในที่ source connector สร้างขึ้นเอง)

## Dead Letter Queue (DLQ): พิสูจน์ด้วย record เสียจริงหนึ่งตัว

`errors.tolerance=all` (ค่าเริ่มต้นคือ `none`) บอก connector ให้ทำงานต่อไปแม้เจอ record เสีย แทนที่จะตายไปเลย `errors.deadletterqueue.topic.name` ให้ record เสียนั้นมีที่ไปจริง ๆ แทนที่จะหายไปเฉย ๆ พิสูจน์แล้วด้านบนด้วยสาม record บน `scs-dlq-source` (JSON ถูกต้องสองตัว หนึ่งตัวจงใจให้ผิด): task ยังคง **RUNNING** ตลอด สอง record ที่ถูกต้องไปถึง `/tmp/scs-dlq-output.txt` และ record ที่ผิดรูปแบบหนึ่งตัว — ที่ล้มเหลวตั้งแต่ตอน deserialize ด้วย `JsonConverter` ก่อนที่โค้ดของ connector เองจะเห็นด้วยซ้ำ — ไปลงที่ `scs-dlq-demo-dlq` ตรงตัวเป๊ะ ถ้าไม่มี `errors.tolerance=all` record เสียตัวเดียวกันนี้จะฆ่า task ทันทีตั้งแต่ความล้มเหลวครั้งแรก (`errors.tolerance=none` คือค่าเริ่มต้น) พา record ดี ๆ ทุกตัวที่อยู่ข้างหลังบน partition นั้นตายไปด้วย

## Distributed vs standalone

- **Standalone** — worker ตัวเดียว config ในไฟล์ท้องถิ่น offset ในไฟล์ท้องถิ่น ง่าย ไม่มี fault tolerance พิสูจน์แล้วด้านบนว่าเป็นวิธีที่ง่ายที่สุดที่จะเจอ error "connector not found" ระหว่างทดลอง เหมาะกับ demo บนแล็ปท็อปหรือการดึงไฟล์ครั้งเดียว
- **Distributed** — worker หลายตัวประสานงานกันเหมือน consumer group โดยเก็บ connector config, offset, และ status **ใน topic ของ Kafka** (`config.storage.topic`/`offset.storage.topic`/`status.storage.topic` ข้างบน) ถ้า worker ตาย task ของมัน rebalance ไปยังตัวที่รอดชีวิต นี่คือสิ่งที่ production รัน จัดการทั้งหมดผ่าน REST API ที่พิสูจน์แล้วด้านบน

## เมื่อไหร่ควรใช้ Connect แทนการเขียนโค้ด

ใช้ Connect เมื่องานคือ **ย้ายข้อมูลโดยไม่มี logic กำหนดเอง** — ดึงตารางเข้า, mirror topic ไปยัง S3, ป้อน search index จะได้ offset management, การรีสตาร์ท, และ scaling ฟรี บวก SMT สำหรับการแปลง inline เล็ก ๆ และ DLQ สำหรับ record เสีย ทั้งหมดพิสูจน์แล้วด้านบน เขียน producer หรือ consumer แทนเมื่อต้องการ **business logic** จริง: การ enrich กับเซอร์วิสอื่น, การแตกแขนงที่ไม่ตรงไปตรงมา, หรือการแปลงที่เกินกว่า converter/SMT ธรรมดาจะทำได้ ถ้าพบว่าต้องการ *แปลงและ join* stream นั่นคืองานของบทก่อนหน้า (Kafka Streams) ไม่ใช่ของ Connect

**Kafka Connect** ย้ายข้อมูลเข้าออก Kafka ด้วย **configuration** `plugin.path` เริ่มต้นของโหมด standalone ว่างเปล่า — พิสูจน์แล้วด้านบนด้วย error แบบ `ClassNotFoundException` จริงจนกว่าจะ mount connector jar เอง โหมด **Distributed** คือ production: config, offset, และ status อยู่ใน topic ของ Kafka จัดการทั้งหมดผ่าน **REST API** ที่พิสูจน์แล้วด้านบน (`/connector-plugins`, `POST /connectors`, `GET .../status`) SMT อย่าง `InsertField` ต้องการ record แบบ **Struct-schema** — พิสูจน์แล้วด้านบนว่าล้มเหลวกับ FileStream source แบบ plain-string `errors.tolerance=all` + `errors.deadletterqueue.topic.name` ทำให้ task รอดจาก record เสีย — พิสูจน์แล้วด้านบนด้วย record จริงที่ถูกส่งไปยัง DLQ topic จริงขณะที่เพื่อนบ้านที่ดียังไหลต่อไป
</Callout>

## Mental Model

ทุกอย่างที่ Kafka Connect ทำคือ worker ที่รันโค้ด Java ของ connector คุณภายใน classloader ของตัวเอง ถูกค้นพบผ่าน `plugin.path` เท่านั้น -- พิสูจน์แล้วด้านบนว่าเป็นเหตุผลตรงตัวที่ jar ที่อยู่ใน `/opt/kafka/libs/` มองไม่เห็นจนกว่าจะ mount เองอย่างชัดเจน เมื่อถูกค้นพบแล้ว connector ก็แค่ producer หรือ consumer ที่ worker จัดการให้: task คือ parallelism ของมัน converter คือการ (de)serialize ของมัน SMT คือการแก้ record แบบ inline และ DLQ คือที่ที่พฤติกรรม fail-fast ปกติของ `errors.tolerance=none` ถูก redirect ไปแทนที่จะถูกปิด ไม่มีอะไรตรงนี้ทำ business logic -- พิสูจน์แล้วด้านบนว่า `InsertField` เองปฏิเสธที่จะรันกับค่าที่ไม่มีโครงสร้าง -- ซึ่งตรงคือขอบเขตของ Connect: ย้ายและปรับรูปร่างข้อมูลเบา ๆ ส่งต่ออะไรที่มากกว่านั้นให้ Streams หรือ consumer จริง

## Trade-offs

- **Standalone** -- ทำซ้ำได้เร็วที่สุดในเครื่อง แลกกับ fault tolerance เป็นศูนย์และ (พิสูจน์แล้วด้านบน) เป็นโหมดที่เจอช่องว่างของการค้นหา plugin แบบเงียบ ๆ ได้ง่ายที่สุด
- **Distributed** -- fault tolerance ระดับ production และ REST API เต็มรูปแบบ (พิสูจน์แล้วด้านบนแบบ end-to-end) แลกกับการต้องมี topic ภายในเพิ่มอีกสามตัวและคลัสเตอร์ worker ที่กำลังรันแทนที่จะเป็น process เดียว
- **SMT** -- การแปลง inline ที่ไม่ต้อง deploy แลกกับการถูกจำกัดด้วยสิ่งที่ transform class ตัวเดียวรองรับ -- พิสูจน์แล้วด้านบนว่า `InsertField` ปฏิเสธค่าที่ไม่ใช่ Struct ตรง ๆ แทนที่จะหาทางอ้อม
- **DLQ (`errors.tolerance=all`)** -- ทำให้ task รอดจากข้อมูลเสีย แลกกับการยอมรับการสูญหาย/ข้ามข้อมูลแบบเงียบ ๆ เว้นแต่จะมีอะไรจริงจังคอยดู DLQ topic -- DLQ ที่ไม่มีใครอ่านก็เทียบเท่ากับการทิ้ง record นั้นไป

## ความเข้าใจผิดที่พบบ่อย

- **"ถ้า connector jar อยู่ใน Kafka image แล้ว Connect ใช้ได้เลย"** พิสูจน์แล้วว่าผิดด้านบน: `connect-file-4.3.1.jar` มากับ `/opt/kafka/libs/` แต่ `plugin.path` เริ่มต้น (ว่างเปล่า) ของโหมด standalone หามันไม่เจอ -- error จริงแสดงแค่สาม connector ของ Mirror ว่ามีอยู่
- **"errors.tolerance ค่าเริ่มต้นคือค่าที่ปลอดภัย"** พิสูจน์แล้วว่าผิดใน SpotTheBug: ค่าเริ่มต้นคือ `none` -- record เสียฆ่า task ทันที เว้นแต่จะตั้ง `errors.tolerance=all` เอง
- **"SMT อย่าง InsertField ทำงานกับ record อะไรก็ได้"** พิสูจน์แล้วว่าผิดด้านบนด้วย `DataException` จริง: `InsertField$Value` ต้องการค่าแบบ Struct-schema; record จาก FileStream source แบบ plain-string ล้มเหลวทุกครั้ง
- **"record ใน DLQ แปลว่า Connect แก้ปัญหาให้แล้ว"** DLQ แค่หยุดไม่ให้ record เสียทำให้ task พังหรือหายไปเงียบ ๆ -- พิสูจน์แล้วด้านบนว่ามันยังคงไปลงใน topic ที่ไม่มีการรับประกันว่าจะมีใครอ่าน -- record นั้นยังต้องการคนหรือกระบวนการปลายทางมาจัดการจริง ๆ
