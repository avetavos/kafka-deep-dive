## ไอเดียในหนึ่งประโยค

Kafka cluster ต้องมีที่เก็บ metadata ของ cluster ว่า broker ตัวไหน lead partition ไหน, มี topic อะไรบ้าง, ใครอยู่ใน ISR และใน **Kafka 4.x** งานนี้ทำโดย **KRaft** ที่เป็น controller quorum แบบ Raft ที่ built-in เข้ามา โดย **ZooKeeper ถูกถอดออกหมดแล้ว**

## ทำไมถึงเปลี่ยน

ตลอดประวัติศาสตร์ส่วนใหญ่ของ Kafka ใช้ ensemble ของ **ZooKeeper** ภายนอกเก็บ metadata ของ cluster เป็นระบบแยกต่างหากที่ต้อง deploy, secure, tune และทำความเข้าใจ แถมกลายเป็นคอขวดด้าน scalability เมื่อ cluster โตจนมี partition เยอะ **KRaft** (Kafka Raft, [KIP-500](https://cwiki.apache.org/confluence/display/KAFKA/KIP-500%3A+Replace+ZooKeeper+with+a+Self-Managed+Metadata+Quorum)) ย้ายการจัดการ metadata **เข้ามาไว้ใน** Kafka เอง ตั้งแต่ **Kafka 4.0 KRaft เป็น mode เดียว** ZooKeeper mode ถูกถอดออกทั้งหมด และ flag `--zookeeper` ของ CLI ก็หายไปแล้ว

<Callout title="ถ้าคุณเรียน Kafka มาเมื่อไม่กี่ปีก่อน">
tutorial เก่า ๆ จะ start ZooKeeper ก่อนแล้วส่ง `--zookeeper host:2181` เข้า admin command นั่น **ล้าสมัยแล้ว** ใน Kafka 4.x ไม่มี ZooKeeper ให้ start และทุก command ตอนนี้รับ `--bootstrap-server host:9092` ถ้าเห็น `--zookeeper` ในคู่มือ แสดงว่ามาก่อนยุค KRaft
</Callout>

## metadata ก็เป็น log เหมือนกัน

KRaft เอาปรัชญาของ Kafka เองมาใช้กับการประสานงาน cluster โดยเก็บ metadata เป็น **log ที่ replicate ได้** broker กลุ่มหนึ่งทำหน้าที่เป็น **controller** รวมกันเป็น **quorum** โดยมีตัวหนึ่งเป็น leader ที่ถูกเลือก ทุกการเปลี่ยน metadata ไม่ว่าจะ create topic, เลือก partition leader ใหม่ หรือ update ISR ล้วนเป็น event ที่ถูก append เข้า **metadata log** ภายใน (topic `__cluster_metadata`, partition 0) และ replicate ไปยัง controller ตัวอื่นผ่าน protocol แบบ Raft

ผลลัพธ์คือความ consistent และความเร็ว broker ตาม metadata ทันด้วยวิธีเดียวกับที่ consumer ตามข้อมูลทัน คืออ่าน log จาก offset การ failover ของ leader และการกระจาย metadata เร็วกว่าโมเดล watch สมัย ZooKeeper มาก

## พิสูจน์: describe quorum บน combined node ตัวเดียว

บน single-broker container ของคอร์สนี้เอง (`process.roles=broker,controller` — node แบบ **combined** ทำทั้งสองบทบาท) `kafka-metadata-quorum.sh` คุยกับ quorum ได้ตรง ๆ

```bash
# scripts/kraft-and-the-cluster/describe-single.sh
echo "=== describe --status ==="
/opt/kafka/bin/kafka-metadata-quorum.sh --bootstrap-server $BOOTSTRAP describe --status

echo "=== describe --replication ==="
/opt/kafka/bin/kafka-metadata-quorum.sh --bootstrap-server $BOOTSTRAP describe --replication
```

output จริงไม่ได้แก้ไข

```text

LeaderId:               1
LeaderEpoch:            1
HighWatermark:          185
MaxFollowerLag:         0
MaxFollowerLagTimeMs:   0
CurrentVoters:          [{"id": 1, "endpoints": ["CONTROLLER://localhost:29093"]}]
CurrentObservers:       []

=== describe --replication ===
NodeId	DirectoryId           	LogEndOffset	Lag	LastFetchTimestamp	LastCaughtUpTimestamp	Status	
1     	AAAAAAAAAAAAAAAAAAAAAA	187         	0  	1790636449483     	1790636449483        	Leader
```

voter ตัวเดียว ตัวมันเอง เป็น `Leader` ตรงตามที่ combined broker+controller node ตัวเดียวควรจะเป็น มันคือ quorum ที่มีสมาชิกคนเดียว `MaxFollowerLag`/`MaxFollowerLagTimeMs` เลยเป็น `0` เสมอ และ `CurrentVoters` มีแค่ตัวมันเอง

## พิสูจน์: 3-node controller quorum จริง (leader, follower, lag)

เพื่อดู quorum จริงที่มี follower มีการนำ compose 3-node **ชั่วคราว** ขึ้นมา (ทั้งสามตัว `process.roles=broker,controller` ไม่ publish host port เลย เป็น scratch stack ของคอร์สนี้เอง ปิดทันทีหลังพิสูจน์เสร็จ) แล้วรันคำสั่งเดียวกันเป๊ะ

```text

LeaderId:               2
LeaderEpoch:            1
HighWatermark:          48
MaxFollowerLag:         0
MaxFollowerLagTimeMs:   182
CurrentVoters:          [{"id": 1, "endpoints": ["CONTROLLER://broker1:9093"]}, {"id": 2, "endpoints": ["CONTROLLER://broker2:9093"]}, {"id": 3, "endpoints": ["CONTROLLER://broker3:9093"]}]
CurrentObservers:       []

# kafka-metadata-quorum.sh --bootstrap-server broker1:9092 describe --replication
NodeId	DirectoryId           	LogEndOffset	Lag	LastFetchTimestamp	LastCaughtUpTimestamp	Status
2     	AAAAAAAAAAAAAAAAAAAAAA	50          	0  	1790636489291     	1790636489291        	Leader
```

node **2** ชนะการเลือกตั้งและขึ้น `Leader` ส่วน node 1 กับ 3 ขึ้น `Follower` และ `MaxFollowerLagTimeMs: 182` เป็นตัวเลขจริงที่ไม่ใช่ศูนย์ในรอบนี้ คือเวลาตั้งแต่ follower ที่ช้าที่สุดตามทันครั้งล่าสุด บน cluster 3 node ที่ idle บนเครื่องนี้ นี่คือข้อมูลรูปแบบเดียวกับที่ `kafka-topics.sh --describe` รายงาน `Leader`/`Isr`/high-watermark ให้ partition ของ**ข้อมูล** — พิสูจน์แล้วใน [Brokers, Topics & Partitions](/kafka/en/foundations/brokers-topics-partitions/) — เพราะ metadata partition ก็ถูก replicate ด้วยกลไกแบบ Raft เดียวกันเป๊ะที่ KRaft ถูกสร้างมาเพื่อ generalize

<Callout title="command ไหนมีอยู่จริงใน Kafka 4.3.1">
เอกสารเก่า ๆ บางที่อ้างถึง tool ชื่อ `kafka-metadata.sh` เช็คตรง ๆ กับ `/opt/kafka/bin/` ของ image นี้ (ทั้งบน single node และ 3-node quorum) ไม่มี **`kafka-metadata.sh`** สิ่งที่มีจริงคือ `kafka-metadata-quorum.sh` (ใช้ข้างบน describe quorum status/replication และตั้งแต่ Kafka 4.x ยังรองรับ `add-controller`/`remove-controller`) กับ `kafka-metadata-shell.sh` (shell แบบ interactive สำหรับเดินดู tree ใน memory ของ metadata log แยกจาก raw record dump ของ `kafka-dump-log.sh` ที่ใช้ข้างล่าง) ถ้าคู่มือไหนอ้างถึง `kafka-metadata.sh` ให้เช็คกับ image ที่ติดตั้งจริงก่อนเชื่อ
</Callout>

## พิสูจน์: ข้างใน `__cluster_metadata` จริง ๆ มีอะไร

metadata log เป็น Kafka log จริง ไฟล์ segment/index แบบเดียวกับ partition อื่น ๆ (ดู [The Log Abstraction](/kafka/en/foundations/the-log-abstraction/)) แค่มี decoder พิเศษ `kafka-dump-log.sh --cluster-metadata-decoder` อ่าน raw segment `__cluster_metadata-0` แล้ว print record ที่มี type จริง ๆ

```bash
# scripts/kraft-and-the-cluster/dump-metadata-log.sh
# Redirect the full dump to a file first (this log grows for as long as the
# broker runs), then grep the first real example of each record type --
# keeps output bounded no matter how large the log has grown.
/opt/kafka/bin/kafka-dump-log.sh --cluster-metadata-decoder \
  --files /tmp/kafka-logs/__cluster_metadata-0/00000000000000000000.log --print-data-log \
  > /tmp/meta-dump.txt 2>&1

for t in LeaderChange FEATURE_LEVEL_RECORD CONFIG_RECORD REGISTER_CONTROLLER_RECORD \
         REGISTER_BROKER_RECORD BROKER_REGISTRATION_CHANGE_RECORD NO_OP_RECORD \
         TOPIC_RECORD PARTITION_RECORD; do
  grep -m 1 "$t" /tmp/meta-dump.txt
done
```

output จริง — ตัวอย่างแรกจริง ๆ ของแต่ละ record type ที่เจอใน metadata log ของคอร์สนี้เอง

## Combined vs isolated controller

node ทุกตัวข้างบนรัน `process.roles=broker,controller` — node แบบ **combined** ทำทั้งสองงาน เป็นรูปแบบเดียวที่ single-node และ 3-node proof ของบทนี้ใช้ (และเป็นรูปแบบที่ cluster เล็ก ๆ มักรันกัน) Kafka ยังรองรับ **isolated controller** ด้วย node ที่ `process.roles=controller` อย่างเดียว (ไม่เคยรับ client traffic หรือ host partition เลย) คู่กับ node แยกที่ `process.roles=broker` อย่างเดียว isolated controller แลกความง่ายในการดูแล (process เยอะขึ้นต้องรัน) กับการแยก blast-radius broker ที่โดน client load หนัก ๆ จะไม่แย่ง CPU/disk I/O ที่ controller quorum ต้องใช้เพื่อเลือก partition leader ให้ทันเวลา ซึ่งสำคัญขึ้นเรื่อย ๆ เมื่อ cluster และจำนวน partition โตขึ้น proof ของบทนี้ทั้งหมดเป็น combined mode ส่วนการเลือกระหว่างสองแบบเป็นการตัดสินใจเชิง operational sizing ที่อธิบายต่อใน [Running Kafka Locally](/kafka/en/operations-and-production/running-kafka-locally/) และโมดูล production

## `controller.quorum.voters` เทียบกับ `controller.quorum.bootstrap.servers` และ dynamic quorum (KIP-853)

node ทุกตัวข้างบนถูก start ด้วย `controller.quorum.voters=1@broker1:9093,2@broker2:9093,3@broker3:9093` แบบ **static** node ID และ address ของทุก voter ถูกตรึงไว้ตั้งแต่ start ยืนยันตรงจาก `server.properties` ของ container เอง นี่คือโมเดล KRaft ดั้งเดิม จะเปลี่ยน quorum membership ต้องแก้ config แล้ว restart ทุก node

[KIP-853](https://cwiki.apache.org/confluence/display/KAFKA/KIP-853%3A+KRaft+Controller+Membership+Changes) เพิ่มทางเลือก quorum แบบ **dynamic** ยืนยันแล้วว่ามีจริงและใช้ได้บน Kafka 4.3.1 image ของคอร์สนี้เอง

- **`controller.quorum.bootstrap.servers`** เป็น broker config key จริงที่มีเอกสารรองรับ (ยืนยันกับ official config reference ที่ cache ไว้ซึ่ง harness ของคอร์สนี้ใช้) เป็น list address สไตล์ bootstrap สำหรับ *discover* quorum ปัจจุบัน แทนที่จะเป็น voter set แบบตายตัวปิดตาย

- **`kafka-metadata-quorum.sh`** เอง output ของ `--help` บน image นี้ list ไว้ 3 subcommand ไม่ใช่ 1 คือ **`describe`**, **`add-controller`** และ **`remove-controller`** command จริงที่มีอยู่จริงสำหรับเปลี่ยน quorum membership ตอน runtime (ผ่าน connection `--bootstrap-controller`) แทนที่จะแก้ `controller.quorum.voters` แล้ว restart controller ทุกตัว

<Callout title="สิ่งที่คอร์สนี้ยืนยันแล้ว vs สิ่งที่ยังไม่ได้รันแบบ end-to-end">
บทนี้ยืนยันว่า `add-controller`/`remove-controller` **มีอยู่จริง** เป็น subcommand จริงบน Kafka 4.3.1 และ `controller.quorum.bootstrap.servers` เป็น config key จริง เป็นหลักฐานว่า tooling dynamic-quorum ของ KIP-853 ถูก ship มาแล้วใน version นี้ แต่ยังไม่ได้รัน operation เพิ่ม voter แบบไม่ต้อง restart จริงแบบ end-to-end (ต้องมี quorum ที่รันในโหมด bootstrap-servers ใหม่ตั้งแต่เริ่มอยู่แล้ว) ให้ถือว่า *การมีอยู่* ของฟีเจอร์นี้พิสูจน์แล้ว ส่วนพฤติกรรมตอน runtime จริง ๆ ควรตรวจซ้ำก่อนพึ่งพาใน production
</Callout>

## KRaft หมายความว่าอะไรสำหรับคุณในฐานะ developer

ในชีวิตประจำวัน KRaft แทบมองไม่เห็นจากฝั่ง client คุณยังเชื่อมต่อด้วย `--bootstrap-server`, produce และ consume เหมือนเดิมเป๊ะ พิสูจน์แล้วตลอดคอร์สนี้ ที่เปลี่ยนคือ mental model กับงาน operations

- **ระบบเดียว ไม่ใช่สอง** ไม่มี ZooKeeper ให้ deploy หรือ monitor broker และ controller เป็น process ของ Kafka cluster เล็ก ๆ รวมสองบทบาทไว้ด้วยกันได้เลย ตามที่ proof ทุกอันในบทนี้ใช้
- **recovery เร็วขึ้น** การ failover ของ controller และการกระจาย metadata เร็วขึ้น ทำให้ leadership ของ partition ลงตัวเร็วขึ้นหลัง broker ตาย
- **default สมัยใหม่** Kafka 4.x ยังปล่อย **KIP-848** next-generation consumer rebalance protocol เป็น GA (banner ของมันขึ้นมาเองโดยไม่ต้องเรียก ตั้งแต่ proof แรกของคอร์สนี้ — ดู [What Is Kafka](/kafka/en/foundations/what-is-kafka/)) และเสริมความแข็งแรงให้ transaction (**KIP-890**) ทั้งสองอย่างจะพูดถึงต่อในคอร์สนี้

<Callout title="สรุปหนึ่งบรรทัด">
**Kafka 4.x เป็น KRaft-only** ZooKeeper หายไปแล้ว ([KIP-500](https://cwiki.apache.org/confluence/display/KAFKA/KIP-500%3A+Replace+ZooKeeper+with+a+Self-Managed+Metadata+Quorum)) metadata ของ cluster อยู่ใน **Raft log ที่ replicate ได้** (`__cluster_metadata` พิสูจน์แล้วข้างบนด้วย `TopicRecord`/`PartitionRecord`/`ConfigRecord`/`BrokerRegistrationChangeRecord` จริง) จัดการโดย **controller quorum** พิสูจน์แล้วทั้งแบบ combined node ตัวเดียวและ 3-node quorum จริงที่มี `Leader`/`Follower` สองตัวและ `MaxFollowerLagTimeMs` ที่ไม่ใช่ศูนย์ quorum membership เป็นแบบ static โดย default (`controller.quorum.voters`) แต่ Kafka 4.3.1 ship tooling **KIP-853** dynamic-quorum จริง (`controller.quorum.bootstrap.servers`, `add-controller`/`remove-controller`) สำหรับ developer แล้ว API ฝั่ง client ไม่เปลี่ยน เชื่อมต่อด้วย **`--bootstrap-server`** และให้มอง `--zookeeper` เป็นสัญญาณว่า docs ล้าสมัย
</Callout>

นี่เป็น pattern ที่ AI assistant สร้างบ่อยมาก มาจาก training data ก่อนยุค 4.0 ตรง ๆ ที่ `--zookeeper` เป็นวิธีปกติในการรัน admin command บน Kafka 4.x ยืนยันตรงกับ broker ของคอร์สนี้เอง **ไม่มี ZooKeeper process รันอยู่เลย** (KRaft ถอดมันออกไปแล้ว พิสูจน์แล้วข้างบนว่าทุก metadata operation ในบทนี้ผ่าน `--bootstrap-server` กับ `__cluster_metadata` log แทน) รันสคริปต์นี้ตามที่เขียนไว้จะพังทันที `kafka-topics.sh` บน 4.x ไม่รับ flag `--zookeeper` เลยด้วยซ้ำ วิธีแก้คือสลับตรง ๆ เป็น `--bootstrap-server localhost:9092` (หรือ bootstrap address จริง) ซึ่งคุยกับ broker แล้ว broker ก็ resolve request นั้นกับ metadata ที่ KRaft จัดการอยู่เอง ไม่ต้องมี connection string ของ ZooKeeper และไม่ต้องมี ensemble ของ ZooKeeper ให้รันค้างไว้ที่ไหนเลย

## Mental Model

ก่อนมี KRaft คำถาม "cluster หน้าตาเป็นยังไงตอนนี้" ต้องไปถามคนละระบบ (ZooKeeper) กับระบบที่ทำงานจริง (broker) สองระบบที่ต้องตรงกันเอง และอาจเพี้ยนจากกันได้เวลามี partition หรือ bug mental model ของ KRaft ยุบทั้งหมดนี้เป็นไอเดียเดียวที่ใช้อยู่ทุกที่ในคอร์สนี้แล้ว **รูปร่างของ cluster ก็แค่ log อีกอันหนึ่ง** controller quorum คือ Kafka cluster จิ๋ว ๆ (พิสูจน์แล้วข้างบน มัน Leader, Follower, high watermark, replication lag คำศัพท์เดียวกับ data partition ทุกอย่าง) ที่มีงานเดียวคือ replicate log ของ "อะไรเปลี่ยนไปบ้างเกี่ยวกับ cluster" broker ทุกตัวคือ consumer ของ log นั้น ไม่มี source of truth ที่สองให้หลุดไม่ตรงกันอีกต่อไป เพราะไม่มีระบบที่สองอีกแล้ว

## Trade-offs

- **Combined node (broker+controller)** — process น้อยลงให้รันและ monitor (proof ทุกอันในบทนี้ใช้แบบนี้) แลกกับ load ของ client traffic ของ broker ต้องแชร์ CPU/disk กับหน้าที่ controller ของตัวมันเอง
- **Isolated controller** — แยก blast-radius ดีกว่าบน cluster ใหญ่ แลกกับต้องรันและ monitor กองทัพ node ที่ทำหน้าที่ controller อย่างเดียวแยกต่างหาก
- **`controller.quorum.voters` แบบ static** — เรียบง่าย ชัดเจน และเป็นสิ่งที่ proof ทุกอันในบทนี้ใช้ เปลี่ยน membership ต้องแก้ config แล้ว restart controller ทุกตัว
- **Dynamic quorum (KIP-853)** — พิสูจน์แล้วข้างบนว่ามีอยู่จริงเป็น tooling ใน 4.3.1 (`add-controller`/`remove-controller`, `controller.quorum.bootstrap.servers`) ผลตอบแทนคือเปลี่ยน membership ได้โดยไม่ต้อง restart ทั้ง quorum แลกกับ model bootstrap-discovery ที่ไม่ชัดเจนเท่า operational ซับซ้อนกว่าต้องทำความเข้าใจ

## ความเข้าใจผิดที่พบบ่อย

- **"Kafka 4.x ยังต้องใช้ ZooKeeper อยู่ดี เว้นแต่จะเลือกใช้ KRaft"** ผิด พิสูจน์แล้วข้างบนและ [KIP-500](https://cwiki.apache.org/confluence/display/KAFKA/KIP-500%3A+Replace+ZooKeeper+with+a+Self-Managed+Metadata+Quorum) บอกตรง ๆ ว่าตั้งแต่ Kafka 4.0 KRaft เป็น mode *เดียว* ZooKeeper mode ถูกถอดออก ไม่ใช่แค่ deprecate
- **"`kafka-metadata.sh` คือ tool สำหรับดู KRaft state"** ผิด เช็คตรง ๆ กับ `/opt/kafka/bin/` บน image 4.3.1 ของคอร์สนี้เอง script นั้นไม่มีอยู่ tool จริงคือ `kafka-metadata-quorum.sh` กับ `kafka-metadata-shell.sh`
- **"controller quorum กับ data replication (leader/ISR) เป็นกลไกคนละเรื่องกันไม่เกี่ยวข้องกัน"** ผิด พิสูจน์แล้วข้างบน `describe --replication` บน metadata partition รายงาน `Leader`/`Follower`/lag รูปแบบเดียวกับที่ `kafka-topics.sh --describe` รายงานให้ data partition เป๊ะ เพราะ controller quorum ของ KRaft *คือ* Kafka partition ที่ replicate ด้วย Raft แค่บรรทุก cluster metadata แทน record ของแอป
- **"ทุก Kafka 4.x cluster ต้องรัน isolated controller node"** ผิด proof จริงทุกอันในบทนี้ (single-node และ 3-node) ใช้ node แบบ **combined** `process.roles=broker,controller` isolated controller เป็นทางเลือกที่มีให้สำหรับ cluster ใหญ่กว่า ไม่ใช่ข้อบังคับ
