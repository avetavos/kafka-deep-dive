## Client & versions

### 1. `--zookeeper` บน CLI tool

training data ของ AI ครอบคลุม tutorial Kafka สิบปี และ tool `kafka-*.sh` ทุกตัวเคยรับ flag `--zookeeper` ZooKeeper ถูกถอดออกเต็ม ๆ ใน **Kafka 4.0** — ทุก tool ตอนนี้รับแค่ `--bootstrap-server` และ flag เก่าไม่ได้ถูกเมินเงียบ ๆ มันเป็น parse error จริง

```bash
# scripts/reading-kafka/ai-bug-catalog/01-zookeeper-flag.sh — @expect-error --zookeeper was removed in Kafka 4.0, every tool now requires --bootstrap-server
/opt/kafka/bin/kafka-topics.sh --zookeeper localhost:2181 --list
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง:**

```text
joptsimple.UnrecognizedOptionException: zookeeper is not a recognized option
	at joptsimple.OptionException.unrecognizedOption(OptionException.java:108)
	at joptsimple.OptionParser.handleLongOptionToken(OptionParser.java:510)
	at joptsimple.OptionParserState$2.handleArgument(OptionParserState.java:56)
	at joptsimple.OptionParser.parse(OptionParser.java:396)
	at org.apache.kafka.tools.TopicCommand$TopicCommandOptions.<init>(TopicCommand.java:795)
```

**วิธีแก้:**

```bash
# scripts/reading-kafka/ai-bug-catalog/01-zookeeper-flag-fixed.sh
/opt/kafka/bin/kafka-topics.sh --bootstrap-server "$BOOTSTRAP" --list
```

**จับได้ด้วย:** รัน command เดียวกันนี้กับ broker Kafka 4.x จริงตัวไหนก็ได้ — นี่คือ parse error ฝั่ง client ของ `joptsimple` ไม่ใช่อะไรที่ `tsc` หรือ properties-key check จะเห็นได้; `kafka-topics.sh --help` เองก็ไม่แสดง `--zookeeper` เลยแล้ว

### 2. `group.protocol=consumer` ที่ก็อปเข้า KafkaJS config

protocol rebalance ตัวใหม่ของ **KIP-848** (`group.protocol=consumer`) เป็นของจริง current และ GA แล้ว — แต่มันเป็น setting ของ Java client training data ของ AI ผสม Java กับ KafkaJS ตัวอย่างปนกันอย่างอิสระ และชื่อ property นี้ถูกก็อปเข้า KafkaJS consumer constructor ที่ไม่รู้จัก option นี้เลย — object literal ของ JavaScript ไม่ปฏิเสธ key ที่ไม่รู้จัก เลยไม่มีอะไรปฏิเสธมันเหมือนกัน

```typescript
// src/reading-kafka/ai-bug-catalog/02-group-protocol.ts — @expect-error 'group.protocol' is a Java-client (KIP-848) setting; KafkaJS has no such option and silently ignores it
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ clientId: 'orders', brokers: ['localhost:9092'] });
const consumer = kafka.consumer({
  groupId: 'orders-group',
  'group.protocol': 'consumer', // AI comment: "opt in to the new KIP-848 rebalance protocol"
} as any);
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง (describe group ต่อทันที):**

```text
$ kafka-consumer-groups.sh --bootstrap-server "$BOOTSTRAP" --list --type classic
quick-batch-group-2              Classic
```

consumer connect, subscribe, และ consume ได้ปกติสมบูรณ์ — และ group ยังถูกรายงานเป็น `Classic` ไม่ใช่ `Consumer` ไม่มี error ไม่มี warning ไม่มีการเปลี่ยน protocol: property นี้ถูกทิ้งไปเงียบ ๆ

**วิธีแก้:**

```typescript
// src/reading-kafka/ai-bug-catalog/02-group-protocol-fixed.ts
import { Kafka } from 'kafkajs';

// KafkaJS has no KIP-848 support at all -- do not pass a Java-only key hoping it does something.
// To actually use the new consumer rebalance protocol, switch clients:
//   import { KafkaJS } from '@confluentinc/kafka-javascript';
//   const consumer = new KafkaJS.Kafka({}).consumer({ 'group.protocol': 'consumer', groupId: 'orders-group' });
const kafka = new Kafka({ clientId: 'orders', brokers: ['localhost:9092'] });
const consumer = kafka.consumer({ groupId: 'orders-group' });
```

**จับได้ด้วย:** ไม่มีอะไรอัตโนมัติ — นี่คือเหตุผลตรง ๆ ที่ลำดับการอ่านในบทก่อนเริ่มด้วย "client ไหน version ไหน": คนรีวิวโค้ดต้องรู้ว่า KafkaJS ไม่เคย implement KIP-848 เลย จึงจะรู้ว่า key นี้ไม่ทำอะไร; `kafka-consumer-groups.sh --list --type classic` เทียบกับ `--type consumer` เป็นวิธีเดียวที่ยืนยันได้ว่า group เข้าร่วม protocol ไหนจริง ๆ

### 3. คว้า `kafkajs` มาใช้โดยไม่เช็คว่ามันยังเป็นอะไรอยู่

`kafkajs` ยังเป็น client ที่ tutorial, blog post, และ AI completion ส่วนใหญ่คว้ามาใช้เป็น default — มันก็ **ไม่มีคนดูแลตั้งแต่ 2023-02-27** ด้วย (ยืนยันผ่าน `npm view kafkajs time.modified`) มีให้ในตัวแค่ compression codec เดียว และ partition assigner เดียว

```typescript
import { Kafka, CompressionTypes } from 'kafkajs';

// AI comment: "kafkajs is the standard Node client for Kafka, actively maintained"
const kafka = new Kafka({ clientId: 'payments', brokers: ['localhost:9092'] });
```

## Producer

### 4. ลืม `idempotent: true`

idempotent producer ของ KafkaJS มี default เป็น **ปิด** — ตรงข้ามกับที่ tutorial Java client หลายอันฝึกให้ผู้อ่านคาดหวัง producer ที่สร้างโดยไม่มีมันจะ retry ภายใต้ `acks=all` โดยไม่มีการป้องกัน request ที่ retry สร้าง duplicate บน broker เลย

```typescript
// src/reading-kafka/ai-bug-catalog/04-idempotent-default.ts — @expect-error illustrates a missing safety default, not a runtime failure
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ clientId: 'payments', brokers: ['localhost:9092'] });
// AI comment: "idempotent producer for payments"
const producer = kafka.producer(); // idempotent defaults to false -- this is NOT an idempotent producer
```

**อาการ — output จริง อ่าน source ของ `node_modules/kafkajs` ตรง ๆ บน probe ของโมดูลนี้เอง:**

```text
$ grep -n "idempotent = false" node_modules/kafkajs/src/producer/index.js
  idempotent = false,
$ grep -n "acks = -1" node_modules/kafkajs/src/producer/messageProducer.js
  const sendBatch = async ({ acks = -1, timeout, compression, topicMessages = [] }) => {
```

`idempotent` มี default เป็น `false` จริง ๆ ใน package ที่ install ไว้ (`kafkajs@2.2.4`) — comment ที่อ้างว่า "idempotent producer" ข้าง ๆ การเรียก `kafka.producer()` เปล่า ๆ ผิดตรง ๆ ยืนยันจาก source ที่โค้ด import มาใช้จริง

**วิธีแก้:**

```typescript
// src/reading-kafka/ai-bug-catalog/04-idempotent-default-fixed.ts
// @run
import { Kafka } from 'kafkajs';

const brokers = [process.env.KAFKA_BROKERS ?? 'localhost:9092'];
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}ai-bug-catalog-04-idempotent`;

const kafka = new Kafka({ clientId: 'ai-bug-catalog-04', brokers });
const admin = kafka.admin();
await admin.connect();
await admin.createTopics({ topics: [{ topic, numPartitions: 1, replicationFactor: 1 }] }).catch(() => {});
await admin.disconnect();

const producer = kafka.producer({ idempotent: true, maxInFlightRequests: 1 }); // explicit, matches acks=all
await producer.connect();
const [r] = await producer.send({ topic, acks: -1, messages: [{ value: 'safe-to-retry' }] });
console.log('idempotent send OK, partition', r.partition, 'errorCode', r.errorCode);
await producer.disconnect();
process.exit(0);
```

**จับได้ด้วย:** อ่าน `node_modules/kafkajs/src/producer/index.js` ตรง ๆ (ไม่มี test ตัวไหนจับ option ที่หายไปได้ ถ้ามันไม่มีผลที่สังเกตได้บน happy-path send); `tsc --noEmit` ของ harness ยืนยันว่า fix compile ผ่าน `--run` ยืนยันว่ามัน send ได้จริง

### 5. สมมติว่า compression LZ4/Snappy/ZSTD มีให้ในตัว

comment tuning performance ที่ยกมาจากคำแนะนำของ Java client ("ใช้ `lz4` สิ มันคือ codec general-purpose ที่ดีที่สุด") ถูกเอาไปใช้ตรง ๆ กับ KafkaJS producer — ที่ไม่มี codec นั้นให้ในตัว

```typescript
// src/reading-kafka/ai-bug-catalog/05-compression.ts — @expect-error KafkaJS ships only GZIP natively; ZSTD/LZ4/Snappy throw KafkaJSNotImplemented
import { Kafka, CompressionTypes } from 'kafkajs';

const kafka = new Kafka({ clientId: 'events', brokers: ['localhost:9092'] });
const producer = kafka.producer();
await producer.connect();
// AI comment: "zstd gives the best compression ratio for JSON payloads"
await producer.send({ topic: 'events', compression: CompressionTypes.ZSTD, messages: [{ value: 'zstd-body' }] });
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง:**

```text
KafkaJSNotImplemented: ZSTD compression not implemented
```

**วิธีแก้:**

```typescript
// src/reading-kafka/ai-bug-catalog/05-compression-fixed.ts
// @run
import { Kafka, CompressionTypes } from 'kafkajs';

const brokers = [process.env.KAFKA_BROKERS ?? 'localhost:9092'];
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}ai-bug-catalog-05-compression`;

const kafka = new Kafka({ clientId: 'ai-bug-catalog-05', brokers });
const admin = kafka.admin();
await admin.connect();
await admin.createTopics({ topics: [{ topic, numPartitions: 1, replicationFactor: 1 }] }).catch(() => {});
await admin.disconnect();

const producer = kafka.producer();
await producer.connect();
// GZIP is the only codec KafkaJS registers a real implementation for.
const [r] = await producer.send({ topic, compression: CompressionTypes.GZIP, messages: [{ value: 'gzip-body' }] });
console.log('gzip send OK, partition', r.partition, 'errorCode', r.errorCode);
await producer.disconnect();
process.exit(0);
```

**จับได้ด้วย:** การรัน send จริง (type-check ผ่านเฉย ๆ — `CompressionTypes.ZSTD` เป็น enum member ที่ valid ความล้มเหลวเกิดที่ runtime อย่างเดียว); `node_modules/kafkajs/src/protocol/message/compression/index.js` สำหรับเหตุผลที่แท้จริง

### 6. Transactional producer แต่เรียก `.send()` ตรง ๆ

การสร้าง producer พร้อมตั้ง `transactionalId` เตรียมมันไว้สำหรับ transaction — แต่การเรียก `.send()` ตรง ๆ แทนการห่อ write ด้วย `.transaction()` ไม่ error มันจะ send แบบ ordinary, non-transactional, non-idempotent write ทุก write บน producer instance นั้นที่ข้าม `.transaction()` จะหลุดออกจากเรื่อง exactly-once ที่ `transactionalId` สื่อไว้ไปเงียบ ๆ

```typescript
// src/reading-kafka/ai-bug-catalog/06-txn-bypass.ts — @expect-error illustrates a silent semantic gap, not a runtime failure
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ clientId: 'payments', brokers: ['localhost:9092'] });
// AI comment: "transactional producer for the payments pipeline"
const producer = kafka.producer({ transactionalId: 'payments-tx-1' });
await producer.connect();
// AI forgot to call producer.transaction() -- this bypasses the transaction entirely
await producer.send({ topic: 'accounts', messages: [{ value: 'debit' }] });
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง:**

```text
direct send result: [{"topicName":"txn-guard-topic","partition":0,"errorCode":0,"baseOffset":"0","logAppendTime":"-1","logStartOffset":"0"}]
```

ไม่มี error เลย — `errorCode: 0` record อยู่บน topic แล้ว อยู่นอก transaction ไหนเลย ทั้งที่ producer ถูกสร้างพร้อม `transactionalId`

**วิธีแก้:**

```typescript
// src/reading-kafka/ai-bug-catalog/06-txn-bypass-fixed.ts
// @run
import { Kafka } from 'kafkajs';

const brokers = [process.env.KAFKA_BROKERS ?? 'localhost:9092'];
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}ai-bug-catalog-06-txn`;

const kafka = new Kafka({ clientId: 'ai-bug-catalog-06', brokers });
const admin = kafka.admin();
await admin.connect();
await admin.createTopics({ topics: [{ topic, numPartitions: 1, replicationFactor: 1 }] }).catch(() => {});
await admin.disconnect();

const producer = kafka.producer({ transactionalId: 'ai-bug-catalog-06-tx', idempotent: true, maxInFlightRequests: 1 });
await producer.connect();
const txn = await producer.transaction(); // every write MUST go through this object
await txn.send({ topic, messages: [{ value: 'debit-inside-transaction' }] });
await txn.commit();
console.log('write went through the transaction, not producer.send() directly');
await producer.disconnect();
process.exit(0);
```

**จับได้ด้วย:** ไม่มีอะไรอัตโนมัติ — `producer.send()` กับ `txn.send()` มีหน้าตาเหมือนกันและสำเร็จทั้งคู่ คนรีวิวต้องสังเกตว่า producer ที่สร้างด้วย `transactionalId` ไม่เคยเรียก `.transaction()` เลยแม้แต่ครั้งเดียวในไฟล์

## Consumer loop & commits

### 7. handler ที่ช้าไปบล็อก heartbeat

heartbeat ของ KafkaJS ถูกขับเคลื่อนจาก loop เดียวกับ `eachMessage` — มันยิง **หลัง** promise ของ handler resolve แล้ว ไม่ใช่บน timer แยก handler ที่ทำ HTTP call ช้า หรือ DB write ที่ไม่มีขอบเขต อาจรันเลย `session.timeout.ms` ไปได้โดยไม่ส่ง heartbeat เลย แล้ว group coordinator จะ evict member นั้นกลางการประมวลผล

```typescript
// src/reading-kafka/ai-bug-catalog/07-heartbeat-block.ts — @expect-error illustrates a timing bug that needs session.timeout.ms to actually elapse, not a compile/runtime failure
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ clientId: 'orders', brokers: ['localhost:9092'] });
const consumer = kafka.consumer({ groupId: 'orders-group', sessionTimeout: 6000 });
await consumer.run({
  eachMessage: async ({ message }) => {
    // AI comment: "call the fraud-check service before accepting the order"
    await fetch('https://fraud-check.internal/verify', { method: 'POST', body: message.value }); // no timeout -- can hang far past sessionTimeout
  },
});
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง (handler ถูกแทนด้วย sleep 15 วินาที, `sessionTimeout: 6000`):**

```text
handling offset 0 -- sleeping 15s (heartbeat only fires AFTER eachMessage returns)
handler for offset 0 finished
handling offset 1 -- sleeping 15s (heartbeat only fires AFTER eachMessage returns)
{"level":"ERROR","message":"[Connection] Response Heartbeat(key: 12, version: 3)","error":"The coordinator is not aware of this member"}
{"level":"ERROR","message":"[Runner] The coordinator is not aware of this member, re-joining the group","error":"The coordinator is not aware of this member"}
```

**วิธีแก้:**

```typescript
// src/reading-kafka/ai-bug-catalog/07-heartbeat-block-fixed.ts
// @run
import { Kafka } from 'kafkajs';

const brokers = [process.env.KAFKA_BROKERS ?? 'localhost:9092'];
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}ai-bug-catalog-07-heartbeat`;

const kafka = new Kafka({ clientId: 'ai-bug-catalog-07', brokers });
const admin = kafka.admin();
await admin.connect();
await admin.createTopics({ topics: [{ topic, numPartitions: 1, replicationFactor: 1 }] }).catch(() => {});
const producer = kafka.producer();
await producer.connect();
await producer.send({ topic, messages: [{ value: 'order-1' }] });
await producer.disconnect();

// Fix: keep eachMessage itself fast. Hand slow work to a bounded, timed-out call (or a queue), never an
```

### 10. `commitOffsets` แยก แทน `txn.sendOffsets()`

loop consume-transform-produce ที่ commit downstream write **ภายใน** transaction แต่ commit **consumer offset แยกต่างหาก** นอก transaction ทำลาย exactly-once ตั้งแต่โครงสร้าง — crash ระหว่างสอง commit นั้นจะเขียน downstream ซ้ำในการรันครั้งต่อไป เพราะ input offset ไม่เคยขยับ

```typescript

await txn.send({ topic: 'orders.enriched', messages: [{ value: enriched }] });

// BUG: this should be txn.sendOffsets({ consumerGroupId, topics: [...] }) INSIDE the same transaction.
```

### 12. retry transaction ที่ fence แล้วโดยไม่เช็ค `e.retriable`

error ของ client ฝั่ง Kafka พก boolean `retriable` จริง และ error แบบ **fencing** (producer instance ใหม่กว่าที่ถือ `transactionalId` เดียวกัน) เป็น fatal ไม่ใช่ transient — `retriable: false` logic retry ที่ไม่เช็ค field นี้จะวนไปเรื่อย ๆ บน error ที่ไม่มีวันสำเร็จ

```typescript
// src/reading-kafka/ai-bug-catalog/12-retriable-check.ts — @expect-error illustrates a naive retry loop, real output captured separately below
async function commitWithRetry(txn) {
  try {
    await txn.commit();
  } catch (e) {
    // BUG: retries unconditionally -- does not check e.retriable before deciding to retry
    return commitWithRetry(txn);
  }
}
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง (producer ตัวที่สองด้วย `transactionalId` เดียวกัน fence ตัวแรกกลาง transaction):**

```text
attempt 1: ERROR NAME=KafkaJSProtocolError retriable=false message=Producer attempted an operation with an old epoch. Either there is a newer producer with the same transactionalId, or the producer's transaction has been expired by the broker
```

`retriable: false` ยืนยันตรงจาก error object ที่ catch ได้ — retry loop ที่มองข้าม field นี้จะ commit transaction attempt ของ zombie producer ตัวนี้ตลอดไป ไม่เคยสำเร็จ ไม่เคยหยุด

**วิธีแก้:**

```typescript
// src/reading-kafka/ai-bug-catalog/12-retriable-check-fixed.ts
async function commitWithRetry(txn: Awaited<ReturnType<import('kafkajs').Producer['transaction']>>, attempt = 1): Promise<void> {
  try {
    await txn.commit();
  } catch (e: any) {
    // Fix: a fatal, non-retriable error (fencing, expired transaction) must stop the loop, not retry it.
    if (e.retriable === false) {
      console.error('FATAL, not retrying:', e.name, e.message);
      throw e;
    }
    if (attempt >= 5) throw e;
    return commitWithRetry(txn, attempt + 1);
  }
}
```

**จับได้ด้วย:** ไม่มีอะไรอัตโนมัติ — เวอร์ชัน bug และเวอร์ชัน fix compile ผ่านทั้งคู่ และ "ทำงาน" บน happy path ทั้งคู่ มีแค่ scenario fencing จริง (producer instance ที่สองด้วย `transactionalId` เดียวกัน) เท่านั้นที่เผยความต่าง ดู **[Transactions](/kafka/th/delivery-and-transactions/transactions/)** สำหรับหลักฐาน fencing เต็มรูปแบบ

### 14. เพิ่ม partition remap key — และ producer ที่รันอยู่อาจไม่รู้ตัวด้วยซ้ำ

`kafka-topics.sh --alter --partitions` (หรือ `admin.createPartitions()`) เป็น operation ทางเดียวที่มีผลจริงสองอย่างแยกกัน: `hash(key) % partitionCount` ของทุก key เปลี่ยนไป ทำลาย per-key ordering guarantee ที่โค้ดอาจพึ่งพาอยู่ — และ **producer ที่รันอยู่นานแล้วที่ cache partition count เก่าไว้แล้ว** อาจเขียนไปที่ partition set เก่าที่เล็กกว่าต่อไปได้ จนกว่าจะมีอะไรบังคับ refresh metadata

```typescript
// src/reading-kafka/ai-bug-catalog/14-partition-remap.ts — @expect-error illustrates a remap that only appears once partitions are actually added, real output captured separately below
// AI comment: "just bump partitions for more throughput, keys will still route consistently"
await admin.createPartitions({ topicPartitions: [{ topic: 'orders', count: 6 }] });
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง (3 → 6 partition บน topic ที่รันอยู่):**

```text
--- BEFORE adding partitions (3 partitions) ---
user-42 -> partition 1
user-7 -> partition 2
user-99 -> partition 2
--- SAME long-lived producer, AFTER admin.createPartitions to 6 (stale cached metadata) ---
user-42 -> partition 1
user-7 -> partition 2
user-99 -> partition 2
--- a FRESH producer, same moment, AFTER partitions already increased to 6 ---
user-42 -> partition 4
user-7 -> partition 2
user-99 -> partition 5
```

ผลจริงสองอย่างแยกกันเกิดพร้อมกัน: producer เดิมที่รันอยู่นานยังส่งไปที่ mapping *เก่า* จนกว่าจะ reconnect และพอ metadata ของ client ตัวหนึ่ง refresh แล้ว `user-42` กับ `user-99` ก็ไปลง partition ที่ต่างจากเดิมจริง ๆ — consumer ไหนที่พึ่งพา "record ของ key นี้ลง partition เดิมเสมอ ตามลำดับ" ผิดไปแล้วสำหรับทั้งสอง key นี้

**วิธีแก้:**

```typescript
// src/reading-kafka/ai-bug-catalog/14-partition-remap-fixed.ts
// Fix: there is no client-side undo for a partition-count change. Provision the final partition count
// up front for any topic whose consumers depend on per-key ordering, and if partitions genuinely must
// grow, treat it as a breaking change: drain in-flight per-key state before the change, not after.
```

**จับได้ด้วย:** ไม่มีอะไรอัตโนมัติ — ทั้ง remap และช่วง metadata ค้างเงียบทั้งคู่ การเทียบ `partition` ที่ `producer.send()` คืนมาสำหรับ key เดียวกันก่อนและหลัง บน cluster จริง เป็นวิธีเดียวที่เห็นได้ ดู **[Keys and Partitioning](/kafka/th/topics-and-partitions/keys-and-partitioning/)** สำหรับกลไก murmur2 เต็มรูปแบบ

### 15. มอง `auto.create.topics.enable` เป็นสิ่งที่สลับได้ตอน runtime

`auto.create.topics.enable` เป็น broker config แบบ **static** — อ่านครั้งเดียวตอน startup จาก `server.properties` ไม่ใช่ config ที่ `kafka-configs.sh --alter` เปลี่ยนบน broker ที่รันอยู่ได้ โค้ด (หรือ runbook) ที่สมมติว่า `--alter` แบบ dynamic มีผลทันทีนั้นผิด

```bash
# scripts/reading-kafka/ai-bug-catalog/15-auto-create-static.sh — @expect-error auto.create.topics.enable is STATIC, not dynamically alterable; real output captured separately below
/opt/kafka/bin/kafka-configs.sh --bootstrap-server "$BOOTSTRAP" --alter --entity-type brokers --entity-name 1 \
  --add-config auto.create.topics.enable=false
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง:**

```text
java.util.concurrent.ExecutionException: org.apache.kafka.common.errors.InvalidRequestException: Cannot update these configs dynamically: [auto.create.topics.enable]
Caused by: org.apache.kafka.common.errors.InvalidRequestException: Cannot update these configs dynamically: [auto.create.topics.enable]
```

**วิธีแก้:**

```properties

```

**จับได้ด้วย:** `kafka-configs.sh --describe --entity-type brokers --entity-name 1 --all` แสดง synonym เดียวเป็น `DEFAULT_CONFIG` (ไม่มี `DYNAMIC_BROKER_CONFIG` เลย) *ก่อน* ลอง alter ด้วยซ้ำ; **[Brokers, Topics & Partitions](/kafka/th/foundations/brokers-topics-partitions/)** ครอบคลุม static vs dynamic config เต็มรูปแบบ

## Connect / Streams / Schema

### 19. Connect standalone ใน "production" และ plugin ที่ไม่อยู่บน path

standalone mode ไม่มี fault tolerance เลย — worker crash เดียวเสีย connector และ task ทุกตัวที่มันรันอยู่ ไม่มีอะไร restart ให้ อีกเรื่องแยกกัน: connector class อาจอยู่จริงบน disk ที่ `/opt/kafka/libs` เป็น jar แต่ยัง load ไม่ได้ เพราะ plugin scanner ของ Connect ค้นหาแค่ class บน `plugin.path` เท่านั้น ไม่ใช่ทุกอย่างบน classpath

```properties
# config/reading-kafka/ai-bug-catalog/19-connect-standalone.properties — @expect-error FileStreamSource is not discoverable without plugin.path set, even though the jar exists on disk; real output captured separately below
# section: connect
bootstrap.servers=localhost:9092
# no plugin.path set -- AI comment: "the connector jars are already in Kafka's own libs, no extra config needed"
```

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง (`connect-file-4.3.1.jar` มีอยู่จริงที่ `/opt/kafka/libs/connect-file-4.3.1.jar`):**

```text
[ERROR] Failed to create connector for file-source.properties (org.apache.kafka.connect.cli.ConnectStandalone:86)
java.util.concurrent.ExecutionException: org.apache.kafka.connect.runtime.rest.errors.BadRequestException: Failed to find any class that implements Connector and which name matches FileStreamSource, available connectors are: PluginDesc{klass=class org.apache.kafka.connect.mirror.MirrorCheckpointConnector, ...}, PluginDesc{klass=class org.apache.kafka.connect.mirror.MirrorHeartbeatConnector, ...}, PluginDesc{klass=class org.apache.kafka.connect.mirror.MirrorSourceConnector, ...}
```

มีแค่ connector MirrorMaker สามตัวที่มาให้ในตัวเท่านั้นที่ discover ได้ — jar ของ `FileStreamSource` อยู่บน disk เป๊ะ ๆ แต่ยังมองไม่เห็นสำหรับ worker

**วิธีแก้:**

```properties
# config/reading-kafka/ai-bug-catalog/19-connect-standalone-fixed.properties
# section: connect
bootstrap.servers=localhost:9092
plugin.path=/opt/kafka/libs
# and for anything needing fault tolerance: run connect-distributed.sh instead of connect-standalone.sh --
# distributed mode persists connector/task config and offsets in Kafka topics and rebalances onto
# surviving workers; standalone mode has no such recovery at all.
```

**อาการของ fix — output จริง รันกับ broker ของโมดูลนี้เองพร้อมเพิ่ม `plugin.path=/opt/kafka/libs`:**

```text
[INFO] Added plugin 'org.apache.kafka.connect.file.FileStreamSourceConnector' (org.apache.kafka.connect.runtime.isolation.DelegatingClassLoader:199)
[INFO] Added alias 'FileStreamSource' to plugin 'org.apache.kafka.connect.file.FileStreamSourceConnector' (org.apache.kafka.connect.runtime.isolation.DelegatingClassLoader:203)
```

**จับได้ด้วย:** `GET /connector-plugins` ของ Connect REST API เองแสดงเป๊ะ ๆ ว่า worker discover อะไรได้บ้าง ก่อนจะ submit connector config เลยด้วยซ้ำ; **[Kafka Connect](/kafka/th/streams-connect-schema/kafka-connect/)** สำหรับการเทียบ standalone-vs-distributed เต็มรูปแบบ

### 20. `errors.deadletterqueue.topic.name` ถูกตั้งโดยไม่มี `errors.tolerance=all`

config ของ dead-letter-queue จะทำงานก็ต่อเมื่อ `errors.tolerance` ถูกตั้งเป็น `all` ชัดเจนเท่านั้น — default จริงที่ยืนยันแล้วคือ `none` ซึ่งภายใต้ค่านี้ record ที่ fail จะทำให้ task fail แทนที่จะ route ไปไหนเลย ไม่ว่า `errors.deadletterqueue.topic.name` จะตั้งเป็นอะไรก็ตาม กับดักที่สองแยกกัน: config ของ DLQ มีความหมายแค่กับ connector แบบ **sink** เท่านั้น — การตั้งมันบน source connector จะ validate ผ่านแต่ไม่มีผลอะไรเลยเงียบ ๆ

**อาการ — output จริง รันกับ broker ของโมดูลนี้เอง (`PUT /connector-plugins/.../config/validate` กับ Connect worker ที่รันจริง):**

`errors.tolerance` รายงานกลับมาเป็น `none` — default จริงของมัน — ยืนยันสด ๆ กับ endpoint validate config ของ worker ที่รันจริง ไม่ใช่สมมติจาก documentation

**จับได้ด้วย:** REST endpoint `/config/validate` ตัวเดียวกัน เช็คก่อน submit connector เลย; **[Kafka Connect](/kafka/th/streams-connect-schema/kafka-connect/)** สำหรับ pipeline การจัดการ error เต็มรูปแบบ รวมถึง `errors.retry.timeout.ms`

### 21. สมมติว่า KafkaJS เข้าร่วม share group ได้
