## The review walk

### `docker-compose.yml`: missing the three RF=1 env vars

Only `KAFKA_NODE_ID`, `KAFKA_PROCESS_ROLES`, listeners, and the controller quorum are set — none of `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR`, `KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR`, or `KAFKA_SHARE_COORDINATOR_STATE_TOPIC_REPLICATION_FACTOR` appear anywhere. Proven directly on a throwaway single-broker container built from this exact reduced env-var set: the broker starts and accepts topic creates just fine —

```text
$ kafka-configs.sh --bootstrap-server localhost:9092 --entity-type brokers --entity-name 1 --describe --all | grep replication.factor
offsets.topic.replication.factor=3
transaction.state.log.replication.factor=3
```

— both real Kafka defaults are **3**, not 1, the moment any `KAFKA_*` env var is set at all (confirmed by this module's own harness-broker compose notes: setting even one `KAFKA_*` env var switches the image's docker wrapper to fully env-driven config generation, which no longer falls back to the static file's single-broker-friendly defaults). A real consumer group against this exact broker:

```text
{"error":"The group coordinator is not available"}
{"error":"The group coordinator is not available"}
... (repeats until the client gives up)
KafkaJSGroupCoordinatorNotFound: Failed to find group coordinator
```

<SpotTheBug code={`KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
# no RF env vars at all`}>
"Replication factor 1 is the default anyway" is true only for a **bare** `docker run` with zero `KAFKA_*` env vars, where the image's static `server.properties` still applies — proven above, the instant this compose file sets even one `KAFKA_*` variable (here: the listeners), the real defaults (`3`) take over for the ones left unset, and a single-broker cluster can never satisfy a replication factor of 3. `__consumer_offsets` and the transaction-state log can never be created, so every consumer group and every transactional producer hangs indefinitely — not an error, a hang, which is why this is easy to miss in a quick manual test where nobody happened to use a consumer group or a transaction. The fix is setting all three RF env vars to `1` explicitly, exactly as this course's own probe compose does, with the reasoning recorded in a comment rather than assumed.
</SpotTheBug>

### `docker-compose.yml`: `KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092`

The broker's only listener advertises `localhost:9092`. Proven directly: from a **separate container** on the same Docker network as the broker (exactly the position the `connect` service in this same compose file is in) —

```text
$ docker run --rm --network kafka-reading-b_readingb busybox sh -c "nc -zv -w3 broker 9092"
broker (172.20.0.2:9092) open

$ docker run --rm --network kafka-reading-b_readingb busybox sh -c "nc -zv -w3 localhost 9092; echo EXIT=$?"
EXIT=1
```

<SpotTheBug code={`KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092`}>
`ADVERTISED_LISTENERS` is not "the address this broker listens on" — it's "the address this broker tells **every client** to reconnect to after the very first metadata fetch," and every Kafka client, including Connect's own internal producer/consumer/admin clients, always reconnects using that advertised address rather than whatever bootstrap address got it in the door. `localhost` inside the `connect` container resolves to the `connect` container itself, not the broker — proven above with the identical failure pattern (a real, non-zero connection result) that a real Connect worker hits the instant it tries any request past its first bootstrap connection. The fix is advertising the Docker Compose **service name** (`PLAINTEXT://broker:9092`, proven reachable above), which every other container on the same compose network resolves correctly via Docker's embedded DNS.
</SpotTheBug>

### Connector: `errors.deadletterqueue.topic.name` without `errors.tolerance=all`

The connector config sets a DLQ topic name and replication factor but never sets `errors.tolerance`, which really defaults to `none`. Proven directly against this module's own `connect-distributed.sh` worker (run inside the broker container) with a source topic containing one line that isn't valid JSON for the sink side of an equivalent pipeline:

```text
$ curl .../connectors/wr3-dlq-notolerance-sink2/status
"trace":"org.apache.kafka.connect.errors.ConnectException: Tolerance exceeded in error handler\n...
Caused by: org.apache.kafka.connect.errors.DataException: Converting byte[] to Kafka Connect data failed due to serialization error...

$ kafka-console-consumer --topic wr3-dlq-notolerance-dlq2 --from-beginning --timeout-ms 3000
Processed a total of 0 messages
```

<SpotTheBug code={`"errors.deadletterqueue.topic.name": "orders-dlq",
"errors.deadletterqueue.topic.replication.factor": "1"
// no errors.tolerance anywhere`}>
The DLQ configs are real, valid, and accepted by Connect's config validation — they simply do nothing while `errors.tolerance` stays at its real default of `none`, under which a failing record fails the **task itself** instead of routing anywhere. Proven above: the exact same failure that should have produced a DLQ record instead produced a dead task (`state: FAILED`) and an empty DLQ topic. The fix is `errors.tolerance=all` alongside the DLQ config — without it, "DLQ" here means "the task crashes and someone has to notice and restart it manually," which is a materially worse failure mode than either dropping the bad record or truly dead-lettering it.
</SpotTheBug>

### Connector: `InsertField$Value` on a plain-string value

The `insertOrigin` transform runs `InsertField$Value` against `FileStreamSourceConnector`'s output, which is a schemaless plain string (one line of the source file), not a `Struct`. Proven directly with the identical transform posted to this module's own Connect worker:

```text
$ curl .../connectors/wr3-orders-file-source/status
"trace":"org.apache.kafka.connect.errors.ConnectException: Tolerance exceeded in error handler\n...
Caused by: org.apache.kafka.connect.errors.DataException: Only Struct objects supported for [field insertion], found: java.lang.String
	at org.apache.kafka.connect.transforms.util.Requirements.requireStruct(Requirements.java:52)
	at org.apache.kafka.connect.transforms.InsertField.applyWithSchema(InsertField.java:175)
```

<SpotTheBug code={`"transforms": "insertOrigin",
"transforms.insertOrigin.type": "org.apache.kafka.connect.transforms.InsertField$Value",
"transforms.insertOrigin.static.field": "source_system"`}>
`InsertField` adds a named field to a **record** — it has no operation that makes sense against a bare string, and it doesn't silently no-op or wrap the value; it throws, and with `errors.tolerance` at its default (see the previous bug — the same task fails outright here too, for the same reason). Every tutorial example of `InsertField` uses a JSON- or Avro-sourced connector where the value already arrives as a `Struct`; a plain `FileStreamSource` line is exactly the wrong input shape for this SMT, no matter how the DLQ or tolerance settings are configured. The fix is either not transforming a schemaless string with a field-insertion SMT, or converting it to a structured value first (`ValueToKey`/a `Cast` or a custom converter) before `InsertField` ever runs.
</SpotTheBug>

### Streams: `left-orders` (3 partitions) joined with `right-payments` (5 partitions)

The AI's own comment claims Kafka Streams "will refuse to start and throw immediately" if the two joined topics' partition counts don't match. The [Kafka Streams DSL developer guide](https://kafka.apache.org/43/streams/developer-guide/dsl-api/) agrees in principle — *"Kafka Streams verifies whether the number of partitions for both sides of a join are the same. If they are not, a `TopologyBuilderException`... is being thrown."* This module's sibling **[Kafka Streams](/kafka/en/streams-connect-schema/kafka-streams/)** lesson tested this exact claim for real, on this exact broker version, with genuinely mismatched partition counts (3 vs 5) — and it did **not** fail fast:

```text
A real run on apache/kafka:4.3.1 joining two genuinely mismatched topics
(3 vs 5 partitions) reached RUNNING with NO exception and silently assigned
tasks that could never see both sides of the join.
```

<SpotTheBug code={`KStream<String, String> left = builder.stream("left-orders");
KStream<String, String> right = builder.stream("right-payments");
left.join(right, ...);`}>
This is the single most dangerous bug in this pipeline precisely because the AI's comment is citing real, correct documentation — the fail-fast behavior really is documented, and it just didn't fire in a real, reproducible run on this course's pinned broker version, per the sibling lesson's own proof. The fix here is not a code change to the join itself; it's a **process** fix, since the runtime guard this AI comment (and the official docs) assumed cannot be relied on for this version: verify `left-orders` and `right-payments` have identical partition counts with `kafka-topics.sh --describe` (or an admin-client check in CI) **before** deploying this topology, every time either topic's partition count could have changed.
</SpotTheBug>

### Streams: `processing.guarantee = "exactly_once"`

The AI's comment calls `"exactly_once"` "the old stable name for exactly-once" — implying it's merely deprecated but still usable. Proven directly by constructing a real `StreamsConfig` with this exact value, against the real `kafka-streams-4.3.1.jar`:

```text
$ java -cp kafka-streams-4.3.1.jar:... ExactlyOnceConfigCheck exactly_once
StreamsConfig REJECTED processing.guarantee=exactly_once -- org.apache.kafka.common.config.ConfigException: Invalid value exactly_once for configuration processing.guarantee: String must be one of: at_least_once, exactly_once_v2
```

<SpotTheBug code={`props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, "exactly_once"); // "the old stable name"`}>
This is not a deprecation warning at start-up — `StreamsConfig`'s own validator rejects the value outright, at construction time, before a single record is processed: `"exactly_once"` (the original, non-`_v2` EOS implementation) has been **removed** from the accepted value set entirely in this course's pinned `kafka-streams` version, not merely discouraged. The fix is `exactly_once_v2` (the value the real error message itself names as the only exactly-once option remaining), which shares the same transactional mechanism proven end to end in [Exactly-Once Processing](/kafka/en/delivery-and-transactions/exactly-once-processing/) and in [worked review 2](/kafka/en/reading-kafka/worked-review-2/), just applied automatically by the Streams library.
</SpotTheBug>

### Schema Registry: compatibility set to `NONE` "to avoid 409s"

The setup script sets subject-level compatibility to `NONE` before registering anything. Proven directly: with `NONE` set, a genuinely breaking schema change (a field removed, another field's type changed from `double` to `string`) is accepted outright —

```text
setting compatibility to NONE
{ status: 200, body: '{"compatibility":"NONE"}' }
registering v1: { status: 200, body: '{"id":1}' }
registering v2 (breaking): { status: 200, body: '{"id":2}' }
```

The identical breaking change against a subject left at the real default (`BACKWARD`):

```text
registering v2 (same breaking change, default compat): {
  status: 409,
  body: '{"error_code":409,"message":"Schema being registered is incompatible with an earlier schema... TYPE_MISMATCH ... reader type: STRING not compatible with writer type: DOUBLE..."}'
}
```

<SpotTheBug code={`await fetch('.../config', { method: 'PUT', body: JSON.stringify({ compatibility: 'NONE' }) });`}>
A `409` from Schema Registry is not a bug to route around — it's the **entire mechanism** that lets producers and consumers evolve independently without ever needing to deploy in lockstep: it means "a consumer running the previous schema version would break on this write," caught before the write ever reaches a topic. Proven above: `NONE` doesn't fix whatever was causing 409s, it just deletes the check that was reporting a real, structural incompatibility — the exact same breaking change silently succeeds under `NONE` and is correctly rejected with a precise, actionable error under the real default. The fix is leaving compatibility at `BACKWARD` (or the mode the org's actual deployment/rollout order needs) and fixing the schema change itself, not the check.
</SpotTheBug>

### KafkaJS consumer: decoding raw bytes instead of using the registry

`eachMessage` calls `message.value!.toString('utf8')` directly — no `registry.decode(...)` anywhere. Proven with a real encode/decode round trip and a real hex dump of the wire format `@kafkajs/confluent-schema-registry` actually produces:

```text
hex bytes: 0000000003086f2d34320000000000e05840
magic byte: 0 (must be 0)
schema id (4 bytes, big-endian) from wire: 3 == registered id? true
decoded correctly (via registry.decode): {"orderId":"o-42","amount":99.5}

raw payload as hex (header skipped): 086f2d34320000000000e05840
raw payload misinterpreted as utf8 text (garbled): "\bo-42\u0000\u0000\u0000\u0000\u0000<0xEF><0xBF><0xBD>X@"
```

<SpotTheBug code={`const decoded = raw.toString('utf8');`}>
Every record `@kafkajs/confluent-schema-registry`'s `encode()` produces is **not** raw Avro bytes — it's a 5-byte wire-format header (1 magic byte, always `0`, plus a 4-byte big-endian schema id) followed by the actual Avro-encoded payload. Proven above byte-for-byte: reading those bytes as UTF-8 text instead of feeding them through `registry.decode()` produces exactly the kind of output this hex dump shows — control characters, a stray length-prefix byte (Avro strings are length-prefixed, not null-terminated), and the tail of an 8-byte double reinterpreted as garbage text. This never throws, which is what makes it dangerous: it "works" in the sense of producing *some* string, logged and possibly persisted downstream, silently wrong the entire time. The fix is `await registry.decode(message.value)`, which strips the header, looks up the schema by the id encoded in it, and returns the real, typed object.
</SpotTheBug>

### Producer side (implied): a cached, stale schema id

Not directly visible in the generated snippet above, but the same mental model gap shows up on the producing side of a real pipeline: a schema evolves (a `currency` field added, a genuinely backward-compatible change under the real default), and a long-running producer that cached the **old** schema id at startup keeps using it. Proven directly:

```text
v1 schema id (cached before currency was added): 5
v2 schema id (current, has currency): 6
encoded with STALE v1 id -- currency field silently has nowhere to go in v1's schema

decoded by a reader using the WIRE schema id (v1): {"orderId":"o-stale-1","amount":15}
currency ("USD") present in decoded output? false
```

<SpotTheBug code={`const encoded = await registry.encode(v1Id, payload);`}>
`registry.encode(id, payload)` trusts the caller's `id` completely — it does not re-derive or verify it from the payload's own shape, and when the target schema is genuinely compatible-but-different (not wildly incompatible), no error is thrown at all: the `currency` field on the payload simply has no slot in the v1 schema the wire format claims to use, so it's silently dropped, and every downstream reader — decoding correctly, by the book, using `registry.decode()` — never sees it. (A wildly mismatched id, tested separately, does throw a real `ConfluentSchemaRegistryValidationError` during `encode()` itself — the dangerous case is specifically a stale-but-still-structurally-plausible id, not a completely wrong one.) The fix is re-registering (or re-fetching the latest id for) a schema on every deploy rather than caching an id indefinitely, or wiring cache invalidation to Schema Registry's own subject-version-changed signal if the client library exposes one.
</SpotTheBug>

`compatibility` for every subject in this pipeline stays at the real default (`BACKWARD`) — not set to `NONE` anywhere in the corrected setup — and a producer re-registers (or re-fetches) its schema id on every deploy rather than caching one indefinitely, closing the stale-id gap proven above. This corrected consumer needs a live Schema Registry to run (this module's own stack on port 48081, not the plain harness broker — the harness has neither Connect nor Schema Registry, per this module's toolchain constraint) and depends on `@kafkajs/confluent-schema-registry`, which is outside the harness probe's devDependencies (same convention [Schema Registry](/kafka/en/streams-connect-schema/schema-registry/) already uses for this package) — so this fence is a fragment, not collected or `--run`; the exact `registry.decode` call it uses was proven end to end, byte-for-byte, against this module's own live registry above.

## What the reviewer writes in the PR

> This pipeline has real, structural gaps in three different systems — Connect, Streams, and Schema Registry each have at least one, plus a compose file that will hang the whole thing the moment anyone uses a consumer group:
>
> 1. **compose is missing all 3 replication-factor env vars.** Not a cosmetic gap — a single broker literally cannot satisfy the real default of 3, and every consumer group and transaction hangs forever, silently.
> 2. **`ADVERTISED_LISTENERS` uses `localhost`.** Works for the broker talking to itself, breaks every other container the instant it reconnects using the advertised address. Use the service name.
> 3. **DLQ config with no `errors.tolerance=all`.** The DLQ settings are dead code without it — the task just dies instead.
> 4. **`InsertField$Value` on a plain string.** Wrong SMT for this connector's output shape. Real `DataException` on every record.
> 5. **Streams join without verifying partition counts.** The docs' fail-fast didn't fire in a real test on this broker version — needs an explicit check before `start()`.
> 6. **`processing.guarantee=exactly_once`.** This value is gone, not deprecated — `exactly_once_v2` is the only EOS option left.
> 7. **Schema Registry compatibility `NONE`.** This isn't fixing the 409s, it's deleting the check that was catching real breaking changes.
> 8. **Consumer skips `registry.decode`.** Silently garbled output, not an error — the scariest kind of bug in this whole review.
> 9. **A cached schema id that never gets refreshed.** Same failure mode as #8 but on the write side — a whole field vanishes with no error anywhere.
>
> None of this is exotic — every fix here is "use the option that already exists for this," not new infrastructure.

## Mental Model

This pipeline touches three systems that each make one implicit promise the generated code broke: Connect promises a task will either process a record or route it somewhere recoverable — broken by DLQ config with no `errors.tolerance`. Kafka Streams promises either a documented fail-fast or a documented guarantee — broken twice, once by trusting a fail-fast this broker version doesn't reliably provide, once by using a config value that was quietly removed rather than merely renamed. Schema Registry promises that every write a reader will ever see is decodable by that reader's own schema — broken by turning the mechanism enforcing that promise off, and separately by two different ways of just not using the wire format Schema Registry's own client library produces. None of these are hypothetical: every one produced a real, byte-for-byte or log-line-for-log-line reproducible result on this module's own live stack.

## Common Misconceptions

- **"If replication factor isn't set, it defaults to 1 on a single broker."** Proven above: the real default is `3` for the offsets and transaction-state topics the instant any `KAFKA_*` env var is set at all — the "defaults to 1" behavior only holds for a bare `docker run` with zero env vars, where the image's static config file is never overridden.
- **"`tasks.max` tells a connector how many tasks to run."** A quick, separate check on this module's own worker: `tasks.max: 3` posted to a `FileStreamSourceConnector` produced exactly **1** running task — `tasks.max` is a ceiling the connector's own `taskConfigs()` implementation is free to never approach; a single file genuinely cannot be split across parallel tasks, so this connector always returns one task regardless of the setting.
- **"A wrong schema id always throws immediately."** Proven above: a wildly mismatched id does throw during `encode()`, but a stale, structurally-compatible id does not — it silently drops whatever field doesn't fit, with zero errors anywhere in the pipeline.
