## The idea in one sentence

**Kafka Connect** is a ready-made framework for moving data **into and out of** Kafka with configuration instead of code — you point a **source connector** at a database or file to pull data in, or a **sink connector** at a search index or warehouse to push data out, and Connect handles scaling, offsets, and restarts for you.

## Source and sink connectors

A vast amount of "Kafka work" is not business logic at all — it is plumbing: read rows from Postgres into a topic, or write a topic into Elasticsearch. Writing that plumbing by hand means re-solving offset tracking, retries, and parallelism every time. Connect packages it as reusable **connectors**:

- **Source connector** — external system → Kafka (a database, a file, a change-data-capture stream).
- **Sink connector** — Kafka → external system (a database, a search index, a data warehouse, object storage).

Because a connector is just config, hundreds already exist. You rarely write one; you configure one.

```json
// A JDBC source connector: poll a Postgres table into a topic
{
  "name": "orders-source",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSourceConnector",
    "connection.url": "jdbc:postgresql://db:5432/shop",
    "table.whitelist": "orders",          // which table to pull
    "mode": "incrementing",               // track new rows by a column
    "incrementing.column.name": "id",
    "topic.prefix": "pg-",                // -> topic "pg-orders"
    "tasks.max": "3"                       // up to 3 parallel tasks
  }
}
```

## Workers, tasks, and converters

Three moving parts do the work:

- **Worker** — the JVM process that runs connectors. One or more workers form a Connect cluster.
- **Task** — the unit of parallelism. A connector splits its job into up to `tasks.max` tasks, which workers spread across the cluster (e.g. one task per table or per partition range).
- **Converter** — translates between Connect's internal record format and the bytes on the topic. This is where Schema Registry plugs in: an `AvroConverter` serializes with a schema id, a `JsonConverter` writes plain JSON.

## Standalone mode: a real, proven `ClassNotFoundException` — and the fix

The `apache/kafka:4.3.1` image ships `connect-standalone.sh` and, in `/opt/kafka/libs/`, a real `connect-file-4.3.1.jar`. That jar being *present* does not mean the FileStream connector is *usable* out of the box — Connect only discovers connectors through its **plugin isolation path** (`plugin.path`), which the default `connect-standalone.properties` ships **empty**. Proven directly:

```bash
# scripts/kafka-connect/connect-standalone-demo.sh
/opt/kafka/bin/kafka-topics.sh --bootstrap-server $BOOTSTRAP --create --topic scs-connect-test --partitions 1 --replication-factor 1 2>&1 | tail -1 || true
printf 'hello line 1\nhello line 2\n' > /tmp/scs-test.txt
cat > /tmp/scs-standalone-empty.properties <<EOF
bootstrap.servers=$BOOTSTRAP
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable=true
value.converter.schemas.enable=true
offset.storage.file.filename=/tmp/scs-connect.offsets
offset.flush.interval.ms=5000
EOF
cat > /tmp/scs-file-source.properties <<EOF
name=scs-local-file-source
connector.class=FileStreamSource
tasks.max=1
file=/tmp/scs-test.txt
topic=scs-connect-test
EOF
echo "== attempt 1: no plugin.path set (default classpath scan) =="
timeout 8 /opt/kafka/bin/connect-standalone.sh /tmp/scs-standalone-empty.properties /tmp/scs-file-source.properties 2>&1 | grep -E "ERROR|Failed to find any class" | head -3
echo "== fix: mount the FileStream connector jar via plugin.path =="
mkdir -p /tmp/scs-plugins/connect-file
cp /opt/kafka/libs/connect-file-4.3.1.jar /tmp/scs-plugins/connect-file/
cat > /tmp/scs-standalone-plugin.properties <<EOF
bootstrap.servers=$BOOTSTRAP
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable=false
value.converter.schemas.enable=false
offset.storage.file.filename=/tmp/scs-connect2.offsets
offset.flush.interval.ms=5000
plugin.path=/tmp/scs-plugins
EOF
timeout 8 /opt/kafka/bin/connect-standalone.sh /tmp/scs-standalone-plugin.properties /tmp/scs-file-source.properties 2>&1 | grep -E "Finished creating connector" || true
echo "== real records that landed on the topic =="
timeout 6 /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server $BOOTSTRAP --topic scs-connect-test --from-beginning 2>&1 | grep -v "^\[" || true
```

With an empty `plugin.path`, Connect's classpath scan finds only the three connectors baked into the image's own `connect-mirror-*.jar` (MirrorMaker's own connectors) — `connect-file-4.3.1.jar` sitting in `/opt/kafka/libs/` is never scanned as a plugin source. Pointing `plugin.path` at a directory that mounts (here: copies) that same jar into its own top-level folder fixes it immediately: `Finished creating connector`, and the two real lines from `/tmp/scs-test.txt` land on the topic.

## Distributed mode: `connect-distributed.sh` + a real REST API session

**Distributed** mode runs one or more workers that coordinate like a consumer group, storing connector configs, offsets, and status **in Kafka topics** instead of local files — this is what production runs, managed entirely over HTTP:

```bash
# scripts/kafka-connect/connect-distributed-demo.sh
printf 'hello line 1\nhello line 2\n' > /tmp/scs-test.txt
mkdir -p /tmp/scs-plugins/connect-file
cp /opt/kafka/libs/connect-file-4.3.1.jar /tmp/scs-plugins/connect-file/
cat > /tmp/scs-distributed.properties <<EOF
bootstrap.servers=$BOOTSTRAP
group.id=scs-connect-cluster
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable=false
value.converter.schemas.enable=false
offset.storage.topic=scs-connect-offsets
offset.storage.replication.factor=1
config.storage.topic=scs-connect-configs
config.storage.replication.factor=1
status.storage.topic=scs-connect-status
status.storage.replication.factor=1
offset.flush.interval.ms=5000
plugin.path=/tmp/scs-plugins
EOF
/opt/kafka/bin/connect-distributed.sh /tmp/scs-distributed.properties > /tmp/scs-distributed.log 2>&1 &
CONNECT_PID=$!
for i in $(seq 1 25); do wget -qO- http://localhost:8083/ >/dev/null 2>&1 && break; sleep 1; done

echo "== GET /connector-plugins =="
wget -qO- http://localhost:8083/connector-plugins

echo
echo "== POST a source connector with an InsertField\$Value SMT =="
cat > /tmp/scs-smt-source.json <<'JSON'
{

  "name": "scs-dlq-demo-sink",

    "tasks.max": "1",
    "topics": "scs-dlq-source",

echo
sleep 5
echo "== good records that reached the sink file =="
cat /tmp/scs-dlq-output.txt
```

Three real things proven in one session: (1) after mounting the plugin path, `connector-plugins` lists `FileStreamSinkConnector`/`FileStreamSourceConnector` alongside the built-in Mirror connectors — the REST API is the source of truth for what a worker can actually run; (2) `tasks.max`, SMTs, and connector config all deploy with a plain `POST /connectors`; (3) `GET /connectors/<name>/status` distinguishes **connector state** (`RUNNING`) from **task state** (`FAILED` here) — a connector can be healthy while every one of its tasks is dead.

## `tasks.max`, and a real SMT failure worth reading carefully

`tasks.max` caps the parallelism a connector is allowed to split into — a JDBC source with `tasks.max: 3` and 3 tables gets one task per table; a FileStream source is inherently single-task (one file, one reader).

**Single Message Transforms (SMTs)** run inline on each record, no separate job needed — `transforms=insertOrigin` plus `transforms.insertOrigin.type=...InsertField$Value` above adds a static field to every record. Proven above: it **failed** with a real, specific error — `DataException: Only Struct objects supported for [field insertion], found: java.lang.String`. `FileStreamSourceConnector` emits values with a **`STRING` schema attached**, not a schemaless value and not a `Struct` — and `InsertField`'s schema-aware code path (`applyWithSchema`) unconditionally requires a `Struct`, regardless of what the schema's actual type is. This is a genuinely useful thing to know before reaching for `InsertField`/`ReplaceField`: they work against **structured (Struct-schema'd) records** — typically from a JDBC source, Debezium, or an Avro/JSON-Schema-converted topic — not against a plain-string source like `FileStreamSourceConnector`, no matter how `key.converter.schemas.enable`/`value.converter.schemas.enable` are set (those affect the wire format written to Kafka, not the internal `SourceRecord.valueSchema()` a source connector itself constructs).

## Dead Letter Queue (DLQ): proven with one real bad record

`errors.tolerance=all` (default `none`) tells a connector to keep running past a bad record instead of dying; `errors.deadletterqueue.topic.name` gives that bad record somewhere real to go instead of vanishing. Proven above with three records on `scs-dlq-source` (two valid JSON, one deliberately invalid): the sink task stayed **RUNNING** the whole time, the two good records reached `/tmp/scs-dlq-output.txt`, and the one malformed record — which fails `JsonConverter` deserialization before the connector's own code ever sees it — landed verbatim in `scs-dlq-demo-dlq`. Without `errors.tolerance=all`, the same bad record would have killed the task on the first failure (`errors.tolerance=none` is the default), taking every good record behind it in that partition down with it.

## Distributed vs standalone

- **Standalone** — a single worker, config in a local file, offsets in a local file. Simple, no fault tolerance, proven above as the easiest way to hit the "connector not found" error while iterating. Good for a laptop demo or a one-off file ingest.
- **Distributed** — multiple workers coordinating like a consumer group, with connector configs, offsets, and status stored **in Kafka topics** (`config.storage.topic`/`offset.storage.topic`/`status.storage.topic` above). If a worker dies, its tasks rebalance onto the survivors. This is what you run in production, managed entirely over the REST API proven above.

## When to use Connect instead of code

Reach for Connect when the job is **moving data with no custom logic** — ingest a table, mirror a topic to S3, feed a search index. You get offset management, restarts, and scaling for free, plus SMTs for small inline transforms and a DLQ for bad records, all proven above. Write a producer or consumer instead when you need real **business logic**: enrichment against another service, non-trivial branching, or transformations that outgrow a simple converter/SMT. If you find yourself wanting to *transform and join* streams, that is the previous lesson's job (Kafka Streams), not Connect's.

The trailing comment's claim is backwards. `errors.tolerance` **defaults to `none`**, not a lenient mode -- proven directly above with real behavior: without an explicit `errors.tolerance=all` (and ideally `errors.deadletterqueue.topic.name` so the bad record goes *somewhere*), the very first record this connector cannot convert or transform kills the task outright, and every record behind it on that partition stops flowing until someone notices and restarts it. The fix is to add `"errors.tolerance": "all"` and `"errors.deadletterqueue.topic.name": "orders-enricher-sink-dlq"` (plus `errors.deadletterqueue.topic.replication.factor` in production) explicitly -- proven above as the combination that keeps a task alive and gives bad records a real destination instead of silently assuming a default that does not exist.

## Mental Model

Everything Kafka Connect does is a worker running your connector's Java code inside its own classloader, discovered only through `plugin.path` -- proven above as the literal reason a jar sitting in `/opt/kafka/libs/` was invisible until mounted explicitly. Once discovered, a connector is just a producer or consumer the worker manages for you: tasks are its parallelism, converters are its (de)serialization, SMTs are inline record edits, and the DLQ is where the normal `errors.tolerance=none` fail-fast behavior gets redirected instead of disabled. Nothing here does business logic -- proven above that `InsertField` itself refuses to run against an unstructured value -- which is exactly Connect's boundary: move and lightly reshape data, hand off anything more to Streams or a real consumer.

## Trade-offs

- **Standalone** -- fastest to iterate with locally, at the cost of zero fault tolerance and (proven above) the easiest mode to hit a silent plugin-discovery gap in.
- **Distributed** -- production-grade fault tolerance and a full REST API (proven above end to end), at the cost of needing three extra internal topics and a running cluster of workers instead of one process.
- **SMTs** -- zero-deploy inline transforms, at the cost of being limited to what a single transform class supports -- proven above that `InsertField` simply refuses non-Struct values rather than working around it.
- **DLQ (`errors.tolerance=all`)** -- keeps a task alive past bad data, at the cost of silently accepting data loss/skips unless something actually watches the DLQ topic -- a DLQ that nobody reads is equivalent to dropping the record.

## Common Misconceptions

- **"If a connector jar is in the Kafka image, Connect can use it."** Proven false above: `connect-file-4.3.1.jar` ships in `/opt/kafka/libs/` yet standalone mode's default (empty) `plugin.path` cannot find it -- the real error lists only the three Mirror connectors as available.
- **"errors.tolerance defaults to something safe."** Proven false in the SpotTheBug: the default is `none` -- a bad record kills the task, full stop, unless `errors.tolerance=all` is set explicitly.
- **"SMTs like InsertField work on any record."** Proven false above with a real `DataException`: `InsertField$Value` requires a Struct-schema'd value; a plain-string FileStream source record fails it every time.
- **"A DLQ record means Connect fixed the problem."** A DLQ only stops the bad record from crashing the task or getting silently dropped -- proven above that it still lands in a topic nobody is guaranteed to be reading; the record still needs a human or a downstream process to actually handle it.
