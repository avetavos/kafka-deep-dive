## The idea in one sentence

**Kafka Streams** is a Java library — not a separate cluster — that you embed in your own application to transform, aggregate, and join Kafka topics as continuous streams, with state and exactly-once guarantees handled for you.

## KStream, KTable, and the duality

Kafka Streams gives you two views of a topic:

- **`KStream`** — an unbounded sequence of independent **events**. Every record is a new fact ("user clicked"). Nothing is overwritten.
- **`KTable`** — a **changelog** interpreted as the latest value **per key**. Each record updates the row for its key, like `UPSERT`s into a table.

This is the **stream-table duality**: a table is the snapshot you get by replaying a stream of updates, and a stream is the sequence of changes you get by watching a table. The same topic can be read either way depending on what you need — a running feed of events, or the current state per key.

## Stateless vs stateful operations

Operations split into two families:

- **Stateless** — each record is handled on its own: `map`, `filter`, `flatMap`, `branch`. No memory of past records is needed.
- **Stateful** — the result depends on records seen so far: `aggregate`, `count`, `reduce`, `join`, and **windowing** (grouping records into time buckets). These need somewhere to keep the running result.

That "somewhere" is a **state store** — a local key-value store (RocksDB by default) living inside your app instance. To survive a crash, every state store is backed by a **changelog topic** in Kafka: each update is also written to the changelog, so if the instance restarts elsewhere, Streams rebuilds the store by replaying it. Your local state is durable without you managing a database.

## A word-count topology, proven with a real `TopologyTestDriver` run

Here is the classic example — count how often each word appears across an input topic. This is not a hypothetical: it was compiled with plain `javac` and **run** with `java` against real `kafka-streams-4.3.1.jar` / `kafka-streams-test-utils-4.3.1.jar` (plus `rocksdbjni`, `jackson-databind`, and friends) fetched directly from Maven Central by URL — no gradle, no maven, per this course's toolchain constraint.

```java
// src/main/java/streams/WordCountTopologyTest.java
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.StreamsConfig;
import org.apache.kafka.streams.TestInputTopic;
import org.apache.kafka.streams.TestOutputTopic;
import org.apache.kafka.streams.Topology;
import org.apache.kafka.streams.TopologyTestDriver;
import org.apache.kafka.streams.kstream.KStream;
import org.apache.kafka.streams.kstream.KTable;
import org.apache.kafka.streams.test.TestRecord;

import java.util.Arrays;
import java.util.List;
import java.util.Properties;

public class WordCountTopologyTest {
    public static void main(String[] args) {
        StreamsBuilder builder = new StreamsBuilder();

        // Read the input topic as a stream of (key, line) events
        KStream<String, String> lines = builder.stream("text-input");

        KTable<String, Long> counts = lines
            .flatMapValues(line -> Arrays.asList(line.toLowerCase().split("\\W+"))) // split into words
            .groupBy((key, word) -> word)     // re-key by the word itself
            .count();                         // stateful: running total per word -> a KTable

        counts.toStream().to("word-counts");  // write the changelog of counts out

        Topology topology = builder.build();
        System.out.println(topology.describe());

        Properties props = new Properties();
        props.put(StreamsConfig.APPLICATION_ID_CONFIG, "wordcount-test");
        props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "dummy:9092");
        props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);
        props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);

        // TopologyTestDriver: an in-memory harness -- no broker needed to unit-test a topology
        try (TopologyTestDriver driver = new TopologyTestDriver(topology, props)) {
            TestInputTopic<String, String> input = driver.createInputTopic(
                "text-input", Serdes.String().serializer(), Serdes.String().serializer());
            TestOutputTopic<String, Long> output = driver.createOutputTopic(
                "word-counts", Serdes.String().deserializer(), Serdes.Long().deserializer());

            input.pipeInput(null, "the quick brown fox");
            input.pipeInput(null, "the lazy fox sleeps");

            List<TestRecord<String, Long>> results = output.readRecordsToList();
            for (TestRecord<String, Long> r : results) {
                System.out.println("word-counts: " + r.key() + " = " + r.value());
            }
            System.out.println("TOTAL RECORDS: " + results.size());
        }
    }
}
```

Two real things this proves: (1) `count()` compiled into **two sub-topologies** joined by an internal **repartition topic** (`...-repartition`) — `groupBy` re-keys by word, which is not guaranteed to land on the same partition as the input, so Streams inserts a repartition step automatically; (2) `the` and `fox` each emit **twice** (once per input line that updates their running count), because a `KTable`'s changelog emits every **update**, not just final totals — 8 output records for 2 input lines, not the "final" 6 distinct words, exactly the stream-table duality from the section above made concrete.

<Callout title="TopologyTestDriver needs a Struct-free default serde, or it throws immediately">
The first attempt at this run, without `DEFAULT_KEY_SERDE_CLASS_CONFIG`/`DEFAULT_VALUE_SERDE_CLASS_CONFIG` set, failed immediately with a real `org.apache.kafka.common.config.ConfigException: Please specify a key serde or set one through StreamsConfig#DEFAULT_KEY_SERDE_CLASS_CONFIG` — `count()`'s internal state store needs a serde and none is inferred automatically just from `Serdes.String()` passed to `createInputTopic`. Setting both `DEFAULT_KEY_SERDE_CLASS_CONFIG`/`DEFAULT_VALUE_SERDE_CLASS_CONFIG` in `props` fixed it.
</Callout>

## KIP-1071: the new `group.protocol=streams` — GA with a limited feature set, verified

```java
// Turn on end-to-end exactly-once for the whole topology
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, "exactly_once_v2");

// The new broker-side rebalance protocol for Streams groups (KIP-1071)
props.put(StreamsConfig.GROUP_PROTOCOL_CONFIG, "streams");
```

Confirmed live on this broker: `kafka-configs.sh --entity-type brokers --entity-default --describe --all` prints `group.coordinator.rebalance.protocols = [classic, consumer, share, streams]` — `streams` is a real, enabled rebalance protocol on `apache/kafka:4.3.1`, matching `kafka-features.sh describe`'s `Feature: streams.version  FinalizedVersionLevel: 1`.

<Callout title="'Limited feature set' — what it actually means, quoted">
[The Kafka 4.2.0 release announcement](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/) states plainly: **"Kafka Streams brings the server-side rebalance protocol to GA with a limited feature set."** [KIP-1071](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1071:+Streams+Rebalance+Protocol) and its GA-scoped follow-up coverage spell out the limits concretely: the protocol ships with **sticky assignment only** — no warm-up tasks and no rack-aware placement yet; **no static membership**; **no on-the-fly topology changes** while the group is running; and migrating a group between the classic and new streams protocols is **offline-only** — every instance must stop and the group must go empty before restarting with the new protocol. Setting `group.protocol=streams` in production today means accepting those specific gaps, not "GA" in the unqualified sense the word usually carries.
</Callout>

## Co-partitioning: what the docs promise, and what one real run actually showed

A **stream-stream join** (`KStream.join(...)`) requires its two input topics to be **co-partitioned** — same partition count, same partitioning strategy — so that partition *N* of the left topic only ever needs to join partition *N* of the right topic. The [Kafka Streams DSL developer guide](https://kafka.apache.org/43/streams/developer-guide/dsl-api/) is explicit: *"The input topics of the join (left side and right side) must have the same number of partitions... During the partition assignment step, i.e. at runtime, Kafka Streams verifies whether the number of partitions for both sides of a join are the same. If they are not, a `TopologyBuilderException` (runtime exception) is being thrown."* The exception class in the current 4.3.1 jar is `org.apache.kafka.streams.errors.TopologyException`, not the older `TopologyBuilderException` name the doc still uses — confirmed by decompiling `CopartitionedTopicsEnforcer.class` from the real `kafka-streams-4.3.1.jar`, which contains the literal format string `"%sTopics not co-partitioned: [%s]"` thrown as a `TopologyException`.

<Callout title="Honest result: this did NOT throw in one real, reproducible run on 4.3.1">
Two real topics were created on a live broker — `left-stream` (3 partitions) and `right-stream` (5 partitions) — and joined with a real `KStream.join(...)` (windowed, `StreamJoined.with(...)`) inside an actual `KafkaStreams` app (not `TopologyTestDriver`) pointed at that broker. The app reached `RUNNING` with **no exception thrown**. The real partition-assignment log line was: `Adding newly assigned partitions: [left-stream-0, left-stream-1, left-stream-2, right-stream-0, right-stream-1, right-stream-2, right-stream-3, right-stream-4]` across 5 tasks (`0_0`…`0_4`) — meaning tasks `0_3` and `0_4` were assigned only a `right-stream` partition with **no corresponding `left-stream` partition at all**, a silent correctness gap (records on those partitions can never join anything), not the documented fail-fast error. This course cannot explain *why* the enforcement in `CopartitionedTopicsEnforcer.enforce()` did not fire here — the bytecode shows the check exists and should run during `RepartitionTopics` setup — so treat this as a genuine, reproducible discrepancy between the documented behavior and this observed run, not a guarantee either way. **Practical takeaway: verify partition counts yourself (`kafka-topics.sh --describe`) before joining two topics — do not rely on Kafka Streams to always fail fast for you.**
</Callout>

## Exactly-once and the streams protocol

Stream processing that reads, updates state, and writes is easy to get *wrong* on failure — you can double-count. Kafka Streams makes this a one-line setting. With `processing.guarantee` set to `exactly_once_v2`, Streams wraps each read-process-write cycle (including the state-store changelog and consumer offsets) in a single Kafka transaction, so a retry never applies an update twice — the same transactional mechanism proven end to end in [Exactly-Once Processing](/kafka/en/delivery-and-transactions/exactly-once-processing/), just driven by the Streams library instead of hand-written `txn.sendOffsets()` calls.

## The JS ecosystem's answer: there isn't a maintained one

Kafka Streams is a JVM-only library by design (state stores, changelog replication, and the rebalance protocol are all implemented in the Java client). The npm package literally named `kafka-streams` — a JS reimplementation of the same KStream/KTable ideas — is real but effectively abandoned: `npm view kafka-streams time.modified` reports **`2022-06-19`**, over four years before this lesson was written, with no `deprecated` flag set but no activity either. There is no maintained Node.js equivalent of Kafka Streams; the options from a Node.js codebase are a plain consumer (this course's default), calling out to a JVM Streams service, or reaching for the next lesson's tool, Kafka Connect, when the job is data movement rather than transformation.

<Callout title="The one-line takeaway">
**Kafka Streams** is an **embedded Java library**: `KStream` is a feed of events, `KTable` is the latest value per key, and the stream-table duality links them — proven above with a real `TopologyTestDriver` run where `count()` emitted 8 update records for 2 input lines via an auto-inserted repartition topic. `group.protocol=streams` (KIP-1071) is real and enabled in 4.3.1 but GA **with named limits** (sticky assignment only, no warm-up, no static membership, offline-only migration). Co-partitioning is a real, documented requirement — but proven above that a live 4.3.1 run with mismatched partition counts did **not** fail fast, so verify partition counts yourself. `processing.guarantee=exactly_once_v2` makes read-process-write safe. There is no maintained JS equivalent (`kafka-streams` on npm: last published 2022).
</Callout>

## Mental Model

Kafka Streams' entire value proposition is turning three hard distributed-systems problems -- local state that survives a crash, exactly-once read-process-write, and rebalancing worker instances -- into library calls instead of code you write yourself. Every proof in this lesson shows where that abstraction is solid (a real `TopologyTestDriver` run producing exactly the update stream the stream-table duality predicts, a real `exactly_once_v2` transactional guarantee shared with the delivery-and-transactions module) and where it is newer and narrower than it looks (KIP-1071's named limits, and a co-partitioning safety net that did not fire in one real, reproducible run). Treat "Kafka Streams handles it" as true for state and exactly-once, and verify-it-yourself for anything the release notes call out as GA "with a limited feature set."

## Trade-offs

- **TopologyTestDriver** -- proven above as a genuine, broker-free way to unit-test a topology's exact output, at the cost of not exercising real partition assignment or co-partitioning enforcement (that gap is exactly what the co-partitioning section above surfaced by testing against a real broker instead).
- **`group.protocol=streams` (KIP-1071)** -- centralized, broker-side task assignment and better observability, at the cost of the named 4.2 limitations (no warm-up tasks, no rack-aware placement, no static membership, offline-only protocol migration).
- **`exactly_once_v2`** -- a real, load-bearing guarantee (shared mechanism with [Exactly-Once Processing](/kafka/en/delivery-and-transactions/exactly-once-processing/)), at the cost of transaction coordinator overhead on every commit interval.
- **Kafka Streams vs Kafka Connect vs a plain consumer** -- Streams is for genuine transform/join/aggregate logic with state; reach for Connect (next lesson) when the job is pure data movement, and a plain consumer when you need another language or full manual control.

## Common Misconceptions

- **"`count()` on a KTable emits one record per key with the final total."** Proven false above: the real run emitted 8 records for 2 input lines because a KTable's changelog emits every intermediate update, not just the last one — a consumer of `word-counts` sees the whole update history, not a snapshot.
- **"Kafka Streams always throws immediately if two joined topics have different partition counts."** Proven false above (SpotTheBug) with a real, reproducible run on 4.3.1 that reached `RUNNING` with mismatched partitions and no exception — the documented fail-fast behavior did not fire in this run.
- **"`group.protocol=streams` is fully GA with no caveats, since the release notes say GA."** The release announcement's own words are "GA with a limited feature set" — sticky-assignment-only, no warm-up/rack-aware/static-membership, offline-only migration, verified via the KIP-1071 wiki.
- **"There's a maintained Node.js Kafka Streams."** The `kafka-streams` npm package exists but was last published in 2022 — effectively abandoned, verified via `npm view`.
