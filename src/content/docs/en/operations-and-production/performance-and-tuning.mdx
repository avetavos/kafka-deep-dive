## The idea in one sentence

Tuning Kafka is choosing where you sit on the throughput-versus-latency curve, and every number in this lesson is from **local Docker, a single broker, on this Mac** — real, reproducible, and not a substitute for benchmarking your own workload on your own hardware.

## Proof: partition count, measured — not just asserted

Two topics, identical broker, identical producer settings, only the partition count differs:

```bash
# scripts/performance-and-tuning/partition-count-perf.sh
/opt/kafka/bin/kafka-topics.sh --bootstrap-server "$BOOTSTRAP" \
  --create --topic perf-1p --partitions 1 --replication-factor 1
/opt/kafka/bin/kafka-topics.sh --bootstrap-server "$BOOTSTRAP" \
  --create --topic perf-12p --partitions 12 --replication-factor 1

echo "=== 1 partition ==="
/opt/kafka/bin/kafka-producer-perf-test.sh --topic perf-1p \
  --num-records 200000 --record-size 200 --throughput -1 \
  --producer-props bootstrap.servers="$BOOTSTRAP" acks=1 2>&1 | tail -1

echo "=== 12 partitions ==="
/opt/kafka/bin/kafka-producer-perf-test.sh --topic perf-12p \
  --num-records 200000 --record-size 200 --throughput -1 \
  --producer-props bootstrap.servers="$BOOTSTRAP" acks=1 2>&1 | tail -1
```

Real, unedited output:

```text
=== 1 partition ===
200000 records sent, 204708.290686 records/sec (39.05 MB/sec), 91.32 ms avg latency, 197.00 ms max latency, 99 ms 50th, 189 ms 95th, 192 ms 99th, 193 ms 99.9th.

=== 12 partitions ===
200000 records sent, 328407.224959 records/sec (62.64 MB/sec), 1.37 ms avg latency, 175.00 ms max latency, 1 ms 50th, 3 ms 95th, 5 ms 99th, 11 ms 99.9th.
```

Same single broker, same disk, same producer config — **~60% higher throughput and ~66x lower average latency** with 12 partitions instead of 1. This is local Docker on one Mac, not a capacity-planning number for your cluster, but the *direction* is real and explainable: with one partition, every append serializes through that one partition's single log-writer path; with 12 partitions, the broker's I/O threads (8 by default, proven below) can append to 12 independent logs concurrently instead of queuing behind one.

<Callout title="Do not over-read this specific ratio">
`~60%` and `~66x` are this run, this Mac, this Docker setup — not a universal multiplier. The lesson is the *existence and direction* of the effect (more partitions parallelize broker-side append work up to the I/O thread count), not that "12 partitions" is a magic number. [Partition count trade-offs](/kafka/en/foundations/brokers-topics-partitions/#choosing-a-partition-count) covers sizing to actual target throughput, not to whatever wins a local benchmark.
</Callout>

## `kafka-consumer-perf-test.sh`, and a real gotcha in its own output

```bash
# scripts/performance-and-tuning/consumer-perf-test.sh
/opt/kafka/bin/kafka-consumer-perf-test.sh --bootstrap-server "$BOOTSTRAP" \
  --topic perf-12p --num-records 200000

# Clean up both scratch topics this lesson created above.
/opt/kafka/bin/kafka-topics.sh --bootstrap-server "$BOOTSTRAP" --delete --topic perf-1p
/opt/kafka/bin/kafka-topics.sh --bootstrap-server "$BOOTSTRAP" --delete --topic perf-12p
```

```text
start.time, end.time, data.consumed.in.MB, MB.sec, data.consumed.in.nMsg, nMsg.sec, rebalance.time.ms, fetch.time.ms, fetch.MB.sec, fetch.nMsg.sec
2026-09-29 02:42:04:251, 2026-09-29 02:42:07:878, 38.1470, 10.5175, 200000, 55141.9906, 3459, 168, 227.0653, 1190476.1905
```

Reading the columns literally, `nMsg.sec` (55,142/sec, blending group-join time in) looks far slower than `fetch.nMsg.sec` (1,190,476/sec, fetch time only) — a ~21x difference in the **same run**, because `rebalance.time.ms` (3,459 ms — the group coordinator handshake) dwarfs `fetch.time.ms` (168 ms — the actual data transfer) on a tiny 200,000-record test. A real consumer-perf-test number that blends rebalance time into "throughput" will make Kafka look dramatically slower than it is for a short benchmark; for anything beyond a quick sanity check, look at `fetch.MB.sec`/`fetch.nMsg.sec` specifically, or run a large enough record count that one-time rebalance cost stops dominating the average.

This lesson's own partition-count run above used the **same tool, same broker family, same Mac**, confirming those numbers are not a one-off: `kafka-producer-perf-test.sh` throughput in the low-to-mid hundreds-of-thousands of records/sec range, single broker, local Docker, is this environment's consistent order of magnitude across multiple independent lessons.

## Thread pools: `num.io.threads`, `num.network.threads`, `num.replica.fetchers`, and the real signal to watch

Real defaults, read directly off this lesson's own broker:

```text
$ kafka-configs.sh --bootstrap-server localhost:9092 --describe --entity-type brokers --entity-name 1 --all | grep -E "num\.(io|network|replica\.fetchers)"
num.io.threads=8 sensitive=false synonyms={DEFAULT_CONFIG:num.io.threads=8}
num.network.threads=3 sensitive=false synonyms={DEFAULT_CONFIG:num.network.threads=3}
num.replica.fetchers=1 sensitive=false synonyms={DEFAULT_CONFIG:num.replica.fetchers=1}
```

- **`num.io.threads`** (8) — threads that do the actual disk I/O for produce/fetch requests once the network layer has read them off the wire. Too few and requests queue behind disk operations even with plenty of network capacity.
- **`num.network.threads`** (3) — threads that read requests off the socket and write responses back; too few and clients see connection-level slowness even when disk I/O is fast.
- **`num.replica.fetchers`** (1) — threads a **follower** broker uses to fetch from the leader; irrelevant on this course's single-broker setups (RF=1, no followers), but the first knob to raise on a real multi-broker cluster if replication itself is falling behind (visible as `UnderReplicatedPartitions` rising, proven in the [previous lesson](/kafka/en/operations-and-production/monitoring-and-consumer-lag/)).

`RequestHandlerAvgIdlePercent` (introduced in that same lesson) is the real signal for whether `num.io.threads` is sized right — not a guess, a direct measurement. Running this lesson's heaviest producer load (millions of records, `acks=1`, default batching) against this single-threaded `kafka-producer-perf-test.sh` client and sampling mid-run:

```text
kafka.server:type=KafkaRequestHandlerPool,name=RequestHandlerAvgIdlePercent:OneMinuteRate=0.9810855172428229
```

Still **~98% idle** under this lesson's heaviest sustained load. The honest conclusion is *not* "8 threads is oversized" — it is that **one single-threaded producer process on one Mac cannot generate enough concurrent request volume to meaningfully load 8 I/O threads on a local broker.** Saturating that metric for real needs many concurrent client connections, which is exactly why `RequestHandlerAvgIdlePercent` trending down in *production* (many real clients) is meaningful, while the same metric staying flat in a single-client local benchmark is not evidence either way about the broker's true capacity.

<Callout title="A real result that resists over-interpretation">
This lesson genuinely tried to saturate the broker's request-handler threads locally and could not, with the tooling available. That is itself the lesson: local single-client benchmarks are good for *relative* comparisons (partition count, batching, compression — all proven above with real deltas) and bad for *absolute* capacity claims (thread-pool sizing under real concurrent load needs real concurrent load, not one client).
</Callout>

## Page cache, and why Kafka avoids the JVM heap for data

Kafka's own design documentation is explicit about this (quoted from `kafka.apache.org/43/design/design/`): *"rather than maintain as much as possible in-memory and flush it all out to the filesystem in a panic when we run out of space, we invert that"* — Kafka writes through to the filesystem immediately and lets the **OS page cache**, not the JVM heap, hold hot data in memory. Serving a fetch request that is already in page cache uses `sendfile`, and the same docs state directly: *"Using sendfile, this re-copying is avoided by allowing the OS to send the data from pagecache to the network directly"* — the kernel moves bytes from page cache to the network socket without ever copying them into the JVM's user-space heap. The same page also states the durability consequence for consumers that are caught up: *"you will see no read activity on the disks whatsoever as they will be serving data entirely from cache."* [Storage & Segments](/kafka/en/kafka-internals/storage-and-segments/) covers the on-disk segment format this zero-copy path reads directly from — not repeated here.

<Mermaid title="Zero-copy: page cache to network socket, no JVM heap copy" code={zeroCopyFlow} />

export const zeroCopyFlow = `flowchart LR
  disk["Disk"] -->|"read once"| cache["OS page cache"]
  cache -->|"sendfile() -- zero-copy"| socket["Network socket"]
  socket --> consumer["Consumer"]
  cache -.->|"NOT copied into"| heap["JVM heap (bypassed)"]`;

This is also the practical reason Kafka broker JVM heaps stay deliberately small (a few GB is typical, even on machines with far more RAM) — a large heap steals RAM the page cache would otherwise use for exactly the data Kafka is trying to serve fast, and a large heap means longer GC pauses on the broker's own request-handling path.

## Configs that exist and that you should still leave alone

`socket.send.buffer.bytes` (real default, `102400` — confirmed on this lesson's broker, same command as above) sizes the OS-level TCP send buffer per connection; raising it can help high-latency/high-bandwidth network paths, but on a healthy local network it makes no measurable difference, and setting it too high just reserves memory per connection that a busy broker with many connections will feel.

`log.flush.*` is a different case — not "rarely helpful," but **actively dangerous to touch** on most workloads. This lesson's own broker's real values:

```text
log.flush.interval.messages=9223372036854775807 sensitive=false synonyms={DEFAULT_CONFIG:log.flush.interval.messages=9223372036854775807}
log.flush.scheduler.interval.ms=9223372036854775807 sensitive=false synonyms={DEFAULT_CONFIG:log.flush.scheduler.interval.ms=9223372036854775807}
```

`9223372036854775807` is `Long.MAX_VALUE` — Kafka's real default is to **never** force an `fsync` based on message count or a fixed interval. Durability comes from **replication** (multiple brokers holding the data) and **`acks`**/**`min.insync.replicas`**, proven throughout [producers](/kafka/en/producers/acks-and-durability/) and [delivery-and-transactions](/kafka/en/delivery-and-transactions/delivery-guarantees/), not from forcing every write to disk before acking. Setting `log.flush.interval.messages` low adds a real `fsync` on the broker's hot write path for every batch, which measurably lowers throughput and *still* does not substitute for real replication — a single un-replicated broker that fsyncs on every message is still a single point of data loss if that disk dies.

## OS limits that matter at scale — cited, not run

More partitions means more open files and more memory-mapped regions, and two real OS defaults become load-bearing once a broker hosts many of them. From Kafka's own operations documentation (`kafka.apache.org/43/operations/hardware-and-os/`):

> Kafka recommends at least 100,000 allowed file descriptors for the broker processes as a starting point. If a broker hosts many partitions, the broker needs at least `(number_of_partitions) * (partition_size / segment_size)` file descriptors to track all log segments, in addition to the number of connections the broker makes.

> By default, on a number of Linux systems, the value of `vm.max_map_count` is somewhere around 65,535. Each log segment... requires a pair of index/timeindex files, and each of these files consumes 1 map area... Creating 50,000 partitions on a broker will result in allocation of 100,000 map areas and likely cause broker crash with `OutOfMemoryError (Map failed)` on a system with default `vm.max_map_count`.

This course's own Docker containers already run with generous limits — confirmed directly, not from docs:

```text
$ docker exec broker sh -c 'ulimit -n; cat /proc/sys/vm/max_map_count'
1048576
262144
```

`1,048,576` open files and a `262,144` `vm.max_map_count` — both already well above the bare Linux defaults the docs warn about, which is exactly why this course's own single-broker, low-partition-count lessons never hit either limit. A real production host provisioned with plain OS defaults, running a broker with tens of thousands of partitions, genuinely can hit both — the fix is the `sysctl`/`ulimit` values quoted above, applied **before** the broker is under that load, not after the `OutOfMemoryError` the docs describe.

<Callout title="The one-line takeaway">
Every throughput/latency number in this lesson is local-Docker-on-one-Mac, proven above with real `kafka-producer-perf-test.sh`/`kafka-consumer-perf-test.sh` output: 12 partitions genuinely beat 1 partition on the same broker (~60% more throughput, ~66x lower latency, this run), and `RequestHandlerAvgIdlePercent` staying near-`1.0` under this lesson's heaviest single-client load is itself a real, honest result about the limits of local single-client benchmarking, not a claim about the broker's true ceiling. Kafka's own design docs (quoted above) explain why the JVM heap stays small and the OS page cache plus `sendfile` zero-copy does the real work. `log.flush.*` defaults to `Long.MAX_VALUE` (proven above) because durability is replication's job, not `fsync`'s. And `vm.max_map_count`/file descriptor limits (cited above from the real ops docs) are dormant on this course's small setups and genuinely load-bearing on a real cluster with tens of thousands of partitions.
</Callout>

## Reading AI-generated code

<SpotTheBug lang="properties" code={`# section: broker
# AI comment: "Tune for maximum durability and consistency"
log.flush.interval.messages=1
log.flush.interval.ms=1000
num.io.threads=64
`}>

This reads like a careful, durability-first tuning pass — flush constantly so nothing sits unflushed for long, and throw more I/O threads at the broker for good measure. The real problem, proven above: Kafka's actual durability mechanism is replication (`acks`, `min.insync.replicas`) — forcing an `fsync` on every single message (`log.flush.interval.messages=1`) adds a real, measurable write-path cost on every batch for a guarantee replication already provides more robustly (surviving a whole broker's disk failing, which a single broker's own `fsync` discipline cannot do at all). `num.io.threads=64` is not "more tuning" either — proven above, this course's own broker could not push its default **8** threads past ~98% idle with a real, heavy single-client load; raising the thread count on a broker that is not I/O-thread-bound spends memory and context-switch overhead on threads that will sit idle, and does nothing for the actual bottleneck (which, on a single disk, is more likely the disk itself, or — proven above — the number of partitions available to parallelize across in the first place).

</SpotTheBug>

## Mental Model

Every Kafka performance number lives on one of three independent axes: **producer-side** (batching, compression, partition count — how fast you can get bytes accepted), **broker-side** (thread pools, page cache, disk — how fast the broker can process and store what it receives), and **consumer-side** (fetch size, parallelism, group rebalance overhead — how fast you can get bytes back out). This lesson proved a real producer-side win (partitions), a real broker-side non-result (thread pools not saturated locally), and a real consumer-side gotcha (rebalance time dominating a short benchmark). Tuning the wrong axis for your actual bottleneck is the single most common mistake — proven directly by this lesson's own `SpotTheBug`, which "tunes" durability and I/O threads while the real durability mechanism (replication) and the real throughput lever this lesson measured (partition count) go untouched.

## Trade-offs

- **More partitions for producer/consumer parallelism** — proven above, real throughput and latency wins on the same broker — versus the real cost proven in [Brokers, Topics & Partitions](/kafka/en/foundations/brokers-topics-partitions/): more open files, more controller metadata, longer rebalances. There is a real ceiling; this lesson does not locate it, only proves the direction below it.
- **Raising thread-pool sizes** — free to configure, but proven above to be meaningless when the workload never approaches saturating the defaults; real cost is memory and context-switching overhead paid regardless of whether the threads ever do useful work.
- **Touching `log.flush.*` for "extra safety"** — feels conservative, is provably (via the real defaults above) not how Kafka's own durability model works, and has a real, direct throughput cost with no corresponding durability benefit once replication is configured correctly.
- **Local single-broker Docker benchmarks** — cheap, repeatable, genuinely useful for *relative* comparisons (this lesson's partition-count and batching cross-link results) — and not a substitute for load-testing your real cluster under real concurrent client load before trusting any absolute number.

## Common Misconceptions

- **"More `num.io.threads` always means better throughput."** No — proven above: this course's broker sat at ~98% idle on `RequestHandlerAvgIdlePercent` under its heaviest local test; more threads help only when the current pool is actually the bottleneck, which this lesson could not even produce locally with a single client.
- **"Frequent `log.flush.interval.messages` makes Kafka more durable."** No — proven above: the real default is `Long.MAX_VALUE` (effectively never), because durability comes from replication and `acks`, not per-message `fsync`; forcing frequent flushes adds real cost for a guarantee it does not actually strengthen.
- **"`kafka-consumer-perf-test.sh`'s headline `nMsg.sec` number is the tool's real fetch throughput."** No — proven above: that number blends one-time `rebalance.time.ms` into the average; the real fetch-only throughput (`fetch.nMsg.sec`) was over 20x higher in the same run.
- **"Kafka is fast despite writing every message to disk."** Backwards — proven above with Kafka's own design docs quoted directly: Kafka is fast *because* it writes to disk immediately and lets the OS page cache plus `sendfile` zero-copy do the serving, deliberately avoiding a competing in-process JVM cache rather than working around disk writes.
