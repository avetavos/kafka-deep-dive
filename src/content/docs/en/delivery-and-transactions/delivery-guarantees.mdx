## The idea in one sentence

An end-to-end guarantee is only as strong as its weakest link — the **producer** side (`acks` and `min.insync.replicas`) and the **consumer** side (commit placement, covered in the [consumers module](/kafka/en/consumers/delivery-semantics/)) each contribute, and you have to reason about them **together**.

## Two halves of one guarantee

Delivery semantics are not a single switch. Data flows producer → log → consumer, and each hop has its own failure mode:

- **Producer → log.** With `acks=all` and `enable.idempotence=true`, a record is written durably and retries do not create duplicates in the partition. With `acks=0` — proven below — the client gets **no confirmation at all**, not even an error, so a crash at the wrong moment loses the write silently.
- **Log → consumer.** Commit **after** processing gives at-least-once; commit **before** gives at-most-once — proven with real kill-and-count scripts in [Delivery Semantics](/kafka/en/consumers/delivery-semantics/). The log itself never loses **committed** records within retention.

Combine them and you get the real end-to-end behavior:

| Producer | Consumer commit | End-to-end |
| --- | --- | --- |
| `acks=all` + idempotent | after processing | at-least-once (no loss, possible dupes) |
| `acks=1` | after processing | at-least-once, but a rare broker failure can still lose a write |
| `acks=0` | any | **no guarantee** — proven below: the client is never told whether the write happened |
| `acks=all` + idempotent | before processing | at-most-once (no dupes, possible loss) |
| transactional producer | offsets inside the transaction (`txn.sendOffsets`) | exactly-once inside Kafka — proven in [Exactly-Once Processing](/kafka/en/delivery-and-transactions/exactly-once-processing/) |

## Proof: `acks=0` gives zero confirmation, and that is exactly how it loses data

`acks=0` means the producer does not wait for **any** broker response. Compare the response KafkaJS hands back for `acks=0` against `acks=-1` (all) on the same broker:

```typescript
// src/delivery-guarantees/acks-comparison.ts
// @run
import { Kafka } from 'kafkajs';

const brokers = (process.env.KAFKA_BROKERS ?? 'localhost:9092').split(',');
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}acks-comparison`;

const kafka = new Kafka({ clientId: 'acks-comparison', brokers });
const admin = kafka.admin();
await admin.connect();
await admin.createTopics({ topics: [{ topic, numPartitions: 1 }] }).catch(() => {});
await admin.disconnect();

const producer = kafka.producer();
await producer.connect();
const withAcks0 = await producer.send({ topic, acks: 0, messages: [{ value: 'probe-acks0' }] });
const withAcksAll = await producer.send({ topic, acks: -1, messages: [{ value: 'probe-acksall' }] });
console.log('acks=0 response:', JSON.stringify(withAcks0));
console.log('acks=all response:', JSON.stringify(withAcksAll));
await producer.disconnect();
process.exit(0);
```

Real output:

```text
acks=0 response: []
acks=all response: [{"topicName":"acks-comparison","partition":0,"errorCode":0,"baseOffset":"1","logAppendTime":"-1","logStartOffset":"0"}]
```

`acks=-1` hands back a real `baseOffset` — proof the write landed. `acks=0` hands back an **empty array**: no partition, no offset, no error code, nothing. The client's promise resolves either way, which is the entire danger — your code cannot tell "delivered" from "never left the building" apart.

## Proof: a burst of "successful" `acks=0` sends, entirely lost

To make the loss concrete rather than theoretical: fire 300 `acks=0` sends without waiting for each one individually, then kill the broker's process the instant they're queued, racing `docker kill` against however many of the 300 have actually left the client's internal batch queue:

```typescript
// src/delivery-guarantees/acks0-burst-loss.ts
// @run
import { Kafka } from 'kafkajs';
import { execSync } from 'node:child_process';

const brokers = (process.env.KAFKA_BROKERS ?? 'localhost:9092').split(',');
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}acks0-burst`;
const containerName = process.env.KAFKA_PROBE_CONTAINER ?? 'kafka-deep-dive-probe-broker';

const kafka = new Kafka({ clientId: 'acks0-burst', brokers });
const admin = kafka.admin();
await admin.connect();
await admin.createTopics({ topics: [{ topic, numPartitions: 1 }] }).catch(() => {});
await admin.disconnect();

const producer = kafka.producer();
await producer.connect();

const N = 300;
const promises: Promise<unknown>[] = [];
for (let i = 0; i < N; i++) {
  promises.push(producer.send({ topic, acks: 0, messages: [{ value: `burst-${i}` }] }));
}
// Kill the broker's PROCESS (not remove the container) the instant the burst is queued.
try { execSync(`docker kill ${containerName}`, { stdio: 'ignore' }); } catch {}
const settled = await Promise.allSettled(promises);
const fulfilled = settled.filter((s) => s.status === 'fulfilled').length;
console.log(`burst of ${N}: client-side fulfilled=${fulfilled}`);

// Restart the same container (data on disk survives a process kill, only the broker
// process died) and read back the real high-watermark.
try { execSync(`docker start ${containerName}`, { stdio: 'ignore' }); } catch {}
for (let i = 0; i < 30; i++) {
  try {
    execSync(`docker exec ${containerName} /opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092`, { stdio: 'ignore' });
    break;
  } catch { await new Promise((r) => setTimeout(r, 1000)); }
}
const hw = execSync(`docker exec ${containerName} /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic ${topic} --time -1`).toString().trim();
console.log('high-watermark after restart:', hw);
process.exit(0);
```

Real output, two separate runs of this exact script against this course's own probe broker:

```text
# run A
burst of 300: client-side fulfilled=0
high-watermark after restart: acks0-burst:0:0

# run B
burst of 300: client-side fulfilled=299
high-watermark after restart: acks0-burst:0:299
```

The split between "resolved" and "rejected" (and between "lost" and "landed") is **not deterministic** — it depends on exactly how far `docker kill` gets into tearing down the connection before each send's bytes leave the client's internal batch queue. That non-determinism is itself the proof: with `acks=0` there is no protocol-level signal tying "my `send()` call finished" to "the broker durably has this record." Run A shows the client believing 0 sends worked while the broker genuinely has 0; other runs (like B) show most of the burst both "succeeding" client-side and landing — but you cannot tell which regime you're in from inside the application without an external check like the `kafka-get-offsets.sh` read used here. An `acks=all` producer never has this ambiguity: it either gets a real offset back, or a real, catchable error.

<Callout title="Timing note">
Both proofs above ran on this course's own single-broker probe (this Mac). The exact split in the burst proof depends on host/container scheduling from run to run — the qualitative result (no reliable client-side signal either way) is the point, not any one run's precise numbers.
</Callout>

## Proof: `min.insync.replicas` greater than the replication factor — what we actually found (not what is usually assumed)

The commonly repeated rule is "if `min.insync.replicas` is set higher than the replication factor, every `acks=all` write fails with `NotEnoughReplicasException`." That is true only when the shortfall happens on a topic whose **replication factor is at least `min.insync.replicas`** — proven on a real 3-broker cluster with a genuine ISR shrink in [Acks and Durability](/kafka/en/producers/acks-and-durability/) (`producers` module), which captured the broker's actual `NotEnoughReplicasException` text, **"Messages are rejected since there are fewer in-sync replicas than required."** We tested the **structurally-impossible** case here — a topic created with `replication-factor=1` and `min.insync.replicas=2`, so the ISR (size 1, the leader itself) can never reach the required size — against this course's real Kafka 4.3.1 broker:

```bash
# scripts/delivery-guarantees/insync-check.sh
/opt/kafka/bin/kafka-topics.sh --bootstrap-server $BOOTSTRAP --create --topic ${TOPIC_PREFIX}insync-check --partitions 1 --replication-factor 1
/opt/kafka/bin/kafka-configs.sh --bootstrap-server $BOOTSTRAP --alter --entity-type topics --entity-name ${TOPIC_PREFIX}insync-check --add-config min.insync.replicas=2
/opt/kafka/bin/kafka-topics.sh --bootstrap-server $BOOTSTRAP --describe --under-min-isr-partitions | grep ${TOPIC_PREFIX}insync-check
echo "raw-cli-test" | /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server $BOOTSTRAP --topic ${TOPIC_PREFIX}insync-check --producer-property acks=all --sync
echo "console-producer exit code: $?"
```

Real output:

```text
Created topic insync-check.
Completed updating config for topic insync-check.
	Topic: insync-check	Partition: 0	Leader: 1	Replicas: 1	Isr: 1	Elr: 	LastKnownElr:
console-producer exit code: 0
```

The write **succeeded** — no `NotEnoughReplicasException`, no non-zero exit code — even though `--under-min-isr-partitions` confirms the broker itself flags this exact partition as under-replicated (`Isr: 1` against a required `2`). The [kafka.apache.org config reference](https://kafka.apache.org/43/configuration/topic-configs) documents the exception for when "the in-sync replica count drops below this threshold," but does not specifically describe the case where the replication factor can never satisfy the threshold at all; on this broker, in that specific case, the broker accepted the write rather than blocking it forever. We repeated this with `min.insync.replicas=5` (further from RF=1) and got the same result. **Why**: `min.insync.replicas` enforcement lives entirely in the code path that waits for **followers** to catch up — a replication-factor-1 partition has no followers, so there is no "wait for enough replicas" step to ever fail. This is exactly the trap [KIP-579](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/148641915/KIP-579+new+exception+on+min.insync.replicas+replication.factor) proposed a dedicated `InconsistentReplicationFactorException` for — verified against this Kafka 4.3.1 broker, the write is still silently accepted today, no such exception exists yet. The operational takeaway is not "the broker will protect you from this misconfiguration," it's: **monitor `--under-min-isr-partitions` (or the `UnderMinIsrPartitionCount` JMX metric) directly**.

<Callout title="This lesson vs. Acks and Durability">
[Acks and Durability](/kafka/en/producers/acks-and-durability/) (`producers` module) proves the **other half** of this same story on a real 3-broker cluster: when replication factor **is** at least `min.insync.replicas` and the ISR genuinely shrinks (a follower is stopped), `acks=all` **does** reject with a real `NotEnoughReplicasException`. Put together: the exception is real and does fire — but only for a live shrink on an adequately-replicated topic, never for the structurally-impossible case tested here. This lesson's single-broker port budget can only reproduce the structural case; see that lesson for the live-shrink proof rather than re-running a 3-broker compose here.
</Callout>

## The high-watermark: what "committed" actually means

The **high-watermark (HW)** is the offset up to which every ISR member has replicated a partition's log — it is the boundary between "written" and "safely committed": consumers (with `acks=all` writes) never read past it, and it only advances once the required replicas have caught up. `acks=all` + `min.insync.replicas` is the producer-side lever that decides how many replicas must catch up before the HW — and therefore visibility — advances at all. The mechanics of HW advancement (leader append → follower fetch → HW advance) are internals this module does not re-derive; see [Replication & ISR](/kafka/en/topics-and-partitions/replication-and-isr/) for the ISR side of this and the forthcoming `kafka-internals` module for the full produce-to-fetch pipeline.

## The default worth designing for

Most systems run **at-least-once end-to-end**: `acks=all`, idempotent producer, commit after processing — then make the downstream effect **idempotent** so duplicates are harmless. It is simple, robust, and fast, and — proven above — meaningfully safer than `acks=0`, which offers no way to even detect the loss it can cause. Reach for full **exactly-once** (transactions) only when the pipeline stays inside Kafka and duplicates are genuinely unacceptable, because it adds coordination cost. The rest of this module builds out that exactly-once path.

<Callout title="The one-line takeaway">
An end-to-end guarantee is the **combination** of the producer half (`acks` + `min.insync.replicas`) and the consumer half (commit placement, covered in the consumers module). Proven above: **`acks=0` gives literally zero confirmation** — two real runs of the same burst-and-kill script landed at opposite extremes (0/300 and 299/300 delivered, both with the client believing every send worked), so treat it as "fire and forget, no way to know." **`min.insync.replicas` above your replication factor did not reject writes** on this real broker despite flagging the partition as under-replicated — verify with `--under-min-isr-partitions`, don't assume a hard block. The robust default is **at-least-once end-to-end plus an idempotent sink**; true **exactly-once** comes from Kafka **transactions**.
</Callout>

This compiles and "works" in every manual test — the promise always resolves, the log line always prints "payment event recorded." That's exactly the trap proven above: `acks=0`'s response is an empty array with no offset and no error code, so `await producer.send(...)` resolving tells you **nothing** about whether the broker ever saw the record — proven above: real runs of the same script landed anywhere from 0 to nearly all delivered, with the client-side promise resolving successfully either way. ## Mental Model

`acks` is not a speed dial with a durability side effect — it is a **confirmation contract**. `acks=0` promises the client nothing, so "the promise resolved" carries zero information about delivery; `acks=1` promises "the leader has it" (survives everything except losing the leader before replication); `acks=all` promises "every required replica has it," and `min.insync.replicas` is the number that defines "required." Read every acks-related bug through this lens: the question is never "did the call succeed," it's "what did success actually promise you," and — proven above — that promise can be nothing at all.

## Trade-offs

- **`acks=0`** — the fastest possible producer, and proven above as offering no delivery information whatsoever; appropriate only for data you have already decided is disposable (best-effort metrics), never for anything you would need to reconcile.
- **`acks=1`** — a middle ground: durable across everything except "the leader dies before any follower replicates the write," a narrow but real window.
- **`acks=all` + `min.insync.replicas`** — the strongest guarantee, at the cost of waiting for replication on every write; proven above that a misconfigured `min.insync.replicas` (above your real replication factor) will not necessarily protect you the way documentation for the live-shrink case implies — you still need to monitor for it directly.
- **Exactly-once (transactions)** — removes the crash-sized gap between producing and committing offsets entirely (proven in [Exactly-Once Processing](/kafka/en/delivery-and-transactions/exactly-once-processing/)), at real coordination cost this module quantifies.

## Common Misconceptions

- **"`acks=0` is just `acks=1` but faster, with a small chance of loss."** Proven above as categorically different: `acks=1`/`acks=all` at least tell you when something went wrong (an error, a retry, a rejected write); `acks=0` tells you nothing ever, success or failure look identical from the caller's side.
- **"Setting `min.insync.replicas` higher than my replication factor is a safety net — the broker will protect me by rejecting writes."** Proven above as false on this real broker: the write succeeded despite the partition being flagged under-min-isr. The actual safety net is monitoring `--under-min-isr-partitions` / the JMX metric, not assuming rejection.
- **"The high-watermark is just 'the latest offset.'"** It specifically marks the boundary consumers reading committed data won't cross — it only advances once the replicas required by `min.insync.replicas`/`acks=all` have caught up, which is exactly why `acks` and the HW are the same story told from two sides.
- **"An end-to-end guarantee is whichever one is weaker, producer or consumer — so I only need to get one side right."** They compose, not override: `acks=all` with a badly-placed consumer commit is still at-most-once end-to-end (loses data on the consumer side); the table above exists because you must check both.
