## The idea in one sentence

An **idempotent producer** tags every record with a producer id, epoch, and per-partition sequence number so the broker can **discard duplicates** created by retries — giving exactly-once delivery **per partition**.

## The duplicate problem retries create

Without idempotence, a retry can silently duplicate a record. The producer sends a record, the broker writes it, but the acknowledgement is lost on the way back. The producer times out, retries, and the broker writes the **same record a second time**. You now have two copies and no way to tell them apart. (The previous lesson proved exactly this — five real duplicate copies from one `send()` call — with `idempotent: false`.)

Idempotence fixes this: the broker assigns each producer a **producer id (PID)** and an **epoch**, and the producer stamps every record with a **monotonically increasing sequence number** per partition. When a record arrives, the broker checks the sequence number: if it has already seen it for that PID and partition, it **acknowledges but does not write** the record again.

<Callout title="On by default — but only in the Java client">
`enable.idempotence=true` is the **default in the Java client** (since Kafka 3.0). **KafkaJS defaults the other way — `idempotent: false`** — so you must opt in explicitly. Do not assume a KafkaJS producer is idempotent unless you set it yourself.
</Callout>

```properties
# The Java client: idempotence is on by default; shown explicitly here
enable.idempotence=true
# acks=all is required and applied automatically once idempotence is on
acks=all
# retries must be > 0 (defaults high) so the producer actually retries
retries=2147483647
# ordering is preserved only if in-flight requests per connection stays <= 5
max.in.flight.requests.per.connection=5
```

**KafkaJS** requires an explicit opt-in on the producer:

```typescript
const producer = kafka.producer({ idempotent: true })
```

## The real producer id, epoch, and sequence numbers, on disk

This is not an abstraction — it is real data in the record batch header on disk. Three records were sent with an idempotent KafkaJS producer, then the segment file was read directly with `kafka-dump-log.sh --print-data-log`:

```typescript
// src/idempotent-producer/send-three.ts
// @run
import { Kafka } from 'kafkajs';

const brokers = [process.env.KAFKA_BROKERS ?? 'localhost:9092'];
const prefix = process.env.TOPIC_PREFIX ?? '';
const topic = `${prefix}orders-idem-demo`;

const kafka = new Kafka({ clientId: 'idem-demo', brokers });

async function main() {
  const admin = kafka.admin();
  await admin.connect();
  await admin.createTopics({ topics: [{ topic, numPartitions: 1, replicationFactor: 1 }] });
  await admin.disconnect();

  const producer = kafka.producer({ idempotent: true });
  await producer.connect();
  for (let i = 0; i < 3; i++) {
    const [meta] = await producer.send({
      topic,
      messages: [{ key: `order-${i}`, value: `payload-${i}` }],
    });
    console.log(`sent order-${i} -> offset ${meta.baseOffset}`);
  }
  await producer.disconnect();
  process.exit(0);
}

main();
```

```bash
# scripts/idempotent-producer/dump-idempotent-log.sh

LOGFILE=$(find "$LOGDIR" -name '*.log' | head -1)
/opt/kafka/bin/kafka-dump-log.sh --print-data-log --files "$LOGFILE"
```

Real, trimmed output — one `baseSequence`/`lastSequence` per record, all sharing the same `producerId`:

```text
baseOffset: 0 ... producerId: 0 producerEpoch: 0 baseSequence: 0 lastSequence: 0
| offset: 0 sequence: 0 key: order-0 payload: payload-0
baseOffset: 1 ... producerId: 0 producerEpoch: 0 baseSequence: 1 lastSequence: 1
| offset: 1 sequence: 1 key: order-1 payload: payload-1
baseOffset: 2 ... producerId: 0 producerEpoch: 0 baseSequence: 2 lastSequence: 2
| offset: 2 sequence: 2 key: order-2 payload: payload-2
```

Every record from this producer session carries `producerId: 0` (the PID Kafka assigned this connection when `InitProducerId` ran) and `producerEpoch: 0`; the `sequence` climbs by exactly one per record, per partition. This is the literal mechanism the previous lesson's duplicate-retry proof relied on: when a retried attempt arrives with a `sequence` the broker already has recorded for that `(producerId, partition)`, it is dropped instead of appended.

## What `enable.idempotence` really requires — verified against the official config reference

Quoting `kafka.apache.org/43/configuration/producer-configs/` directly, on `enable.idempotence`:

> "enabling idempotence requires `max.in.flight.requests.per.connection` to be less than or equal to 5 (with message ordering preserved for any allowable value), `retries` to be greater than 0, and `acks` must be 'all'."

And on `max.in.flight.requests.per.connection`:

> "if this configuration is set to be greater than 1 and `enable.idempotence` is set to false, there is a risk of message reordering after a failed send due to retries" — and idempotence requires this value to be **at most 5**, "since brokers retain a maximum of 5 batches per producer" for sequence tracking.

That is a **ceiling of 5**, not a requirement of exactly 1 — the Java client (and the broker's own sequence-number cache) allow up to five in-flight batches per connection while still guaranteeing order, because the broker keeps enough history to detect an out-of-order or duplicate batch within that window.

<Callout title="Correction verified against KafkaJS's own source: this ceiling is not enforced client-side">
It would be easy to assume KafkaJS enforces the same 5-batch ceiling (or even forces `maxInFlightRequests` down to `1`) once you pass `idempotent: true`. It does not. Read directly from `kafkajs@2.2.4`'s source (`node_modules/kafkajs/src/producer/index.js`): the only things `idempotent: true` changes are the retry default (`retries: Number.MAX_SAFE_INTEGER`) and validation that retries aren't disabled — there is no code path that reads or clamps `maxInFlightRequests` based on `idempotent`. `maxInFlightRequests` remains the separate, unrelated `Kafka.producer({ maxInFlightRequests })` connection-pool option from the previous lesson, defaulting to `null` (unlimited). If you want the same safety margin the Java client's default gives you, **you must set `maxInFlightRequests: 5` yourself** — KafkaJS will not do it for you, and will not stop you from setting it higher.
</Callout>

```typescript
// idempotent: true does NOT imply or clamp maxInFlightRequests in KafkaJS —
// verified from source. Set the connection-pool cap yourself if you want it.
const producer = kafka.producer({ idempotent: true })
const kafka2 = new Kafka({ clientId: 'orders-app', brokers: ['localhost:9092'] });
const producerWithCap = kafka2.producer({ idempotent: true, maxInFlightRequests: 5 })
```

## What it requires, and what it guarantees

Idempotence is not free-standing — it needs a specific configuration to hold its guarantee:

- **`acks=all`** — the record must be confirmed by all in-sync replicas.
- **`retries > 0`** — retries are what create duplicates in the first place; without them there is nothing to dedupe.
- **`max.in.flight.requests.per.connection <= 5`** — up to five in-flight batches are allowed while **still preserving ordering**, because the broker tracks sequence numbers and rejects anything out of order.

In the Java client these three are **enforced configuration constraints** (setting them incompatibly with idempotence throws a `ConfigException` at producer construction). In **KafkaJS**, only `acks` and `retries` are actually forced by the client when `idempotent: true` — `maxInFlightRequests` is left entirely up to you, per the correction above.

When those hold, you get **exactly-once delivery per partition on retries**: no matter how many times a record is retried, it is written **once**. The **epoch** is what makes this safe across producer restarts and network partitions — a newer epoch **fences** an older, possibly zombie, producer instance so stale writes are refused.

## Idempotence is not transactions

This is a common mix-up. Idempotence guarantees a record is written **once per partition** despite retries — but that is the **only** thing it does. It does **not** make a multi-record, multi-partition write atomic, and it does **not** tie a producer write to a consumer offset commit.

That stronger guarantee — atomic writes across partitions and true exactly-once processing — is what **transactions** provide, built **on top of** the idempotent producer. The Delivery Semantics and Transactions module covers `transactionalId`, `producer.transaction()`, and `txn.commit()`. For now, hold the boundary: idempotence removes retry duplicates; transactions add atomicity.

<Callout title="The one-line takeaway">
An idempotent producer stamps records with a **producer id**, **epoch**, and **sequence number** (proven above, directly on disk) so the broker discards retry **duplicates**, giving **exactly-once per partition**. The Java client requires **`acks=all`**, **`retries > 0`**, and **`max.in.flight.requests.per.connection <= 5`** — and enforces all three. **KafkaJS only enforces the first two**; the in-flight ceiling is yours to set. It is the **default in the Java client**, but in **KafkaJS you must opt in** with `idempotent: true` — and it is **not** the same as full **transactions**.
</Callout>

## Mental Model

Idempotence moves duplicate-detection from "does this look like the same record?" (a content comparison, which is fragile and expensive) to "have I already applied this exact `(producerId, partition, sequence)` coordinate?" (an integer comparison the broker can do in constant time, tracked per partition, bounded to the last few batches). It is fundamentally a **coordinate system**, not a content filter — two records with byte-identical `key`/`value` but different sequence numbers are two different records to the broker, and a genuine retry of the same attempt is recognized purely by its coordinate matching one already seen, never by comparing payloads.

## Trade-offs

- **`idempotent: true`, default `maxInFlightRequests` (`null`, unlimited)** — matches KafkaJS's actual, verified default behavior; convenient, but silently gives up the ordering/duplicate-detection safety margin the Java client would have enforced for you.
- **`idempotent: true, maxInFlightRequests: 5`** — matches the Java client's real ceiling exactly, keeps the broker's 5-batch sequence cache able to track every in-flight batch; the safe, deliberate choice for anything durability-sensitive.
- **`idempotent: true, maxInFlightRequests: 1`** — strictly serializes requests per connection; the simplest mental model and zero risk of exceeding the broker's tracking window, at a real throughput cost (no pipelining).
- **`idempotent: false`** (the KafkaJS default) — no PID/epoch/sequence machinery at all, the cheapest option, but every retry is a potential silent duplicate (proven in the previous lesson).

## Common Misconceptions

- **"`idempotent: true` in KafkaJS automatically caps or validates `maxInFlightRequests` like the Java client does."** No — proven from source: KafkaJS applies no such clamp or validation. You must set the ceiling yourself.
- **"The idempotent producer requires `max.in.flight.requests.per.connection` to be exactly 1."** No — verified against the official config reference: the real requirement is **`<= 5`**, because the broker retains up to 5 batches per producer for sequence tracking. `1` is the strictest safe value, not the only safe value.
- **"Idempotence and transactions are the same feature, just different names."** No — idempotence only guarantees a record lands once per partition on retry; it has no concept of atomically writing across partitions or of consumer offsets. That is what transactions add on top.
- **"The producer id in the dump-log output is some kind of random UUID."** No — it is a small monotonically-assigned integer (`producerId: 0`, `1`, `9`, ... in this course's own runs) handed out by the broker's `InitProducerId` handler per producer session, paired with an `epoch` that increments on producer restart to fence out stale instances.
